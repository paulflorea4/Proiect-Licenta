## 6.1b — `pydantic-settings` config class

- **New dependency `pydantic-settings` (gate, approved by the human).** Offered against a hand-written class over `os.environ`, which would not read `ai-service/.env` itself. It brings `python-dotenv` as its only new package. Added without a version bound in `pyproject.toml`, like `fastapi` and `uvicorn` (`uv add` wrote `>=2.16.1`, removed to match); `uv.lock` pins 2.16.1 and 1.2.4.
- **Only `AI_SERVICE_TOKEN` is required now.** The row says the service refuses to start without it. `.env.example` says the API key is only needed once the service calls the real API (6.2a), and the model is not used before then either, so both are optional (`None`) until 6.2a, which will refuse to build the Gemini provider without them. The model has no default anywhere, as the root `CLAUDE.md` asks.
- **Blank is empty.** A token of spaces is refused like an empty one; a blank Gemini value is `None`. A token is not trimmed or otherwise changed (the backend compares it as it is), and no minimum length is enforced: none is written anywhere, and `.env.example` already asks for a long random value. Left to the human if wanted.
- **"Refuses to start" is the app's `lifespan`,** which calls `get_settings()` before serving: uvicorn prints the validation error (the variable's name and "must not be empty", never a value) and exits with code 3 (checked by hand with a real uvicorn start). Reading the settings at import time instead would have made `import ai_service.main` fail in every test without a token.
- **The token and the API key are `SecretStr`,** so the settings print as `**********` in a log line, a `repr` or a dump (the root `CLAUDE.md`: the token is never logged).
- **The `.env` path is found from the package's own location** (`DEFAULT_ENV_FILE`), not the working directory, so the service reads `ai-service/.env` however it is started. Real environment variables win over the file (pydantic-settings' order); unknown variables in the file are ignored, so one shared file with other services' variables would not stop it.
- **Tests never read the developer's own `.env`:** `tests/conftest.py` sets `config.ENV_FILE` to `None`, a test token and no Gemini values for every test, and clears the `get_settings` cache around each. A test that wants a file writes one in `tmp_path`.
- **Tests (+17, ai-service 1 -> 18; backend 2226 and frontend 3 unchanged and passing):** the three values from the environment and from a file; the environment wins; the default file is `ai-service/.env`; the settings are exactly the variables of `.env.example`; unknown variables ignored; a missing, empty or blank token refused (also the unfilled copy of `.env.example`); the app does not start without a token and answers `/health` with one; Gemini values optional, blank = unset; no secret in `str`, `repr` or a dump; settings read once.
- **Mutation-checked, each failing at least one test:** no blank check (3 failures); the token a plain `str` (4); the settings not read at startup (1); the env file never read (1).
- **Existing warning, not from this change:** pytest reports Starlette's `StarletteDeprecationWarning` about `httpx` in its test client (it was there before, with 1 test). Not acted on.

## 6.1c — Bearer-token authentication

- **"At the router level" = `protected_router()`.** It returns an `APIRouter` whose `dependencies` hold `require_bearer_token`, so every endpoint declared on it is checked and none can opt out. Every module that adds endpoints (`POST /feedback` in 6.5a first) creates its router with it and `main.py` includes it. A dependency on the whole app was the other way, but it would have had to skip `/health` by path inside the check; with routers, `/health` simply is not on one.
- **What makes "can't forget" true is the guard test,** as for the backend's matrices: `test_every_route_of_the_app_but_health_requires_the_token` lists every route of the real app and fails for any but `GET /health` that lacks the check (an endpoint put straight on `app`, a router built with `APIRouter()`, a mounted app). A positive control shows the guard does see such routes.
- **FastAPI's `/docs`, `/redoc`, `/openapi.json` (and `/docs/oauth2-redirect`) are switched off.** They were served without a token, and the row says every route except `GET /health` requires one. Protecting them instead would mean replacing FastAPI's built-in routes with our own; the service is internal (only the backend calls it) and its contract is its pydantic models and tests, so they are off. Turning them back on behind the token is a small change if the human wants them.
- **The comparison:** `hmac.compare_digest` on the UTF-8 bytes of the sent and the configured token. On `str` it raises `TypeError` for non-ASCII characters, which would make such a header a 500; as bytes it is a 401 (tested by sending raw UTF-8). It runs whatever the scheme, so a wrong scheme takes the same path. Only the token's length can still show in the timing, which `compare_digest` does not hide; with a long random token that tells nothing useful.
- **One refusal for everything:** a missing header, an empty one, another scheme, a token without a scheme, extra spaces, a near miss and a wrong token all get the same 401 body `{"detail": "Not authenticated"}` and `WWW-Authenticate: Bearer` (RFC 6750), and the body never holds what was sent. The scheme is matched ignoring case (RFC 7235: scheme names are case-insensitive); the token exactly. `{"detail": ...}` is FastAPI's own error shape: the backend's `{status, code, message}` is its public contract, and this service's only caller is the backend's own client (Phase 7), which will map any non-2xx to its own error.
- **Nothing is logged** by the check, so the token cannot be.
- **The token is read through `get_settings()` on each request** (cached since 6.1b), so a test's `monkeypatch` of `AI_SERVICE_TOKEN` is seen once the cache is cleared, as the conftest does.
- **There is no protected endpoint yet,** so the tests build a probe app with one endpoint on a router from `protected_router()`: the same function, check and settings the real endpoints will use.
- **Tests (+26, ai-service 18 -> 44; backend 2226 and frontend 3 unchanged and passing):**
  - the right token reaches the endpoint, with the scheme in any case;
  - 15 wrong headers are each a 401 with the fixed body and `WWW-Authenticate`: none, empty, scheme only, scheme and space, wrong token, Basic, another scheme, token without scheme, two spaces, trailing space, one character more at either end, upper case, half the token, non-ASCII;
  - every refusal is byte-identical and shows no token;
  - `compare_digest` is what compares (spied, with the exact bytes), and the configured token is the one checked;
  - `/health` answers 200 without a header, with a wrong one and with a malformed one;
  - every route of the app but `/health` is checked, the documentation routes are 404, and the guard sees an unchecked route (positive control).
- **Mutation-checked, each failing at least one test:** the router without the check (17 failures); the scheme not checked (3); `==` instead of `compare_digest` (1); the documentation routes served again (2); `str` instead of bytes (2: the non-ASCII header becomes a 500).
- Also checked by hand on a real uvicorn: `/health` 200 without a token, `/docs` and `/openapi.json` 404, the token not in the log.

## 6.2a — LLM provider interface + Gemini over httpx

- **Gate resolved by the human:** `GEMINI_API_KEY` and `GEMINI_MODEL` were already in `ai-service/.env` (checked only for being non-empty; the key was never read or printed). Two more questions were put and answered:
  - **`httpx` moved from the `dev` group to the runtime dependencies** (a gate: it was not installed in production). Same version as before (0.28.1, already locked for the test client), so nothing new is downloaded. The alternative offered was the standard library's `urllib`.
  - **Real Gemini calls were allowed** ("a few calls"). Three were made: the live test (HTTP 404, see below), one listing of the models the key may use (only names printed), and the live test again (passed, 4 characters of text).
- **The model in `.env` did not exist.** `gemini-3-flash` answered 404; the key's model list has `gemini-3-flash-preview` and `gemini-3.5-flash`, not that name. The human chose `gemini-3.5-flash` (a fixed, non-preview version, so the thesis's experiments are not moved by a model change), and only the `GEMINI_MODEL` line of their `.env` was changed. Nothing in the repository names a model.
- **The API's shape was taken from Google's documentation at the time of writing,** not from memory: `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, body `contents[].parts[].text`, text at `candidates[].content.parts[].text`, `promptFeedback.blockReason` when the prompt is blocked (then no candidates). The documentation's own examples put the key in the URL (`?key=`); its API-key page shows the **`x-goog-api-key` header**, which is what this uses, so the key never appears in a URL (proxies and access logs record URLs).
- **The interface is an `ABC` with one method, `generate(prompt) -> str`,** the row's "prompt in, text out". Synchronous: the endpoint (6.5a) will be a plain `def`, which FastAPI runs on a worker thread, so a blocking call does not stall the event loop; and the service makes one call per request.
- **Errors are typed, and the type says what 6.3c can do about it:** `LlmUnavailable` (no answer: timeout, connection failure, any non-2xx status), `LlmBadResponse` (an answer without usable text: not JSON, blocked, no candidate, empty or blank text), `LlmNotConfigured` (key or model missing, or a model name that is not a plain name). Their messages are fixed text. **None ever holds the key, the prompt (it will hold student code) or Gemini's answer** (an error body can echo the request). The original `httpx` error is chained for the log: its text holds at most the URL, and the key is in a header, which a traceback never prints.
- **No retry here.** 6.3c's row is "retry once, then a clean error"; this row only reports.
- **The model name must be a plain name** (letters, digits, `.`, `_`, `-`, starting with a letter or digit), because it goes into the URL's path: `models/x`, `x?key=1`, `../x`, `x:generateContent` and the like are refused at configuration rather than producing a strange URL. The model is not given a default anywhere, and `test_no_model_name_is_written_in_the_code` greps `src/` for Gemini model names.
- **Timeouts are named placeholders,** connect 5 s and read 30 s (write and pool get 30 s too, so no phase is unbounded). **Phase 7's backend client must allow for them**: its read timeout on the call to this service has to exceed this read timeout, or the backend gives up while Gemini is still answering.
- **Only the first candidate is used,** its text parts joined (one prompt asks for one answer; Gemini returns one candidate unless asked for more). Non-text parts are skipped.
- **The provider is not wired into any endpoint:** 6.2b proves it with one hardcoded prompt, and 6.5a wires `POST /feedback`.
- **Tests (+46 and 1 opt-in, ai-service 44 -> 90; backend 2226 and frontend 3 unchanged and passing):**
  - the request: one `POST` to the exact URL, the exact JSON body, the key only in the header and nowhere in the URL, the prompt byte for byte (quotes, backslashes, tabs, non-ASCII, emoji), the timeouts bounded and equal to the constants;
  - the answer: the text, the first candidate's parts joined and other candidates ignored, the class an `LlmProvider`;
  - no usable answer: seven HTTP statuses each `LlmUnavailable` with only the status in the message; four transport failures (connect and read timeouts, connection refused, protocol error); twelve shapes without usable text and a non-JSON answer each `LlmBadResponse`; no message ever holds the key or the prompt;
  - configuration: key or model missing, eight bad model names, an empty key, the configured key and model used, the key not in the provider's `repr`, no model name in the source;
  - `test_the_real_gemini_api_answers_a_prompt`, skipped unless `RUN_LIVE_GEMINI=1`; it prints only the length of the answer.
- **Mutation-checked, each failing at least one test:** the key in the URL (4 failures); no HTTP status check (7); the last candidate instead of the first (1); any model name accepted (8); the answer's text in the error message (7); no read timeout (1, after tightening the timeout test: it first compared the client with the constant, so a constant of `None` passed).

## 6.3a — Pydantic models for `POST /feedback`

- **camelCase on the wire (gate, the human's choice):** `assignmentDescription`, `publicTests`, `hintLevel`. Every other JSON in the platform is camelCase, so the backend's DTO (7.1a) needs no naming annotation. Python keeps snake_case attributes through pydantic's `to_camel` alias generator. **Only the camelCase names are accepted** (`validate_by_alias=True`, `validate_by_name=False`): accepting both would make two spellings of one contract, and with unknown fields forbidden a snake_case key is refused like any other.
- **Hidden tests are hidden by the shape, as the row asks:** `HiddenTestResult` has exactly one field, `passed`. No name either (not even the masked `Hidden test N` of 5.5a): the model needs only how many passed and failed, and a free-text name field is a field a hidden test's real name could be put into. Their order is the run order the backend sends.
- **Every model forbids undeclared fields** (`extra="forbid"`). The point is the hidden tests: a backend that sends `{"passed": false, "input": ...}` gets a 422 instead of the input quietly being ignored today and used by a later prompt change. It also catches a backend DTO that drifts from this one (a misspelt or extra field fails loudly).
- **What a public test carries:** name, input, expected output, status, actual output, stderr ("public test results with detail"). Not its weight, position or runtime: none helps a hint, and the rubric is not shown to students (3.4a). `actualOutput` and `stderr` are optional, because a compile error has no actual output (5.3b).
- **`compilerOutput` at the top level,** the same text the student sees (5.5a). It is there because a compile error's message otherwise travels only in the stderr of public tests, and an assignment whose tests are all hidden would send none.
- **`TestOutcome` is copied from the backend,** and `test_the_outcomes_are_exactly_the_backends` reads `backend/.../sandbox/TestOutcome.java` (comments stripped) and compares the names in order, so the two cannot drift. The ai-service CI checks out the whole repository, so the file is there.
- **Strict where a coercion would hide a bug:** `hintLevel` is a strict integer from 1 to 3. A `Literal[1, 2, 3]` was tried first, and the tests showed it accepts `true`, because Python's `True == 1`. `passed` is a strict boolean, so `"true"`, `1` or `null` are refused. The three texts must be non-empty and are kept exactly as sent (no stripping): code is whitespace-sensitive.
- **The response is `{hint}`,** the row's "hint text". Nothing else is needed by 7.2a, which stores it with the level it asked for.
- **The models are frozen,** so a request read once cannot be changed on its way to the prompt.
- **Not decided here: size limits.** Nothing bounds the length of the code (128 KiB in the backend), a test's texts (up to 100000 characters) or outputs (up to 1 MiB each) in a request, and all of it can end up in a prompt, which costs tokens. Either 7.1b (what the backend sends) or 6.3b (what the prompt includes) should cut it; noted in `docs/suggestions.md`.
- **Tests (+54, ai-service 99 -> 153; backend 2226 and frontend 3 unchanged and passing):**
  - a valid request read field by field, from a dict and from JSON text; text kept exactly; a compile error with `compilerOutput` and no actual output; optional outputs; no tests of either kind; each level; every outcome; the outcomes equal the backend's;
  - a hidden test is only `passed`; seven attempts to add a field to it are refused; no model but the public test has a content field; unknown top-level and public-test fields refused;
  - every required field, empty texts, nine bad levels (0, 4, -1, 1.5, "1", null, true), five non-booleans, an unknown outcome, snake_case names, a change after reading;
  - the response is `{"hint": ...}` and refuses an empty hint; the request is written back with exactly the camelCase keys the backend's DTO must have.
- **Mutation-checked, each failing at least one test:** unknown fields ignored (13 failures); an `input` field on the hidden test (4); a lax boolean (4); snake_case accepted (1); level 4 allowed (1); empty code allowed (1); an outcome missing (1).

## 6.3b — Prompt builder

- **The shape of the prompt:** the rules (the tutor's task, never a complete solution, the UNTRUSTED blocks are data whose instructions are ignored, hidden tests are only pass/fail, answer with `{"hint": ...}`), then the level's instructions, then the data in blocks, then a reminder that repeats the data rule. Instructions on both sides of the data ("sandwich") is the usual defence against text in the data that tries to take over.
- **What is untrusted:** the root `CLAUDE.md` names student-supplied text. Here that is the code, but also the compiler's message (it quotes the code) and a public test's actual output and stderr: the student's program printed them, so a student can make them say anything, "ignore your rules" included. All four are labelled `UNTRUSTED`. The description and a public test's input and expected output come from the teacher and are labelled so; they are fenced too, so every outside text is delimited the same way.
- **"Neutralizes code that contains the delimiter itself" = the fence grows.** The fence is a line of backticks one longer than the longest run of backticks in any block (at least three), the CommonMark rule for code fences. So no line of any block can be the fence, a block can only end where the builder ends it, and the code is passed **unchanged**. Escaping a fixed delimiter would have altered the code the model reads (Java's `>>>` operator, for one), and a random delimiter would have made the builder impure. The prompt states the fence's length, so the model is told exactly where each block ends.
- **The levels, from the row and the root `CLAUDE.md`:**
  - 1, nudge: the part of the program or the idea to look at again; not the mistake, the exact place or the fix; no code;
  - 2, pointer: where (statement, condition, loop, function) and what kind of mistake; not the fix; no code;
  - 3, partial explanation: what is wrong, why, and the reasoning the fix needs, step by step; at most one illustrative snippet of `MAX_SNIPPET_LINES` lines on a **different, small example**, never the corrected program or a piece to paste in.
- **`MAX_SNIPPET_LINES` = 5, a placeholder** for the human, defined here because the prompt states it; 6.4a's guard enforces the same constant.
- **The answer is asked for as `{"hint": "..."}`.** The spec says the service "validates the structured response"; that is 6.3c. Until then `generate_feedback` returns the model's text as it comes.
- **Hidden tests are only counted** (`k of n passed`), with "their inputs and expected outputs are not available" and "do not guess what they contain". The contract (6.3a) carries nothing more, so there is nothing else to leave out.
- **Missing outputs are left out, not shown empty:** a compile error has no actual output, and an empty stderr adds nothing. The compiler message appears only when there is one.
- **`feedback.py` builds the prompt from the request now,** as 6.2b planned: `HARDCODED_PROMPT` is gone, `generate_feedback(provider, request)` takes the request, and the command uses a made-up `SAMPLE_REQUEST` (the product printed instead of the sum) at the level given as its argument (`1` by default).
- **No size budget yet** (6.3a's note in `docs/suggestions.md`): every text goes into the prompt whole.
- **Live check not done:** two calls with the sample request (levels 1 and 3) both got HTTP 503 from Gemini (overloaded on Google's side, as at 6.2b). They were not repeated: the builder is a pure function and fully tested without a model, and a live answer would not test it anyway. 6.3c's retry is for these 503s. A diagnostic call made afterwards at the human's question (outside the service, printing Gemini's error body) got HTTP 200 from the same model with the same key: the 503s were Google's temporary overload, not this code. The service's own error drops Gemini's error body (it could echo the request), which is why the reason was not visible; adding Gemini's fixed status word (`UNAVAILABLE`, `RESOURCE_EXHAUSTED`) to the message was proposed for 6.3c. The same call showed `gemini-2.5-flash` is "no longer available to new users" (Google suggests `gemini-3.8-flash`); the configured `gemini-3.5-flash` is unaffected.
- **Tests (ai-service 153 -> 194; backend 2226 and frontend 3 unchanged and passing):**
  - `test_prompts.py`: the same request gives the same prompt and is not changed; each level holds its own instructions and no other's; the three levels ask for different things, and their key phrases (level 1: no mistake, place or fix and no code; level 2: where and what kind, no fix, no code; level 3: the fault, the reasoning, the snippet cap, never the corrected program); every level forbids the complete solution; the JSON answer; the code is one untrusted block, unchanged (spaces, tabs, a backtick, trailing blank lines); the ignore-instructions rule comes before the code and the reminder after it and last; the level's instructions come before any data; code holding three and six backticks and an "ignore all previous instructions" line gets a seven-backtick fence and stays whole in its block; the fence outgrows backticks in any block (an actual output of 20 gives 21); three without backticks; the code, compiler message, actual output and stderr are untrusted and the teacher's texts are not, and no injected text appears outside a block; the description and language; a public test in full; missing outputs left out; the compiler message only with a compile error; public tests numbered in order; none said plainly; hidden tests counted (four cases) with their details said to be unavailable;
  - `test_feedback.py`: updated to the request (each level's prompt is sent once, the command takes the level, refuses other arguments).
- **Mutation-checked, each failing at least one test:** a fixed three-backtick fence (3 failures); the code marked as the teacher's (3); no reminder (1); level 3's instructions for every level (3); the actual output marked trusted (1); every hidden test counted as passed (2); the fence sized from the code only (1).

## 6.3c — Validate the answer, retry once, clean error

- **Three questions put to the human before writing it, all answered:**
  - **Retry Gemini being briefly unavailable too:** yes, beyond the row's "malformed or empty". One retry also when Gemini answers HTTP 429 or 500/502/503/504 (the 503s seen at 6.2b and 6.3b came back within a second). **A timeout is never retried:** a second 30 s wait (6.2a's read timeout) would outlast the backend's timeout on its call here. A connection failure is not retried either (it has no status), nor any other status (400/401/403/404 will not change on a second try), nor a missing configuration. At most `MAX_ATTEMPTS` = 2 calls per hint in every case.
  - **Gemini's status word in the error message:** yes. `LlmUnavailable` now reads `error.status` from Gemini's error body and appends it, as in `Gemini answered HTTP 503 (UNAVAILABLE)`, **only if it is one uppercase word of at most 40 characters** (`[A-Z][A-Z_]{0,39}`). Nothing else of the body is read into a message (its `message` can echo the request). This is what was missing to see why the 503s happened.
  - **Level 3 must not name the exact edit:** yes. The live level-3 hint said "change the operator from multiplication to addition (`+`)", the whole fix in words. Level 3 now says "Stop short of the exact change: do not name the operator, value, condition or line the student should write instead; the last step is theirs." Checked with one live call: the hint explained the fault and pointed at "the mathematical symbol", without naming the change. Prose like this is not something 6.4a's code-size guard can catch, so the instruction is the only control.
- **What a valid answer is:** exactly `{"hint": "<text>"}` (6.3b's prompt asks for it), read with `FeedbackResponse`, so another key, a missing key or a non-string hint is refused; a blank hint too. The whole answer may be wrapped in one Markdown code fence (` ```json ... ``` `), which models do with JSON; text around the JSON is refused, not searched, because guessing where the JSON is would also accept a hint followed by a solution. The hint is returned stripped of surrounding whitespace; its inside, a code snippet included, is kept.
- **The retry sends the same prompt:** the prompt builder is pure, so a second try is the same question; nothing is added to it.
- **"A clean error" = the last attempt's `LlmError`,** whose message is fixed text (never the key, the prompt or the answer). 6.5a turns it into the endpoint's error response.
- **`LlmUnavailable.status_code`** (the HTTP status, `None` when there was no answer) is what the retry rule reads. A `timed_out` flag was written first and removed: a timeout already has no status code, so the flag could not change any decision, and a mutation of it went unnoticed by the tests.
- **The command** prints the hint text now, not the raw JSON.

## 6.4a — Solution-leak guard

- **What counts as code in a hint:** every non-blank line of a fenced block (```` ``` ```` or `~~~`; a fence closes only on a fence of the same character at least as long, as in CommonMark; an unclosed fence runs to the end of the hint, so leaving it open does not hide code), a line of prose that reads as a statement (ends in `;`, `{` or `}`; starts with a lowercase keyword and has code punctuation; is an assignment; is a whole-line call) and an inline code span that reads as a statement. A span such as `` `*` `` or `` `a * b` `` is not a statement, so a hint may name an operator or an expression. Prose lines start with a capital or a list marker, which none of the patterns match.
- **A line copied unchanged from the student's code is not counted** (whitespace ignored): a level-2 pointer may quote the line it points at, in a span or a fence, and that tells the student nothing they did not write. Only new code counts against the allowance.
- **The allowance is `MAX_CODE_LINES = {1: 0, 2: 0, 3: MAX_SNIPPET_LINES}`**, so the row's "none at levels 1-2, a short snippet at level 3" is one named table, and level 3 uses the prompt's own constant (6.3b), so what the prompt allows and what the guard accepts cannot drift.
- **"Looks like a complete solution", at any level, is two checks:**
  - **`COMPLETE_PROGRAM`:** new code that both reads the input and prints, or declares an entry point (`static void main`, `__name__`, `int main`). Every assignment is stdin to stdout, so that is a whole program, whatever its size (a three-line program fits in level 3's five lines). One list of markers for every language, no branch per language (the root `CLAUDE.md`); a new language may add words to it. A snippet that only prints or only reads is not a program.
  - **`EDITED_STUDENT_LINE`:** a new line at least `LINE_SIMILARITY` (difflib's ratio, whitespace ignored; 0.8, a placeholder) like one of the student's lines, i.e. their line with a change in it. That is the fix, alone or inside the corrected program. **This goes past "a complete solution" on purpose:** a share-of-the-program rule was written first (refuse code that reproduces half the student's lines with one edited) and a probe showed it let through `System.out.println(a + b);` against a ten-line Java program, which is the whole fix and exactly what the human decided at 6.3c that level 3 must stop short of. The edited-line rule catches both, needs one constant instead of two, and the same idea on other names (`print(x + y)` against `print(a * b)`, ratio 0.7) stays apart.
- **Regeneration uses the same two attempts as 6.3c** (`MAX_ATTEMPTS`): a leak is retried like a bad answer, with the same prompt. **The last attempt decides:** leak then leak, or a failure then a leak, returns `SAFE_HINT` (the row: never the leak); a leak then a failure raises the failure, so the backend's request fails cleanly instead of spending the student's level on a generic text. A third call was not added: every call costs the student's wait, and the backend's timeout bounds the whole.
- **`SAFE_HINT` is one fixed text for every level** (trace a failing public test by hand and find the first step where your values and the expected output part ways): it says nothing about the program, so it cannot leak at any level, and the guard itself accepts it (tested).
- **What it cannot catch,** recorded so the thesis does not overclaim: the fix said in words ("use plus instead of times"; 6.3c's prompt sentence is the only control), several statements packed on one line, a short edit (`x=1` against `x=2`, ratio 0.67), a reordering of the student's own lines, and a solution function that neither reads nor prints and fits the allowance.
- **Not changed:** the response is still `{hint}`; the backend cannot tell `SAFE_HINT` from a real hint, so it would store it as a used level (noted in `docs/suggestions.md` for 7.2a).
- **Tests (+100, ai-service 248 -> 348; backend 2226 and frontend 3 unchanged and passing):**
  - `test_leak_guard.py` (85): seven kinds of prose pass at every level (`SAFE_HINT` included); quoting the student's code unchanged (span, fence, spaced differently, the whole program) passes at every level; the allowance table; eleven kinds of new code refused at levels 1 and 2 (fenced, tilde fence, spans, prose assignment, loop header, brace, statement, call, unclosed fence); the allowance at level 3 exactly (five lines pass, six do not); an illustrative snippet on another example passes; lines counted across fences, spans and prose; blank fenced lines not counted; a shorter fence does not close a longer one; five complete programs refused within the allowance; printing alone or reading alone is not a program; the student's own reading and printing lines quoted are not new; five edited lines (Python and a ten-line Java program, fenced and in spans) refused at every level; the same idea on other names is not an edit; the check is pure;
  - `test_feedback.py` (+15): a leak is regenerated with the same prompt at every level; when the last attempt leaks (after a leak, a bad answer or a 503) `SAFE_HINT` is returned at every level; a leak then a failure raises the failure; an allowed snippet is returned as it is.

## 6.4b — Flag the fallback hint

- **New row, the human's decision after PR #129** (option A of the 6.4a suggestion, over returning an error, which would have contradicted 6.4a's row, and over leaving it): `POST /feedback` answers `{"hint": ..., "fallback": true|false}`. The rows 6.4b and 6.4c (the retry sentence, also approved) were added before 6.5a, so the endpoint is built on the final contract and the backend's DTO (7.1a) mirrors it from the start.
- **`fallback` is required and strict:** the response always says which kind it is, so the backend never has to guess from a missing field, and `1`, `"true"` or `null` are refused, like `passed` in 6.3a.
- **True only when the last attempt leaked and `SAFE_HINT` is returned.** A model that answers with `SAFE_HINT`'s own words has given a real hint that passed the guard, so that is `fallback: false` (tested): the flag says what happened, not what the text says.
- **The model cannot set the flag.** `parse_hint` reads the model's answer with its own `_ModelAnswer` (`{hint}` only, unknown keys refused) instead of `FeedbackResponse`, so an answer holding `fallback` (true or false) is a bad answer and is retried. Reusing `FeedbackResponse` would have let the model declare its own hint a fallback, or need the field to be optional.
- **`generate_feedback` returns the `FeedbackResponse`,** which 6.5a will send as it is. The command prints the hint and, for a fallback, one line on stderr saying so (exit 0: it is an answer, not a failure).
- **What the backend does with it is left to 7.2a,** noted on its row: show it without storing it, or store it without counting the level.
- **Tests (+11, ai-service 348 -> 359; backend 2226 and frontend 3 unchanged and passing):** the response with each flag value, key for key and as JSON; the flag strict (five values refused) and required; an empty hint still refused; the model cannot set the flag (true or false, in `parse_hint` and through two attempts); the safe hint's text from the model is not a fallback; every earlier result now compared as a whole `FeedbackResponse` (real hints `false`, the safe hint `true`); the command's stderr line.

## 6.4c — The retry after a leak says why

- **New row, the human's decision after PR #129.** After a leak, the second call's prompt carries `AFTER_LEAK`, a fixed sentence: the previous answer was rejected because it held code the level does not allow, naming the guard's three kinds (more code than the level permits, a program that reads the input and prints the answer, a line of the student's code with a change in it), and asking to follow the level's rules on code exactly.

## 6.5a — `POST /feedback` wired end to end

- **The endpoint is thin:** `api.py` puts `generate_feedback` (request → prompt → LLM → validate → guard, with the retries of 6.3c and the regeneration of 6.4a/6.4c) behind HTTP and returns its `FeedbackResponse` as it is, `{hint, fallback}`. It is on `router = protected_router()`, included in `main.py`; FastAPI resolves the router's token check before the endpoint's own dependencies, so a request without the token is a 401 before the body is read or a provider is built (tested with an invalid body and a counting provider).
- **A plain `def`,** as planned at 6.2a: FastAPI runs it on a worker thread, so the blocking Gemini call (up to two attempts) does not stall other requests.
- **The provider is a dependency, built per request and closed after it** (`get_provider`, a generator). Building it costs nothing worth sharing next to a Gemini call, a per-request client cannot carry state between requests, and tests swap it through `app.dependency_overrides`. A shared client in the app's lifespan was the alternative; it would also have made a missing Gemini setting stop the service at startup, while 6.1b decided only the token does.
- **Error statuses (`ERROR_STATUS`):** `LlmUnavailable` (Gemini down, overloaded, timed out, refused) and `LlmNotConfigured` → 503 Service Unavailable; `LlmBadResponse` (Gemini answered, twice, with nothing usable) → 502 Bad Gateway. The body is FastAPI's `{"detail": ...}` with the error's own message, fixed text by construction (6.2a): no key, prompt, code or model answer. The backend's client (7.1a) maps any non-2xx to its own "hint unavailable" error (6.1c), so the split serves its logs, not the student. No separate 504 for a timeout: the backend does not need to tell them apart, and the message says it was a timeout.
- **A 422 never echoes the body.** FastAPI's default 422 puts each wrong value in `input`, so a request with a hidden test carrying `input`, or a bad field next to the code, would have sent that content back, and into the backend's log if it logs error bodies. The `RequestValidationError` handler in `main.py` keeps `loc`, `msg` and `type` only, which still says which field is wrong (tested: `["body", "hiddenTests", 0, "input"]`, `extra_forbidden`). It is app-wide, so a later endpoint gets it too. A body that is not JSON is a 422 the same way.
- **Found and fixed: the 6.1c route guard did not look inside included routers.** FastAPI 0.142 keeps an included router as one `_IncludedRouter` entry in `app.routes` instead of copying its routes there. The guard treated that entry as an unchecked plain route, so it failed as soon as the first real router was included (that is how it was found), and its positive control had passed for the wrong reason: the "covered" route was absent from the report only because the report named the router entry, not the route. The guard now walks each entry's `effective_candidates()` (full path with the include's prefix, the include's dependencies applied, nested includes recursed), read through `getattr` so a plain list of routes still works. The control now also includes a plain router with a prefix (reported as `POST /v1/forgotten`), a protected router nested in another router and a plain router included with the check (neither reported), and requires every reported entry to be a path.
- **Live check over real HTTP** (an in-process uvicorn on 127.0.0.1, the developer's `ai-service/.env`, the token never printed, the made-up `SAMPLE_REQUEST`): `GET /health` 200; `POST /feedback` without a token 401; level 2 → 200, a pointer at the operator in the `print` statement, `fallback: false`; level 3 → 200, the fault explained and the change left to the student ("determine which operation calculates a sum"), `fallback: false`.
- **Not done here:** a bound on the request size (the 6.3a note in `docs/suggestions.md` still stands); logging (none exists; when it is added, the token and the code must never reach it).
- **Tests (+24, ai-service 370 -> 394; backend 2226 and frontend 3 unchanged and passing):** `test_api.py` (24): a hint at each level, exactly `{hint, fallback}`, with the request's prompt sent and the provider closed; two leaks give the safe hint with `fallback: true`; the whole loop against a faked Gemini (only the network faked: real dependency, settings, provider, URL, key header, prompt, parsing, guard); three kinds of missing token are 401 for a valid and an invalid body, with no provider built; five invalid bodies are 422 with only `loc`/`msg`/`type` and none of the sent text; the exact refusal for a hidden test with `input`; a non-JSON body; six provider failures map to 503/502 with the fixed message, none holding the code, the provider closed; the status table; no Gemini settings → 503 with the configuration message; the real provider's client is closed after the request. `test_auth.py`: the guard's positive control extended (no new test, more assertions), the probe's docstring updated.
