# backend/CLAUDE.md

Spring Boot 4.1.1, Java 17, Maven. Project-wide rules (gates, defaults, Git safety, PR flow) are in the root `CLAUDE.md`; this file only holds what is specific to `/backend`.

## Commands (run from `/backend`)
- Build + test: `./mvnw -B verify` (`mvnw.cmd -B verify` on Windows). This is also what CI runs (`.github/workflows/backend-ci.yml`).
- Tests only: `./mvnw -B test`
- Run: `./mvnw spring-boot:run` — real OS environment variables are read directly (no dotenv library), so load `backend/.env` into the shell or the IDE run configuration first. See the root README, "Environment variables".
- Format: `./mvnw spotless:apply` (palantir-java-format, 4-space). `spotless:check` is bound to the `verify` phase, so `./mvnw -B verify` (and CI) fails on unformatted code — run `spotless:apply` before committing.
- Use the Maven wrapper, never a system Maven — it pins the version.
- Spring profiles: `dev` for local development, `prod` for deployment (root README). Both live in `src/main/resources/application.yml` (the only config file) as profile-specific YAML documents; select one with `SPRING_PROFILES_ACTIVE`. No profile is active by default, and tests run without one. `dev` falls back to the compose database URL and username (the password has no fallback), `prod` has no datasource fallback and fails fast.

## Layout
- Base package: `com.gradingplatform.backend`. Tests mirror it under `src/test/java`.
- On the classpath: Web, Security, Validation, Data JPA, Flyway (`spring-boot-starter-flyway` plus `flyway-database-postgresql` — in Spring Boot 4 bare `flyway-core` does not autoconfigure), the PostgreSQL driver and jjwt 0.13.0 (`jjwt-api`/`-impl`/`-jackson`, version pinned in `pom.xml`, not managed by Spring Boot; chosen by the human at 2.4a). jjwt only signs and checks our own tokens: **no OAuth or social login (Google, GitHub, ...)**; adding any OAuth dependency needs an explicit task, and `NoSocialLoginTests` fails if one appears.
- Migrations live in `src/main/resources/db/migration` (plain SQL, Flyway, run on startup; files named `V<n>__<snake_case_description>.sql`, one per task row). Hibernate runs with `ddl-auto=validate`, so it never changes the schema. Dev-only seed data lives in `src/main/resources/db/dev-seed` (versions from `V1000`, so they sort after every schema migration), a separate Flyway location that `application.yml` puts on the path only under the `dev` profile (`prod` and the no-profile tests use `db/migration` alone; the `DevSeed*Tests` add the location explicitly via `spring.flyway.locations`). `dev` also sets `spring.flyway.out-of-order: true`, so a schema migration added after the seed (V1000+) still applies to an existing dev database. Dev logins and passwords are documented in the header of `V1000__seed_users.sql`; the seeded course and assignments are in `V1001`, the seeded submissions, results, grades and criterion scores in `V1002`.
- `GET /health` (2.2b) is public and returns `{"status":"UP"}` (200) when a database connection is obtained and valid within 3 s, otherwise `{"status":"DOWN"}` (503); it exposes nothing else. `POST /auth/signup` (2.3b, 2.3c) creates a `STUDENT` (a `role` in the body is ignored) with a BCrypt hash from the single `PasswordEncoder` bean. Emails are trimmed and lower-cased (`AuthService.normalizeEmail`, to be reused by signin in 2.4a); a duplicate is a 409 (`EmailAlreadyUsedException`, found through the unique constraint, not a pre-check); the password must be 8 characters to 72 bytes (`dto/PasswordPolicy`); DTOs that carry a password override `toString` so logs never show it. No Spring Boot Actuator: it would be a new dependency.
- Entities (first one: `entity/User`, 2.3a) map a table with explicit `@Column(name = ...)` for every field, so a renamed Java field cannot silently change a column; `ddl-auto: validate` makes startup fail on any mismatch with the Flyway schema. Enums are stored with `EnumType.STRING`. Columns filled by a database default (such as `created_at`) are `insertable = false, updatable = false` with `@Generated(event = EventType.INSERT)` so Hibernate reads the value back after the insert.
- `POST /auth/signin` (2.4a) returns `{token, tokenType: "Bearer", expiresIn, user}` **in the JSON body only, never a cookie** (the human's decision); the client sends `Authorization: Bearer <token>`. `security/JwtService` signs HS256 tokens (claims: `sub` = user id, `email`, `role`, `iat`, `exp`) valid for `jwt.expiration` (24h). `JWT_SECRET` (bound to `jwt.secret`) is required in every profile: it has no default, must be at least 32 characters, and the app refuses to start without it. For `./mvnw spring-boot:run` put it in `backend/.env`; tests get a throwaway one from the surefire `environmentVariables` in `pom.xml`, so an IDE run of the tests needs `JWT_SECRET` set too. A wrong password and an unknown email both give the same 401 (and cost one BCrypt comparison each).
- `GET /auth/me` (2.4c) returns the signed-in user as `UserResponse`, read from the database by the token's subject (not from the claims, so a changed role shows at once); a token whose user was deleted is a 401 (`ACCOUNT_NO_LONGER_EXISTS`). Controllers get the caller with `@AuthenticationPrincipal AuthenticatedUser`.
- Security chain (2.4b, `security/SecurityConfig`): stateless (no session, no cookie), CSRF off (the token only ever travels in the `Authorization` header), form login, HTTP Basic, logout and request cache off. Public: `GET /health`, `POST /auth/signup`, `POST /auth/signin` and `/error` (must stay: errors are forwarded to it); everything else needs a valid token. `JwtAuthenticationFilter` (not a `@Component`, added by the chain) asks `JwtService.parse` and, if the token verifies, authenticates with an `AuthenticatedUser` principal (id, email, role from the claims alone, no database lookup) and the authority `ROLE_<role>`; a missing or bad token just leaves the request anonymous, so a protected path answers **401** in the standard error body (no redirect, no `WWW-Authenticate`) and public paths ignore a bad token. A wrong role is 403 (see the role convention below). Add new rules to the `authorizeHttpRequests` block. A `@WebMvcTest` that imports `SecurityConfig` needs a `@MockitoBean JwtService`.
- Role convention (2.5a): `@EnableMethodSecurity` is on `SecurityConfig`, and the role rule of an endpoint is a `@PreAuthorize` on its **controller method** (never on the class, never as a URL matcher by role), e.g. `@PreAuthorize("hasRole('ADMIN')")` or `@PreAuthorize("hasAnyRole('TEACHER', 'ADMIN')")`. Roles are listed explicitly: there is no role hierarchy, so `ADMIN` does not imply `TEACHER` (write `hasAnyRole('TEACHER', 'ADMIN')` where the row says "teacher or admin"). No annotation means any signed-in user. Anonymous is 401, signed in with the wrong role is 403 (standard error body, no challenge). The role comes from the token, so a promotion applies after the next signin (2.4b). Role checks alone do not protect course data; ownership checks come in 3.1c. `PreAuthorizeConventionTests` fails on a role name that is not a `Role` (a typo such as `hasRole('TEACHR')` would silently lock everyone out) or a class-level rule; `RealHttpRoleSecurityTests` has the pattern for testing a role rule over real HTTP (a probe controller nested in the test class).
- `PATCH /admin/users/{id}/role` (2.5b, `AdminUserController` + `UserAdminService`): admin only (`@PreAuthorize`), body `{"role": "STUDENT|TEACHER|ADMIN"}` (exact enum spelling; missing or unknown is 400), answers the `UserResponse`. It is the only way a `TEACHER` or `ADMIN` comes to exist. Unknown id 404; setting the role a user already has is a 200 no-op; the last remaining admin cannot be demoted (409 `LastAdminException`), but an admin may demote themselves while another exists. `UserAdminService.changeRole` first locks every admin row (`UserRepository.lockAllByRole`, `FOR UPDATE`, inside the transaction) so two simultaneous demotions cannot leave zero admins. The change reaches the user's token only at their next signin (the role is a claim, 2.4b), which also means a **demoted admin keeps admin rights until their token expires (24h)**; `/auth/me` shows the new role at once.
- Pagination convention (2.5c, chosen by the human; first user `GET /admin/users`, admin only, rows `{id, email, role}`): every paginated list returns `dto/PageResponse<T>` = `{items, page, size, totalElements, totalPages}`, takes `?page=0&size=20` (page 0-based; `size` default 20 = `PageResponse.DEFAULT_SIZE`, clamped to `MAX_SIZE` 100 and the response reports the size used; negative page or size below 1 is 400; an empty `page=` means the default; a page past the end is 200 with empty `items`; an offset above `Integer.MAX_VALUE` is 400 because JPA's offset is an `int`). Build the request with `PageResponse.pageable(page, size, sort)` and map with `PageResponse.of(page, toDto)`; give every list a fixed, stable `Sort` (by id for users) so pages do not overlap. Declare the parameters as `@RequestParam(required = false) @Min(0) Integer page` / `@Min(1) Integer size`.
- Error contract (2.6a, shape chosen by the human): every error, whoever produces it, is `dto/ErrorResponse` = `{status, code, message}` plus `fieldErrors: [{field, message}]` on a 400 `VALIDATION_FAILED` only (omitted otherwise; the rejected value is never echoed), content type `application/json`. The frontend branches on `code`, a `dto/ErrorCode` constant (it also fixes the status and a fixed message; renaming one is an API change). To add an error for a rule: add an `ErrorCode`, then a small class extending `dto/ApiException` that passes it to `super(...)` and throw it; no `@ResponseStatus` and no message text from user input. `controller/GlobalExceptionHandler` (extends `ResponseEntityExceptionHandler`, so Spring's own 400/404/405/415... use the shape too, with a fixed message per status) handles `ApiException`, method-security refusals (anonymous 401 / signed-in 403) and anything else as a generic 500 whose cause goes to the log only. Errors answered before MVC use the same body: the security chain's 401/403 (`security/JsonAuthenticationEntryPoint`, `JsonAccessDeniedHandler`) and the servlet container's (`controller/ApiErrorController` replaces Boot's `/error`). A test that expects an error should assert `status` and `code`, not the message.
- Role matrix (2.7d, `RoleMatrixIntegrationTests`): **every new endpoint gets a row in its `ENDPOINTS` list** (method, Spring path pattern, a sample path, a body that is valid for it, and who may call it: public, any signed-in user, or these roles). The test calls each endpoint as nobody, with a bad token, as a student, a teacher and an admin and expects 401 / 401 / 403 / pass, and `everyMappedEndpointHasARowInTheMatrix` fails, naming the endpoint, when a controller method has no row. The sample path should address something that does not exist so an allowed call changes nothing. Known limit of the `@PreAuthorize` convention: a signed-in caller with the wrong role who sends a *malformed* body gets the endpoint's 400, not a 403, because Spring validates the body before the method-security advice runs (a valid body is 403; nothing about any user leaks). Pinned by `aWrongRoleCallerMayStillSeeValidationOfAMalformedBody`.
- Courses (3.1a, `entity/Course`, `CourseService`, `CourseController`): `POST /courses` is teachers only (`hasRole('TEACHER')`, admin excluded), body `CourseRequest {title, description?}` (title trimmed, 1–255; description at most `CourseRequest.DESCRIPTION_MAX` 5000, blank = none; any `teacherId`/`enrollCode` sent is ignored), answers 201 `CourseResponse` **including the `enrollCode`, which is for the owner only**: 3.1b/3.1c must not hand that record to students unchanged. The code is 8 symbols from `EnrollCodeGenerator.ALPHABET` (upper-case letters without `I`/`O`, digits `2–9`, `SecureRandom`): **upper-case whatever a student types before looking one up**. Uniqueness is the DB constraint's job: `CourseService.create` retries on `courses_enroll_code_key` (max 5) and so is deliberately **not** `@Transactional` (Postgres aborts a transaction at the first constraint error). `service/Constraints.isViolationOf(error, constraintName)` is the one way to recognise a named constraint; a deleted teacher (`courses_teacher_id_fkey`) is the 401 `ACCOUNT_NO_LONGER_EXISTS`.
- Course list (3.1b): `GET /courses` is open to any signed-in user and the **token's role picks the list** (`CourseService.listVisibleTo`): a teacher's own courses, a student's enrolled courses (`CourseRepository.findEnrolledBy`, via `entity/Enrollment`, composite key `EnrollmentId`), every course for an admin; no parameter can name another user. Paginated with `PageResponse`, id order. `CourseResponse.forRole(course, viewer)` is the one place that decides who gets the enrollment code: **a student's JSON has no `enrollCode` key at all** (`@JsonInclude(NON_NULL)` on that component only); use it for every course shape a student can see (3.1c).
- Course access (3.1c, `service/CourseAccess`): **"may this user see this course?" is answered only here** (`canView`, `requireViewable`); later phases add their own methods next to it (assignments, submissions) rather than re-implementing the rule. Teacher: owns it; student: enrolled; admin: any; by the token's role, so an enrolled teacher does not see a course they do not own. `GET /courses/{id}` returns `CourseResponse.forRole`. **A course the caller may not see is a 404 `COURSE_NOT_FOUND`, byte-for-byte the same answer as an id that does not exist** (a 403 would tell which ids are taken); use `CourseNotFoundException` for that case. `CourseService.listVisibleTo` is the same rule as a query: `CourseAccessTests` compares the two for every user and course, so change both together.
- Changing a course (3.1d): `PUT /courses/{id}` replaces title and description only (same `CourseRequest` rules as create; owner and code never change) and `DELETE /courses/{id}` answers 204; both are `hasAnyRole('TEACHER', 'ADMIN')` plus `CourseAccess.requireManageable`. **The status convention for writes: if the caller cannot see the course it is the 404 `COURSE_NOT_FOUND`; if they can see it but not change it it is `AccessRefusedException` (403)**; a student is refused 403 by the role rule before any lookup. `canManage` (owner or admin) always implies `canView`, a test keeps it so. Delete removes the course's enrollments (membership only) and is blocked with 409 `COURSE_HAS_ASSIGNMENTS` while assignments exist: the foreign key `assignments_course_id_fkey` decides (no pre-check), and the refusal rolls back the enrollment deletion. A table that gains a foreign key to `courses` must be added to that handling and to `RealHttpTestBase.emptyTables`.
- Joining a course (3.2a, `EnrollmentService`): `POST /courses/enroll` `{code}` is `hasRole('STUDENT')` only. The code is looked up after `EnrollCodeGenerator.normalize` (trim + upper-case, nothing else is guessed). The answer is 200 with the course **as a student sees it (no `enrollCode`)**, the same 200 and body when already enrolled. The insert is `EnrollmentRepository.insertIfAbsent` (`INSERT ... ON CONFLICT DO NOTHING`), so the primary key decides and simultaneous joins cannot produce an error; it is a native `@Modifying` query and **needs a transaction** (the service method is `@Transactional`; a test calling the repository directly must open one). An unknown code is 404 `ENROLL_CODE_NOT_FOUND` (never 403, always the same body); a code over 20 characters is a 400; `EnrollRequest.toString` hides the code. There is no rate limit on guessing codes (see `docs/suggestions.md`).
- Leaving and the roster (3.2b, `EnrollmentService`): `DELETE /courses/{id}/enrollment` is `hasRole('STUDENT')` and answers 204; one `DELETE` statement (`EnrollmentRepository.deleteByCourseIdAndStudentId`) decides, and 0 rows is the 404 `COURSE_NOT_FOUND` (not enrolled, missing course and a second leave all look alike). Only the enrollment row goes: submissions reference the assignment and the student, never the enrollment, so past work stays. `GET /courses/{id}/students` is `hasAnyRole('TEACHER', 'ADMIN')` plus `CourseAccess.requireManageable` (owner or admin, as 3.1d), paginated with `PageResponse` in student id order, rows `StudentSummaryResponse {id, email, fullName}` (no role, no hash). The query is `UserRepository.findEnrolledIn`.
- Creating an assignment (3.3a, `AssignmentService`, `AssignmentController`): `POST /courses/{courseId}/assignments` is `hasRole('TEACHER')` (admin excluded, as for creating a course) plus `CourseAccess.requireManageable`, which runs **first**, so a caller who cannot see the course gets the 404 `COURSE_NOT_FOUND` whatever the body says. Answers 201 `AssignmentResponse` (the teacher's view; 3.3b needs a student shape), always unpublished (`published`, `courseId`, `id` in the body are ignored). Required: `title`, `description`, `language`, `deadline`, `timeLimitMs`, `memoryLimitMb` (no defaults, so no limit can be silently loosened); optional `maxAttempts` (null = unlimited) and `starterCode` (blank = none). The maxima are placeholder constants in `AssignmentRequest` (description 20000, starter code 50000, attempts 100, time 10000 ms, memory 1024 MB). `language` is trimmed, upper-cased and checked against `SandboxProperties.supports` (the languages config, 4.1b, below; the 3.3a stand-in `AssignmentProperties` is gone); unsupported is 400 `UNSUPPORTED_LANGUAGE` (value not echoed). A deadline not after `Clock.instant()` is 400 `DEADLINE_NOT_IN_FUTURE`. A course deleted mid-request (`assignments_course_id_fkey`) is the 404. `RealHttpTestBase.emptyTables` now clears assignments through `AssignmentRepository` (a test that inserts submissions must delete them first).
- Reading assignments (3.3b, `AssignmentService`, `AssignmentController`): `GET /courses/{courseId}/assignments` (paginated with `PageResponse`, id order) and `GET /assignments/{id}` are open to any signed-in user; the rule is `CourseAccess.requireViewable` for the course plus `CourseAccess.canViewAssignment(role, assignment)` (**a student sees published assignments only**; teacher-owner and admin see drafts too). Not visible = 404: a course gives `COURSE_NOT_FOUND`, an assignment gives the new `ASSIGNMENT_NOT_FOUND`, byte-identical for a missing id, another teacher's course, a non-enrolled student and (for a student) a draft. `AssignmentResponse.forRole(a, viewer)` is the one place that shapes it: a student's JSON has **no `published`, `createdAt`, `updatedAt` keys** (`@JsonInclude(NON_NULL)` on those components only; `maxAttempts` stays present as `null` for unlimited). Later phases that add the rubric and tests to this response must mask them for students there. Publishing is `POST /assignments/{id}/publish` (3.3c).
- Changing an assignment (3.3c, `AssignmentService`): `PUT /assignments/{id}` (same body and rules as create), `POST /assignments/{id}/publish`, `POST /assignments/{id}/unpublish` and `DELETE /assignments/{id}` (204) are all `hasAnyRole('TEACHER', 'ADMIN')` (as 3.1d; students 403 by role). `lockManageable` is the one entry: it reads only the course id, runs `CourseAccess.requireManageable`, and turns the course's 404 into `ASSIGNMENT_NOT_FOUND` (so an unseen assignment looks exactly like a missing one), then takes the row lock. **The lock is `AssignmentRepository.findByIdForUpdate`, a native `FOR UPDATE`, on purpose**: Hibernate's `PESSIMISTIC_WRITE` on Postgres is `FOR NO KEY UPDATE`, which does not wait for a submission being inserted (its foreign key holds `FOR KEY SHARE`); `aSubmissionBeingMadeRightNowDecidesTheLanguageLock` pins it. Phase 5's submission insert needs nothing special: the foreign key takes that lock by itself. **Locked after the first submission: only the language** (409 `ASSIGNMENT_LANGUAGE_LOCKED`, only when it actually changes); title, description, deadline, limits, attempts and starter code stay editable. A language or deadline that is not changed is not re-validated (a typo can be fixed after the deadline, a removed language does not freeze the assignment). `DELETE` removes the assignment's rubric criteria and test cases (native deletes until 3.4a/3.5a give them entities; switch to those) and is 409 `ASSIGNMENT_HAS_SUBMISSIONS` when any submission exists, with nothing removed. Publish and unpublish are idempotent 200s returning the teacher's `AssignmentResponse`; publishing a draft is checked by `PublishRules` (3.4b, below). Unpublishing stays allowed with submissions. `Assignment.updatedAt` is now written by the application (`revise`, `setPublished`; microsecond precision, from the injected `Clock`).
- Rubric (3.4a, `RubricService`, `RubricController`, `entity/RubricCriterion`, `CriterionType`): `GET /assignments/{id}/rubric` (answers `{criteria, totalWeight}`, unpaginated), `POST` (201), `PUT /assignments/{id}/rubric/{criterionId}` and `DELETE .../{criterionId}` (204), all `hasAnyRole('TEACHER', 'ADMIN')` (students are refused even for a published assignment: what a student may see of the rubric is undecided, see decisions-phase-03) plus the assignment's access rule (another teacher gets `ASSIGNMENT_NOT_FOUND`, byte-identical to a missing id). Body `{name, type, weight}`: name trimmed 1-255; type spelled exactly as `CriterionType` (unknown = 400); weight 1-100. **`CriterionType.isAvailable()` is the switch for "not available yet"**: only `TESTS` is true, the others are 400 `CRITERION_TYPE_NOT_AVAILABLE`; 5.4d, 13.4a and 15.2a each flip their own flag. **The weights are not required to sum to 100 here** (3.4b enforces it at publish; `totalWeight` is for the client). Locked after the first submission: add, change and delete are all 409 `RUBRIC_LOCKED`. Every write goes through `AssignmentService.lockDraftForGradingChange` (3.5a; it wraps `lockManageable`, public, `Propagation.MANDATORY`, native `FOR UPDATE`, see the 3.3c note) so the submissions check is exact: **use it for anything that changes what a submission is graded against**. Since 3.5a a write is also refused with 409 `ASSIGNMENT_PUBLISHED` while the assignment is published, and the checks run before the body's type check. A criterion of another assignment or a missing one is 404 `CRITERION_NOT_FOUND`; deleting a criterion that test cases reference is 409 `CRITERION_HAS_TESTS` (the foreign key `test_cases_criterion_id_fkey` decides, nothing cascades). The `config` column is not mapped yet. `RealHttpTestBase.emptyTables` now clears `rubric_criteria` first (a test that inserts `test_cases` or `submissions` deletes them itself, see `RealHttpRubricTests`).
- Publish rules (3.4b, `service/PublishRules`, called from `AssignmentService.setPublished` under the row lock): publishing a **draft** needs a rubric whose weights add up to exactly `PublishRules.REQUIRED_TOTAL_WEIGHT` 100 (no criteria = 0, so an empty rubric is refused) and at least one test case in every `TESTS` criterion; otherwise 409 `RUBRIC_WEIGHTS_INVALID` or 409 `CRITERION_HAS_NO_TESTS` (the weight rule is reported first; the message is fixed text, the teacher reads `totalWeight` from `GET .../rubric`). Nothing changes on a refusal. **Only a change to published is checked**: publishing an already-published assignment is the usual no-op 200 and hiding never checks. The test count per criterion is `RubricCriterionRepository.countTestsCriteriaWithoutTests` (native, no `test_cases` entity until 3.5a: switch to it then). That gap (editing a published rubric) is closed in 3.5a, below. A test that needs a publishable assignment calls `RealHttpAssignmentChangeTests.addCriterionWithTest` (one `TESTS` criterion of weight 100 with one test) or publishes by SQL.
- Test cases (3.5a, `TestCaseService`, `TestCaseController`, `entity/TestCase`, `TestVisibility`): `POST` (201), `PUT .../{testId}`, `DELETE .../{testId}` (204) are `hasAnyRole('TEACHER', 'ADMIN')` plus the assignment access rule (another teacher: `ASSIGNMENT_NOT_FOUND`; students 403 by role); `GET /assignments/{id}/tests` (`{tests}` in run order: position, then id; unpaginated) is open to any signed-in user with the shape picked by the token's role (3.5b, below). **`TestCaseResponse` is the teacher's view with hidden tests in full: never build a student or LLM shape from it.** Body `{criterionId, name, input, expectedOutput, visibility, weight, position?}`: name trimmed 1-255; `input`/`expectedOutput` required but may be empty and are stored as sent (no trimming; the comparison normalises trailing whitespace later), except that **`\r\n` in `input` becomes `\n`** (4.7e, in the `TestCaseRequest` constructor, so create and update both get it and the size cap applies to the stored text; a lone `\r` is kept, `expectedOutput` is untouched); visibility exactly `PUBLIC`/`HIDDEN`; weight 1-100; position 0+, left out = after the last test (create) or unchanged (update). Placeholder caps in `TestCaseRequest` (text 100000 chars each, weight 100). `criterionId` must be a `TESTS` criterion of the same assignment, else 400 `TEST_CRITERION_INVALID` (missing, another assignment's and a wrong type are indistinguishable). A test of another assignment or a missing one is 404 `TEST_CASE_NOT_FOUND`. **Writes (tests and rubric) need a draft with no submissions**, via `AssignmentService.lockDraftForGradingChange(user, role, id, lockedBySubmissions)`: submissions first (409 `TESTS_LOCKED` / `RUBRIC_LOCKED`), then published (409 `ASSIGNMENT_PUBLISHED`: unpublish, edit, republish and `PublishRules` runs again). Reads stay open on a published assignment. `RealHttpTestBase.emptyTables` clears `test_cases` first.
- Student view of the tests (3.5b, `dto/StudentTestCaseResponse` + `StudentTestCasesResponse`, `TestListResponse`): `GET /assignments/{id}/tests` is no longer role-restricted; teacher/admin (who manage the course) get `TestCasesResponse` (everything), a **student gets `StudentTestCasesResponse`, and only for a published assignment of a course they are in** (otherwise the 404 `ASSIGNMENT_NOT_FOUND` of a missing id, via `AssignmentService.getVisibleTo`). **The masking is in the type, not in a filter**: `StudentTestCaseResponse` is sealed into `PublicTest {id, name, input, expectedOutput, visibility, weight, position}` and `HiddenTest {id, name, visibility, position}`, and a hidden test's `name` is `Hidden test N` (N counts the hidden tests in run order), so there is no field in which its name, input or expected output could be serialised; `StudentTestCaseResponseTests` pins the component names and `RealHttpStudentTestViewTests` asserts on the raw JSON (key sets, and that no hidden string appears anywhere in the body). `StudentTestCasesResponse.of(List<TestCase>)` is the only mapper from entity to student shape, and **Phase 6's AI prompt must build its test section from it (or the same types), never from a `TestCase`**. Students get no `criterionId` (the rubric is not visible to them, see 3.4a) and no `assignmentId`. A new student-facing field belongs on `PublicTest` only, and needs a test for the hidden one.
- Phase 3 authorization matrix (3.6a, `AuthorizationMatrixTests`): where `RoleMatrixIntegrationTests` asks which *role* may call an endpoint, this asks which *relationship to the course* may: each Phase 3 endpoint (course, enrollment, assignment, rubric and test endpoints; 25 rows) is called by the owner, another teacher, an enrolled student, a non-enrolled student and an admin, with a world built per call in the state the row names (`Setup`: draft, published, criterion without tests, empty course). Per row it checks the five statuses, that a refused caller **changes nothing** (before/after snapshot of the course, enrollment, assignment, rubric and test tables) and that every 404 is **byte-identical** to the 404 of an id that does not exist; plus anonymous = 401 everywhere. `everyPhase3EndpointHasARow` fails, naming the endpoint, when a method of `CourseController`, `AssignmentController`, `RubricController` or `TestCaseController` has no row: **a new endpoint in those controllers needs a row here as well as in the role matrix** (a new Phase 3 controller must be added to that guard). A row whose caller list differs between draft and published (assignment reads) is given twice.
- Phase 3 rule tests (3.6b): `RealHttpPublishRaceTests` (publish round trips and the row-lock claim: a publish waits for a rubric edit in flight and then sees it, and an edit waits for a publish and is then refused; a held `SELECT ... FOR UPDATE` plays the other request), `RealHttpHiddenTestSweepTests` (**sweeps every GET endpoint Spring maps**, as an enrolled student, a non-enrolled student, another teacher and nobody, and searches the raw bodies of every status for three markers that exist only inside one hidden test; it fails with "teach the sweep about {name}" when a new endpoint has a path variable it cannot fill, so a Phase 5+ endpoint cannot ship unchecked; a companion test proves the sweep can see the markers when the owner or an admin asks), `RealHttpEnrollIdempotencyTests` (a repeat join keeps `enrolled_at`, shows once in roster and list, leaves a classmate alone, returns the same body, never shows the code). The single cases of each rule are in `RealHttpPublishRulesTests`, `RealHttpStudentTestViewTests` and `RealHttpEnrollTests`.
- Sandbox types (4.1a, package `sandbox`): `SandboxRunner.run(SandboxRequest)` returns a `SandboxResult`; Phase 5 codes against the interface only. `SandboxRequest {language, sourceFiles, stdin, limits}` (`SourceFile` names must be plain file names, unique ignoring case; `ExecutionLimits {timeLimitMs, memoryLimitMb}` both positive); `SandboxResult {status, exitCode, stdout, stderr, stdoutTruncated, stderrTruncated, runtime}`. `SandboxStatus` is `OK`, `COMPILE_ERROR`, `RUNTIME_ERROR`, `TIMEOUT`, `MEMORY_LIMIT` (the program's doing) and `SANDBOX_ERROR` (the sandbox failed: never a grade, never the student's fault). **Compare stdout only when `completedCleanly()`** (status `OK` and stdout not cut). The `toString` of all of them shows lengths, never code, input or output. 
- Languages config (4.1b, `sandbox/SandboxProperties` + `sandbox/LanguageSpec`, registered by `config/SandboxConfig`): `sandbox.languages.<ID>` in `application.yml` is **the only list of languages** (assignment validation reads it, the runner will too). Each entry: `image`, `source-file-name` (a plain file name; for Java it must match the public class, so `Main.java` / `class Main`: the convention to tell teachers and students), `compile-command` (list; omit for an interpreted language) and `run-command` (list, required). Commands are argument lists, never shell strings. Ids are trimmed and upper-cased, a duplicate id, an empty map, a blank command element, an image starting with `-` or containing whitespace, or a non-plain source file name stops startup. `find(typed)` gives the `LanguageSpec`. **Adding a language is a new yml entry plus an image under `infra/sandbox/`, no code**: `NoLanguageBranchTests` fails if production code names a language as a string literal, and `RealHttpNewLanguageTests` shows a config-only language accepted by `POST .../assignments`. The image names are built by 4.2b, below.
- Runner images (4.2b, `infra/sandbox/java|python/Dockerfile`, bases `eclipse-temurin:17-jdk-jammy` and `python:3.12-slim`, approved at 4.2a): build with `docker build -t grading-sandbox-java:dev infra/sandbox/java` (and `-python:dev` for Python); the tag is `sandbox.languages.<ID>.image`. Both run as the fixed user `10001:10001` (no home, no login shell) with `/work` as an empty working directory that user owns; `curl`/`wget` (Java image) and `pip` (Python image) are removed; the Python image sets `PYTHONDONTWRITEBYTECODE` and `PYTHONUNBUFFERED`. The images hold **no restrictions**: no network, read-only root fs, capability and resource limits come from the runner's `docker run` flags (4.3a). A new language needs a `Dockerfile` in `infra/sandbox/<lower-case id>/`. `SandboxImagesTests` builds the images (cached after the first time) and asserts user, `/work`, absent tools and the config's compile/run commands; it uses `sandbox/DockerCli` (list arguments, timeout, output to files), which later sandbox tests reuse. **Scripts given to `sh -c` through `DockerCli` must not contain double quotes (Windows mangles them before docker.exe sees them).**
- Docker CLI runner (4.3a, `sandbox/DockerCliSandboxRunner`, a `@Component` behind `SandboxRunner`; `DockerRunArguments`, `DockerCommand`): per run a private directory under `<java.io.tmpdir>/grading-sandbox` (owner-only on POSIX; the run directory is `rwxrwxrwx` so the container's user can write it, files `rw-r--r--`; a work root path may not contain a comma) receives the source files and is mounted at `/work` (`--mount`, read-only for test runs, read-write via `runInContainer(..., writable=true)` for the compile step 4.4b). `DockerRunArguments` is **the one place the restrictions are written**: `--network none`, `--pull never`, `--memory` = `--memory-swap`, `--cpus 1`, `--pids-limit 128`, `--read-only`, `--tmpfs /tmp:rw,noexec,nosuid,nodev,size=64m`, `--user 10001:10001`, `--cap-drop ALL`, `--security-opt no-new-privileges`; CPU, PID and tmp size are placeholders pending the human's tuning (Java may need more PIDs, 4.4b). Never loosen one without being asked. No `--rm`: the container is named `sandbox-<uuid>`, labelled `com.gradingplatform.sandbox=true`, its exit code read with `docker inspect` (so a program's exit 125-127 is not mistaken for a Docker failure; no container = `SANDBOX_ERROR`) and then `docker rm --force`d in a `finally`. **No student text is ever a docker argument**; the submission reaches the container only as files and stdin (written from a separate thread so a program that never reads it cannot stall the timeout). `SandboxFlagsTests` creates a container from the runner's own arguments and checks every restriction with `docker inspect`; add a test there for any new flag. A `SANDBOX_ERROR` result has a fixed message and docker's text goes to the log only. **Wall-clock timeout (4.3b):** a run may take the request's `timeLimitMs` plus `START_GRACE` (2 s, placeholder: starting a container is the platform's time, not the program's); then `docker kill` runs on the **container** (killing only the `docker run` client leaves the program running, `DockerCommandTests` shows it) and the result is `TIMEOUT` (no exit code, output so far kept). A program that overruns by less than the allowance is not stopped; its `runtime` shows it. **Output cap (4.3c):** stdout and stderr are each kept to `OUTPUT_LIMIT_BYTES` (1 MiB, placeholder; it must stay above what a test case's expected output can be, 100000 characters) by `BoundedCapture`, which reads the docker client's pipes on its own thread and throws the rest away as it goes, so a program that prints without end grows neither memory nor disk and is never blocked; `stdoutTruncated`/`stderrTruncated` are set on the result and a cut stdout is never `completedCleanly` (a cut stderr does not matter, it is not compared); a cut never splits a UTF-8 character. Output above the cap is not a status of its own: the program runs on (to its exit or the timeout). **Cleanup (4.3d):** the container (`docker rm --force`) and the run directory are removed in `finally` blocks after a success, a failing program, a timeout, a docker failure and an interrupted thread (the removal clears the interrupt flag for its own wait and restores it); `SandboxCleanupTests` counts leftovers. **Startup sweep (4.3e):** a JVM crash or kill skips every `finally`, so `SandboxStartupSweep` (a `SmartInitializingSingleton`: after all beans exist, before any `ApplicationRunner`) calls `DockerCliSandboxRunner.sweepOrphans()` once, which removes every container with the sandbox label and every `run-*` directory under the work root (other entries and symlinks are left alone); it never fails startup, even without Docker. **It removes every labelled container, so nothing that starts runs (Phase 5's executor, 5.2c's recovery) may start before it**, and it assumes one backend instance. **Compile step (4.4b):** a language with a `compile-command` is built first, in one container with the writable run directory and `DockerCliSandboxRunner.COMPILE_LIMITS` (30 s, 512 MB, placeholders: the assignment's memory limit, possibly 128 MB, is too little for `javac`; every other restriction is the same), and run after in a read-only one. A failed build is `COMPILE_ERROR` with the compiler's output in `stdout`/`stderr` and its exit code (no test container is started); a build that exceeds its time is also `COMPILE_ERROR`, with the fixed text `Compilation took too long and was stopped.` and no exit code; a sandbox failure while compiling stays `SANDBOX_ERROR`. `result.runtime()` is the run's, not the build's. `javac` is given the bare file name, so its messages hold no host path. The convention for teachers and students (`Main.java`, public class `Main`, no `package`) is in the README, "Submission conventions". The compile step is part of `run()`; Since 4.6a the build is done once per submission, see below. **Exit conditions (4.5a, `sandbox/ExitClassification`, pure):** the runner reads `State.ExitCode` and `State.OOMKilled` in one `docker inspect` before removing the container, and a container that ended on its own is `OK` (exit 0, whatever the flag), `MEMORY_LIMIT` (non-zero **and** the kernel's out-of-memory flag, whatever the code) or `RUNTIME_ERROR` (any other non-zero code; 137 is `MEMORY_LIMIT` since 4.7a, see below). A timeout is decided first from our own deadline, so our `docker kill` is never taken for a memory kill. **Exit 137 is `MEMORY_LIMIT` whatever the flag says (4.7a, the human's decision):** on the CI runner Docker sometimes did not record `OOMKilled` for a real memory bomb (exit 137, empty stderr, 0.2 s), and reading it again 5 x 100 ms did not bring it back, so `ExitClassification.classify` trusts the code; only a deliberate `exit(137)` is mislabelled (pinned in `SandboxExitStatusTests`), and a 137 without the flag is logged as a warning. **Other non-zero codes still need the flag** for `MEMORY_LIMIT` (a failing parent after a killed helper), so that path can flake the same way. In the compile container a memory kill is a `COMPILE_ERROR` (exit code 137), not `MEMORY_LIMIT`. **A Java memory bomb is a `RUNTIME_ERROR` with `OutOfMemoryError` on stderr, not `MEMORY_LIMIT`:** the JVM caps its heap at a quarter of the container's memory and throws before the kernel acts (pinned in `SandboxExitStatusTests`; the choice is the human's, see decisions-phase-04, 4.5a). Python's PID 1 ignores signals sent from inside the container, so a test cannot make a program SIGKILL itself; use `sys.exit(137)` or a child process. **Output comparison (4.5b, `sandbox/OutputComparison` + `TrailingWhitespaceComparison.INSTANCE`):** `matches(expected, actual)` is the one rule for "is this the expected output" and an interface so a strict mode can replace it; `passes(SandboxResult, expected)` (default method) is what a test case's pass is: `completedCleanly()` **and** a match, so a cut output, a crash after the right output and every non-`OK` status never pass. The default splits at `\n`, strips trailing whitespace (`Character.isWhitespace`, which includes the `\r` of CRLF) from every line and drops trailing empty lines; leading whitespace, interior blank lines and case count, and a no-break space is not whitespace. It is not a Spring bean yet: Phase 5 picks it (a per-assignment mode would need a lookup, not one bean). **Phase 5/4.6a must grade with `passes`, not with `matches` on `stdout` alone.** **All tests of a submission (4.6a, `sandbox/SubmissionTestRunner`, a `@Component`, the entry point for Phase 5):** `runAll(language, sourceFiles, limits, List<TestCaseInput>)` returns one `TestRunResult {testCaseId, outcome, run}` per test, in order. `TestCaseInput {id, input, expectedOutput}` is a copy out of the entity (the sandbox package does not depend on the database model; its `toString` hides both texts). It goes through `SandboxRunner.runAll(SandboxBatchRequest {language, sourceFiles, stdins, limits})`, a **default method** on the interface (calls `run` per input, building every time, so a simple fake still works) that `DockerCliSandboxRunner` overrides: it prepares the directory, builds **once**, then starts one fresh read-only container per input on that directory. A failed build gives every input the same `COMPILE_ERROR` result (5.3b); after a `SANDBOX_ERROR` the remaining inputs are not tried (`not run`). `run(request)` is now `runAll` of one. Only the *inputs* reach the sandbox; the expected output is compared with in the backend (`OutputComparison.passes`, 4.5b), and public and hidden tests are run and judged identically. `TestOutcome` = `PASSED FAILED TIMEOUT MEMORY_LIMIT RUNTIME_ERROR COMPILE_ERROR`, exactly the `test_results.status` values (store `name()`); `OK` becomes `PASSED` or `FAILED` (a cut output is `FAILED`). **A sandbox failure is never an outcome:** any `SANDBOX_ERROR` makes `runAll` throw `SandboxFailedException` (fixed message), and Phase 5 (5.2b) puts the submission in `ERROR`; nothing is stored. Every test is run even after a failure (scoring is the weighted fraction passed). **`TestRunResult.run` holds a hidden test's actual output in full, the teacher's view: a student's view is built from the masked types in 5.5a, never from it.** The runner may now be wired into grading (Phase 5). The first run pulls the two base images and builds, which takes a few minutes.
- Hostile-program suite (4.7a, `SandboxHostileProgramTests`, 22 tests, ~45 s, real containers): the class Javadoc maps every test to a threat category (resource exhaustion, filesystem manipulation, sensitive information exposure, external communication, dangerous operations) and to the restriction that stops it, for the thesis' security chapter. A probe is a Python program that prints `label=ALLOWED` or `label=<errno>` (`PRELUDE` + `attempt`), read back with `facts(result)`; **a new restriction or threat gets a probe line and an `assertRefused` there, and a mutation check (remove the flag in `DockerRunArguments`, the suite must fail)**. Facts learnt: Docker adds `noexec,nosuid,nodev` to every `--tmpfs` by itself (only an explicit `exec` loosens it); Docker masks `/proc/kcore` with an empty file, so the check is "no bytes came back"; the images already set `USER 10001`, so dropping `--user` changes nothing at run time and only `SandboxFlagsTests` notices; the cgroup check (`memory.swap.max` = 0) is skipped on a host with cgroup v1 or without swap accounting. The fork-bomb tests count live processes against `DockerRunArguments.PIDS_LIMIT`, and the leftover check (`nothingIsLeftBehind`) runs after every test. Do not run the unbounded fork bomb without `--pids-limit`. **A test whose outcome depends on which of two limits fires first (process count vs 128 MB memory) must accept both:** the CI runner (native Linux Docker) hits `MEMORY_LIMIT` where Docker Desktop gives `RUNTIME_ERROR`/`TIMEOUT`.
- Concurrent runs (4.7b, `SandboxConcurrentRunsTests`, 2 tests, ~15 s, real containers): six Python runs started at once (same file name `main.py`, different source and stdin) each see only their own source, stdin, `/work` (just `main.py`) and a fresh `/tmp`, and no output holds another run's secret; the test also checks that several run directories existed at the same moment, so it proves the overlap rather than assuming it. Two `runAll` batches with the same file name run side by side without cross-talk. Mutation-checked: one shared run directory fails both tests.
- Output comparison end to end (4.7c, `SandboxOutputComparisonTests`, 12 tests, ~50 s, real containers): the 4.5b rule's edge cases (CRLF/LF on either side, trailing whitespace, empty output, stderr, output at and over the cap) printed by real Python and Java programs and judged by the `SubmissionTestRunner` bean. A program writes exact bytes with `sys.stdout.buffer`; a table of cases is one suite (one build). **The runner passes stdin byte for byte: a CRLF input would reach the program with its `\r`, and Python's `input()` on Linux keeps it** (Java's `readLine` drops it); so a test case's input is normalised when it is saved (4.7e, see 3.5a above), not in the runner.
- Hidden test data stays outside (4.7d, `SandboxHiddenTestDataTests`, 2 tests, ~20 s, real containers): **a test's input reaches the container only as its own stdin, one test per container, and no expected output ever does** (the comparison is in the backend). A spy submission (Python, and Java for the build path) reads its stdin, then every regular file it can reach from `/` in full, plus `/proc/<pid>/cmdline` and `environ` of every visible process and its own environment (`/proc` and `/sys` are otherwise skipped), searching for every test's input and expected output; the markers are in its source as hex only. Positive controls: a literal marker in a source comment must be found in `/work` and the spy's own copy of its stdin in `/tmp`, so a search that silently reads nothing fails. Files the program cannot open (e.g. `/etc/shadow`) count as out of reach. **Anything new that reaches the container (a file in the run directory, a `docker run --env`, a mount, an argument) must keep this test green**; mutation-checked: inputs written into the run directory, the expected output appended to stdin, and the input passed as an environment variable each fail both tests.
- Submitting (5.1a, `SubmissionController`, `SubmissionService`, `entity/Submission` + `SubmissionStatus`, `SubmissionRepository`): `POST /assignments/{assignmentId}/submissions` is `hasRole('STUDENT')` (teachers and admins 403), body `SubmissionRequest {sourceCode}` (`@NotBlank`, stored exactly as sent; its `toString` hides the code; a `language` or anything else in the body is ignored), answers **202** `SubmissionAcceptedResponse {id, attemptNo, status: "QUEUED", submittedAt}` and never waits for grading. The language stored is the assignment's. An assignment the student may not see (not enrolled, a draft, another course, no such id) is the 404 `ASSIGNMENT_NOT_FOUND` of a missing id, byte for byte. **The assignment is read with `AssignmentService.lockVisibleForSubmission`** (`Propagation.MANDATORY`): course access first, then `AssignmentRepository.findByIdForKeyShare` (native `FOR KEY SHARE`, the lock the submission's foreign key takes anyway, taken at the read), then the published check under it, so a teacher's language change or unpublish in flight is waited for and then seen, and a later one waits for the submission and is refused (3.3c). Submissions never wait for each other. `attemptNo` is `SubmissionRepository.nextAttemptNo` (max + 1 per student and assignment), made exact by the enrollment lock of 5.1c (below). `RealHttpTestBase.emptyTables` now clears `submissions` first (`submissions` field); a test that adds `test_results`, `grades` or `ai_feedback` rows deletes them itself.
- Submitting a file (5.1b, same `SubmissionController`/`SubmissionService`): the same URL with `multipart/form-data` (the JSON one now declares `consumes = application/json`; any other content type is 415), **one file in the part `file`** (none, two, or a plain field: 400 `ONE_SOURCE_FILE_EXPECTED`; other parts are ignored), same role, answer and attempt sequence as text. The file is read in memory into `source_code` and never stored: at most `SubmissionService.SOURCE_MAX_BYTES` (128 KiB, placeholder; bytes, not characters; the same cap as text since 5.1c) else 413 `SOURCE_TOO_LARGE`; strict UTF-8 without NUL else 400 `SOURCE_NOT_TEXT`; a leading BOM is dropped; blank is 400 `SOURCE_FILE_EMPTY`; otherwise byte for byte. Then the assignment (the usual 404, so a wrong extension tells nothing about an unseen assignment), then **the extension, compared ignoring case with `LanguageSpec.sourceFileExtension()` (that of `source-file-name`, so no language is named in code) for the language read under the lock**: 400 `SOURCE_FILE_EXTENSION_MISMATCH`; only the part after the last `/` or `\` and the last `.` counts (`SourceFile.extensionOf`), and the file's name is not kept (a Java file is still built as `Main.java`). A language no longer in the config is 400 `UNSUPPORTED_LANGUAGE`. `spring.servlet.multipart` in `application.yml` is the server's hard bound (1MB, must stay above the cap; `GlobalExceptionHandler.handleMaxUploadSizeExceededException` gives it the same `SOURCE_TOO_LARGE`) with `file-size-threshold` above it so no part is ever written to disk; it is checked while the request is parsed, before `@PreAuthorize`, so a teacher's oversized upload is 413, not 403. Tests: `RealHttpSubmitFileTests` (its `upload` helper builds a multipart body by hand).
- Submission rules (5.1c, `SubmissionService.accept`, shared by text and file): first the body (text: at most `SOURCE_MAX_BYTES` UTF-8 bytes else 413 `SOURCE_TOO_LARGE`, and **storable** else 400 `SOURCE_NOT_TEXT`: no U+0000, which Postgres `TEXT` rejects with a 500, and no unpaired surrogate, which would be stored as `?`; files as in 5.1b), then in order: the visibility 404 (assignment under `FOR KEY SHARE`), **the student's enrollment row locked `FOR UPDATE`** (`EnrollmentRepository.lockByCourseIdAndStudentId`; missing = the same 404, so a leave in flight is waited for and seen), so **one student's submissions are made one at a time** and the attempt number and limit are exact (other students never wait); the deadline (409 `SUBMISSION_DEADLINE_PASSED` when the arrival instant is **after** it; exactly at it is accepted); attempts (409 `ATTEMPT_LIMIT_REACHED` when `max_attempts` is set and used up; every stored submission counts, whatever its status); the language still configured (400 `UNSUPPORTED_LANGUAGE`, text too now); a file's extension. Lock order is assignment, then enrollment; keep it (nothing else takes them the other way round). **`submitted_at` is written by the application**: the injected `Clock` read when the request arrives (microseconds), the same instant judged against the deadline, so waiting for a lock never makes a submission late; the column's `DEFAULT NOW()` is only for SQL inserts (seed data). Tests: `RealHttpSubmitRulesTests`, which uses `MutableClock` (test package; `@Import(MutableClock.Config.class)` makes it the primary `Clock`, the system clock until `set`) for exact deadline instants, and its own thread pool so bursts are really simultaneous on a small CI runner.
- CORS (2.4d, `config/CorsConfig` + `config/CorsProperties`): the allowed origins come from the comma-separated `CORS_ALLOWED_ORIGINS` (bound to `cors.allowed-origins`, no default in `application.yml`; unset or empty = no cross-origin call allowed). Entries must be plain `http(s)://host[:port]` origins: a wildcard, a path or a trailing slash stops startup. Credentials are off (the token is a header, never a cookie, 2.4a); methods `GET POST PUT PATCH DELETE OPTIONS`, headers `Authorization Content-Type Accept`, preflight cached 1h. `SecurityConfig` enables it with `http.cors(...)` so a preflight (which carries no token) is answered before authentication; a request from any other origin is a 403. A new header the frontend must send has to be added to the allowed list in `CorsConfig`.
- `MockMvc` does not perform the container's error dispatch to `/error`, so it cannot see a security rule turning an error status into 403. `RealHttpAuthTests` and `RealHttpJwtFilterTests` (a real server on a random port) covers the statuses that matter to clients; add a real-HTTP check for any new endpoint whose error statuses are part of its contract.
- Schema conventions (set in 1.2a, reuse in every later migration): `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`, enum-like values (e.g. `role`) are plain `VARCHAR` validated in the application layer, no DB `CHECK`; foreign keys get an explicit `idx_<table>_<column>` index (Postgres does not create one) unless the column is already the leading column of the primary key or a unique constraint. Migration tests (`*MigrationTests`) run against Testcontainers inside a `@Transactional` test; Postgres aborts the transaction on the first constraint error, so use one test per violation.
- The `SPRING_DATASOURCE_*` environment variables bind directly to `spring.datasource.*` and always override the file. Outside the `dev` fallbacks they have no default, so the app fails at startup if they are missing (the `prod` case). Tests never use them.
- Configuration comes from environment variables listed in `backend/.env.example` (datasource, `JWT_SECRET`, `AI_SERVICE_URL`, `AI_SERVICE_TOKEN`, `CORS_ALLOWED_ORIGINS`). Never commit `backend/.env`, and never log secrets.

## Conventions
- Packages are organised **by layer** under the base package (2.1b, chosen by the human): `controller`, `service`, `repository`, `entity` (JPA entities and their enums), `dto` (request/response objects; entities are never returned from the API), `config`, `security`, plus `sandbox` (Phase 4) and `ai` (Phase 7). Each has a `package-info.java` saying what belongs there; put new classes in the matching package and add a new top-level package only through a task. No other naming convention exists yet — each is decided by the task that introduces the first class of its kind (a choice with no default in any `*.md` file is a gate).
- Backend-relevant rules fixed in the root `CLAUDE.md` Defaults: schema changes only through Flyway; Spring Security + JWT, no OAuth; student code runs only in a sandbox container started through a `SandboxRunner` interface (`docker` CLI via `ProcessBuilder`); calls to the AI service are never made inside an open database transaction and never decide the grade.
- Spotless owns formatting: don't hand-format or fight it — run `spotless:apply`.
- Tests are part of the commit that adds the code, and all tests of all three projects must pass before a task counts as finished (root `CLAUDE.md`, Workflow).
- Tests get their database only from Testcontainers (`postgres:16`, matching `infra/docker-compose.yml`) — never the compose database or a CI service container. There is **one** Postgres container per test run (`SharedPostgres`, started on first use, removed by Ryuk at the end) and every Spring test context gets its **own empty database** in it (`CREATE DATABASE` per context), so a different profile, property, mock bean or `@DirtiesContext` still means a clean database and Flyway history, as before, without starting a container each (a run used to start eight). A test gets its database by `@Import(TestcontainersConfiguration.class)` on its `@SpringBootTest` (a `JdbcConnectionDetails` bean, which beats `spring.datasource.*` and `SPRING_DATASOURCE_*`); do not add `@ServiceConnection` containers, `@Testcontainers`/`@Container` or `@DynamicPropertySource` datasource settings. Tests of one context share its database, so clean up what you insert. Tests that call the running server over HTTP extend `RealHttpTestBase` (2.7a): it provides `port`, `users`, `courses`, `jwtService`, empty `courses` and `users` tables before and after each test (`emptyTables`; a phase that adds a table referencing these adds its `deleteAll()` there, referencing tables first), `saved(email, role)`, `tokenFor(user)` and `send/get/post/patch(path, ..., token)` (token without the `Bearer ` prefix, null = anonymous). Repeat `@SpringBootTest(..., properties = ...)` on the subclass for a different configuration. `RealHttpAuthTests`, `RealHttpMeTests`, `RealHttpJwtFilterTests` and `RealHttpRoleSecurityTests` predate the base class and still carry their own helpers; move one onto it when you next change it. MockMvc tests import `TestcontainersConfiguration` directly.
- Docker must be running for the backend tests (Testcontainers) and for the sandbox tests (from Phase 4). On Windows start Docker Desktop first, or `./mvnw verify` fails before running any test.
