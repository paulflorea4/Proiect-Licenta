- (2.4a) `POST /auth/signin` has no brute-force protection (rate limit per IP/email, or temporary lockout), so passwords can be guessed at the speed of BCrypt (~100 ms each). The spec only rate-limits hints (Phase 7). Worth a small task before deployment (Phase 16); signup has the same weakness for spam accounts.
- (2.4a) MockMvc cannot see the container's error dispatch to `/error`, which hid a 403-instead-of-400/401/409 bug in 2.3b/2.3c until a real HTTP run. `RealHttpAuthTests` covers the auth endpoints; later endpoints with contractual error statuses should get the same kind of real-HTTP test.
- (2.6a) GitGuardian flagged a made-up password in a test (`"password":"x1y2z3"` in `RealHttpErrorShapeTests`, PR #56) as a "Generic Password", a false positive like the one in 0.2b. - (2.7a) After the shared Postgres refactor nothing in our test code uses `spring-boot-testcontainers` (`@ServiceConnection`) or `testcontainers-junit-jupiter` any more; both test dependencies in `backend/pom.xml` could be removed. Not done here: dependency changes are outside the row.
- (2.7d) A signed-in caller with the wrong role who sends a malformed or invalid body to a `@PreAuthorize` endpoint gets that endpoint's 400 instead of 403, because Spring validates `@RequestBody` before the method-security advice runs (found by the role matrix on `PATCH /admin/users/{id}/role`; no user data leaks and anonymous callers are 401). Closing it would need an authorization check ahead of argument resolution (a `HandlerInterceptor` that reads the same `@PreAuthorize`, or an explicit role check in the filter chain for `/admin/**`), which reverses the 2.5a convention, so it is the human's call. The current behaviour is pinned by `aWrongRoleCallerMayStillSeeValidationOfAMalformedBody`.

- (3.2a) `POST /courses/enroll` has no rate limit on wrong codes, so a signed-in student can try codes as fast as the server answers (the space is 2^40, so blind guessing is impractical, but a leaked partial code or a short custom code would change that). Same family as the signin/signup suggestion from 2.4a; one small throttle (per user and per IP, with a delay or temporary block after N misses) could cover signin, signup and enroll before deployment (Phase 16). Not done: it is a new mechanism, outside the row.
