- (4.7c) **Test inputs with Windows line endings reach the program byte for byte, and on Linux that matters for Python.** A test input pasted on Windows is stored as typed (3.5a), so `3 4\r\n` arrives on stdin with its `\r`. Java's `readLine`/`Scanner` drop it; Python's `input()` on Linux does **not** (its stdin splits lines at `\n` only), so `input()` returns `'3 4\r'`. `int()` and `split()` hide it, but `if input() == 'yes'` or `len(input())` see it: a correct student program can fail a test only because the teacher wrote the test on Windows. Pinned as today's behaviour in `SandboxOutputComparisonTests.aTeachersWindowsInputReachesTheProgramByteForByte`. Not changed (it changes what a stored test means, so it is the human's call). Options: (a) normalise `\r\n` to `\n` in `input` when a test case is saved (3.5a's `TestCaseService`; the frontend could do the same in its textarea); (b) normalise it just before stdin is written in the runner; (c) leave it and tell teachers in the README. (a) is the one place, and expected outputs need nothing (the comparison already ignores CRLF).
  **Resolved (4.7e):** the human chose (a); `TestCaseRequest` turns `\r\n` into `\n` in `input` on create and update.

- (5.1c) **The backend test suite is at the shared Postgres's connection limit.** Each distinct Spring test context is cached for the whole run with its own Hikari pool (default 10 connections), and the run has 10 contexts against Postgres's default `max_connections` of 100 (3 reserved for superusers). Not done: it changes the shared test infrastructure, which no task covers.
  **Decided by the human after 5.1c: option 1 (`-c max_connections=300`). Resolved (5.1e).**
