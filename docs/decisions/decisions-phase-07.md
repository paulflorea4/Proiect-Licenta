Historical, append-only. One entry per commit where a non-obvious call was made — a gap in the task spec, a gate resolution, a formatter/tool choice, a bug found and fixed. Not read every session — see the note in root `CLAUDE.md`. Load this only when auditing a specific Phase 7 decision.

## 7.1a — Backend `AiServiceClient`

- **Where it lives:** package `ai` (2.1b reserved it for the AI service client): `AiServiceClient`, `AiServiceProperties`, the request and response records and `AiServiceException`. The `@Configuration` that registers them is `config/AiServiceConfig`, as `config/SandboxConfig` registers `sandbox/SandboxProperties`. The records are the AI service's wire contract, not this API's, so they sit with the client rather than in `dto`.
- **Settings: `ai.service.*`, so the existing `AI_SERVICE_URL` / `AI_SERVICE_TOKEN` bind without mapping** (relaxed binding: `ai-service.*` would have needed `AISERVICE_*`). Timeouts can be overridden by `AI_SERVICE_CONNECTTIMEOUT` / `AI_SERVICE_READTIMEOUT` (tested through a replaced environment).
- **Both required at startup, like `JWT_SECRET`.** The other reading was "missing = hints unavailable, the rest works". It was rejected because a deployment without the token would run with every hint request failing at the first student's click, and the AI service itself refuses to start without its token (6.1b). The URL must be http or https with a host (a path prefix is allowed, a trailing slash dropped; a query or fragment refused); the token must be non-blank (no minimum length, as on the AI service side). Checked in the record's constructor, not with bean-validation annotations, so Spring Boot's startup error never prints the token (tested: a failed startup's stack trace does not hold it); `toString` redacts it. Surefire sets throwaway values (`http://localhost:8000`, nothing listens) so every Spring test context starts.
- **Timeouts:** connect 5 s; **read 70 s**, both placeholders in `application.yml`. The read timeout is sized from the AI service's own worst case, which 6.2a said Phase 7 must allow for: up to two Gemini calls (6.3c) with a 30 s read timeout each, plus the service's own work. A student's hint request waits at most this long (7.2a).
- **The client:** Spring's `RestClient` (in `spring-web`, already present) on the JDK `HttpClient` through `JdkClientHttpRequestFactory`, so no new dependency. Built once with the base URL and `Authorization: Bearer <token>` as a **default header**, as the row asks, so no call can be made without it. **Redirects are never followed** (`HttpClient.Redirect.NEVER`): a redirect would carry the token to another host.
- **Never inside an open database transaction, enforced here:** `feedback` throws `IllegalStateException` before sending anything when `TransactionSynchronizationManager.isActualTransactionActive()`. The rule is the root `CLAUDE.md`'s and 7.2a's to honour, but a check in the one place every call goes through means a mistake there fails its tests instead of holding a connection and its locks for up to 70 s.
- **Errors, one type with a fixed message and the status:** **any non-2xx answer, a redirect included, is `The AI service answered HTTP <n>`** with `status() = n`. `RestClient` treats a 3xx as success by default; the first version then read the redirect's empty body and reported "could not be read", which the redirect test caught. No answer is `did not answer in time` (a JDK `HttpTimeoutException`) or `could not be reached` (status null; the I/O error is chained for the log, its message holds the URL only). A 2xx whose body is not a `FeedbackResponse` with a non-blank `hint` and a present `fallback` is `could not be read`; `fallback` is a `Boolean` so a missing one is caught instead of read as false. Messages never hold the token, the request (the student's code) or the response body (the response exception is not chained, its message quotes the body). An unknown field in the answer is ignored, so the AI service can add one before the backend reads it.
- **The contract cannot drift silently:** `AiContractMirrorTests` reads `ai-service/src/ai_service/schemas.py`, takes each pydantic model's fields in order, turns them into camelCase and compares them with the record components (with a positive control that the parser found fields), as the AI service's own test reads `TestOutcome.java`. The CI checks out the whole repository. It only runs with the backend CI, noted in `docs/suggestions.md`. The serialised body is also checked key for key against a fake service, with hidden tests as exactly `[{"passed":true},{"passed":false}]`.
- **Tests without a new dependency:** a fake AI service on the JDK's own `com.sun.net.httpserver.HttpServer` on a free local port, scripted answer by answer (status, body, delay, redirect location), recording each request. WireMock or OkHttp's mock server would have been a dependency, a gate.
- **Tests (+56, backend 2226 -> 2282; ai-service 919 and frontend 3 unchanged and passing):** `AiServiceClientTests` (29): one POST to `/feedback` with the token, JSON and the exact camelCase body; the token on every call; a path prefix kept; the hint and both flag values; an unknown field ignored; 11 bodies that are not a `FeedbackResponse`; 7 error statuses; a redirect not followed and nothing reaching the other host; a read timeout within its bound; a service not running; the connect timeout and redirect policy of the HTTP client; refused inside a transaction with nothing sent; no message or stack trace ever holding the token, the code or the body. `AiServicePropertiesTests` (18): binding, the environment variables, missing URL or token, blank token, six bad URLs, non-positive timeouts, the trailing slash, no token in `toString` or a failed startup. `AiContractMirrorTests` (8). `ApplicationConfigTests` (+1): the timeouts in `application.yml`, no URL or token there.
- **Mutation-checked, each failing at least one test:** no bearer header (2 failures); no read timeout (1); redirects followed (2); no transaction guard (1); no status handler (8); a missing `fallback` accepted (2); a timeout reported as unreachable (1); a blank token accepted (1); any URL scheme (1); the trailing slash kept (1); the token in `toString` (1); a record component renamed (2).
- **CI paths for the two contract tests (second commit, approved by the human on PR #140).** Each service's workflow now also runs when the one file of the other service that its contract test reads changes: `backend-ci.yml` on `ai-service/src/ai_service/schemas.py` (`AiContractMirrorTests`), `ai-service-ci.yml` on `backend/src/main/java/com/gradingplatform/backend/sandbox/TestOutcome.java` (`test_the_outcomes_are_exactly_the_backends`, 6.3a). Exactly those two files, not the other service's whole directory, so an unrelated change on one side still runs only its own checks; the root `CLAUDE.md`'s CI line says so. A change to either file now runs both services' checks, where before a drift showed only on the next PR of the other side.

A race in the test, not in grading. Each round now reads the status once and asserts that value. The other polling helpers (`RealHttpGradingFailureAndRecoveryTests.awaitEnd`, `RealHttpSubmissionWorkerTests.eventually`) already read once.
- **A second unrelated CI failure, fixed in a fourth commit.** The next backend run failed in `JavaCompileStepTests.theProgramRunsWithItsOwnSmallMemoryLimitWhileTheCompilerHadMore` (4.4b): a Java sum program at 64 MB and 10 s ended in `TIMEOUT` (12 s with the start grace); the class took 43.7 s against 17.7 s in the green run, while the rest of the run was no slower (4:53 against 5:12). It is the only real Java program run at 64 MB in the suite (every other Java run uses 128 MB; the other 64 MB runs are Python or a stand-in compile command), so a JVM under a 64 MB cgroup with swap off is the likely cause (its memory-mapped JDK image counts against the limit), though it could not be reproduced locally: on Docker Desktop `java -version` starts in about 0.55 s at 64, 96, 128 and 256 MB alike. The test's point is that the run gets its own limit, smaller than the compiler's 512 MB; at 128 MB it still makes it. **Not changed: which memory limit a Java assignment may have** (any from 1 MB); noted in `docs/suggestions.md`.

## 7.1b — Build the feedback request from a submission

- **Built from the student's own view, not from entities.** The row warns this is where a hidden test could leak. 3.5b already decided that anything AI-facing builds its test section from the student types (`StudentTestCasesResponse.of` or the same types), never from a `TestCase`; 5.5a's `StudentSubmissionResponse` is those types plus the results, masked by type: a hidden test is `HiddenResult {id, name "Hidden test N", visibility, position, passed}`, with no component for its real name, input, expected output, output or stderr. So the single mapping is `FeedbackRequest.of(StudentSubmissionResponse, assignmentDescription, hintLevel)`: the AI service gets exactly what the student can see and never more, and no change to the mapping can leak what its input does not hold. 7.2a gets the view from `SubmissionViewService`, whose student path already checks that the submission is the caller's own.
- **What goes in:** the description (passed in: the student sees it on the published assignment), the submission's language and code exactly as stored, the compiler's message (the view's, so null unless the build failed), each public test as `{name, input, expectedOutput, status, actualOutput, stderr}` and each hidden test as `{passed}`, both in the view's run order. Hidden test names, even the masked "Hidden test N", are not sent: the AI contract has no field for them (6.3a). Not sent either: weights, positions, runtimes, the rubric and the grade (6.3a's contract, which 7.1a mirrors).
- **Refused, rather than sent wrong:** a submission that is not `GRADED` (its view has no tests yet, so the request would claim there are none); a hint level outside 1-3 (the AI service would refuse it with a 422, 6.3a); and a public test of a graded submission without a result (the contract requires a status; it cannot happen while tests are locked after the first submission, 3.3c/3.5a, so it is an `IllegalStateException`, not a quiet omission).
- **A static method on the request record,** as "single mapping method" asks: one place to review. Java 17, so an `instanceof` over the sealed result type rather than a pattern `switch` (21+).
- **A guard keeps it that way:** `FeedbackRequestMappingTests` reads every file of the `ai` package and fails if one references `entity.TestCase`, `entity.TestResult`, `TeacherSubmissionResponse`, `TestCaseResponse` or `SubmissionDetails`, the types that hold hidden tests in full; the mutation check showed that adding just the import of `TestCase` fails it.
- **Tests (+13, backend 2282 -> 2295; ai-service 919 and frontend 3 unchanged and passing):** the entities are built as stored (ids and status set with `ReflectionTestUtils`, as the database would) with every hidden test's name, input, expected output, output and stderr a marker, then go through `StudentSubmissionResponse.of` and `FeedbackRequest.of`: public tests in full and hidden ones as passed only, in run order (two public, three hidden interleaved, one hidden pass); the request serialised as it would be sent holds no marker and not even the masked name, and `hiddenTests` is exactly `[{"passed":true},{"passed":false}]`; the rest copied (description, language, code with a tab and backticks, stderr, level, no compiler output); a compile error sends the compiler's message and no actual output; no tests sends none; four statuses that are not `GRADED`, three levels and a public test without a result are refused; the package guard. 7.5a will test the request on the wire against a mocked AI service.
- **Mutation-checked, each failing at least one test:** a hidden pass inverted (3 failures); hidden tests dropped (3); input and expected output swapped (1); the compiler's message not sent (1); an ungraded submission accepted (3); any level accepted (3); a public test without a status sent (1); the package importing `TestCase` (1).

## 7.1c — Per-language minimum memory limit

- **New row, the human's decision on PR #140,** after the suite's only Java run at 64 MB stalled to `TIMEOUT` on the CI runner while `AssignmentRequest` accepted any memory limit from 1 MB.
- **In the languages config, optional:** `sandbox.languages.<ID>.min-memory-mb`, bound to `LanguageSpec.minMemoryMb` (`Integer`, null = no minimum, at least 1 when set). Java 128 (the value every Java run in the suite uses and the one the human named), Python none. No language is named in code: the check asks the language's `LanguageSpec` (`allowsMemoryLimit`), so `NoLanguageBranchTests` stays green and a new language sets its own.
- **The record gained a component, the 18 places that build one did not change:** a four-argument constructor (no minimum) delegates to the canonical one, which carries `@ConstructorBinding` so configuration binding still uses it. The mutation check showed it is needed: without it no context starts.
- **The question the row left open, answered by 3.3c's rule, not asked:** what happens to an assignment already below a new minimum. 3.3c decided that "a language or deadline that is not changed is not re-validated (a typo can be fixed after the deadline, a removed language does not freeze the assignment)". So the minimum is checked on create, and on update only when the language or the memory limit changes: an older Java assignment at 64 MB can still be renamed, and raising it must reach 128. Publishing does not check it, for the same reason (a draft made before the minimum is not frozen); the dev seed's Java assignment uses 256 MB. Because the rule follows from a written convention, it was not a gate; the human can ask for a publish check if wanted.
- **The error:** 400 `MEMORY_LIMIT_BELOW_LANGUAGE_MINIMUM`, fixed message "The memory limit is below the minimum for this language", neither the value nor the minimum echoed (2.6a's convention). Checked after the language is found (an unsupported language is still `UNSUPPORTED_LANGUAGE`) and before the deadline. A refused update changes nothing.
- **Tests (+21, backend 2295 -> 2316; ai-service 919 and frontend 3 unchanged and passing):** `RealHttpLanguageMemoryMinimumTests` (15): Java at 1, 64 and 127 MB refused with nothing stored, at 128, 256 and 1024 created; Python at 1, 16 and 64 created; the language matched as typed (` java `, `python`); an older Java assignment at 64 MB renamed without touching memory; changing a Java limit to 100 refused with nothing changed; an older one raised to 100 refused, to 128 allowed; switching Python at 64 MB to Java refused; switching Java to Python at 32 allowed. `LanguageSpecTests` (+4): no minimum allows anything, 127/128/1024 against 128, 0 and -1 refused. `SandboxPropertiesTests` (+1) and `ApplicationConfigTests` (+1): Java 128 and Python none, bound and in the file.
- **Mutation-checked, each failing at least one test:** no check on create (4 failures); a limit equal to the minimum refused (3); every update checked (1); a memory change ignored on update (2); a language change ignored on update (1); no Java minimum in the config (9); no `@ConstructorBinding` (27 errors); a minimum below 1 accepted (2).

## 7.2a — `POST /submissions/{id}/hints`

- **The fallback (gate, the human's decision): shown, not stored.** When the AI service answers with its generic safe hint (`fallback: true`, 6.4b), the endpoint returns it with `fallback: true` (200, `createdAt` null) and writes nothing, so the level stays unused and the next request asks for the same level again. Offered against "store it with a `fallback` column and a unique constraint that ignores such rows", which would have let the teacher and the thesis see the fallback rate at the cost of a migration and partial-index work. With this choice the row count stays "real hints used" (V10's comment, 7.4a) and no schema changes. Repeated fallbacks cost one AI call each; rate-limiting hint requests is 16.4c.
- **The request names no level; each POST asks for the next unused one.** The row says "First call → level 1, then 2, then 3" and "returns the stored hint, never regenerates an existing level"; its last sentence names the case where a stored row is returned: two simultaneous requests for the same level. That is the reading taken: no body, the level is the row count + 1, and a request that loses the race to the unique constraint returns the winner's row (200). A sequential repeat therefore asks for the next level; a double-click, which arrives while the first request still waits for the AI service, is the simultaneous case and returns the same row. 7.5b's "repeat request returns the same row" is tested as that simultaneous case.
- **Statuses:** 201 when this request stored the hint, 200 when it returns a row another request stored or a fallback that was not stored. A client treats any 2xx as a hint and reads `fallback`.
- **Built on the student's view,** as 7.1b requires: `SubmissionViewService.view(user, STUDENT, id)` does the ownership check (another student's submission 403, a missing one 404, 5.5a), `StudentSubmissionResponse.of` masks it, `FeedbackRequest.of` builds the request. The description is read from the assignment (the student may have left the course or the assignment may be unpublished: their own submission stays readable, 5.5a, and so does the hint). Students only (`hasRole('STUDENT')`): a teacher who wants to see hints gets them in 7.2b's read.
- **No transaction around the AI call, by construction:** `HintService.requestNext` is not `@Transactional`. The view, the count and the description are read in their own read-only transactions, the AI service is called with none open (the client refuses otherwise, 7.1a), and the insert runs in its own (`saveAndFlush`). A test checks at the moment of the call that no transaction is active; the mutation check showed that putting one around the whole method fails it. Two simultaneous requests therefore both call the AI service; the unique constraint `ai_feedback_submission_id_hint_level_key` decides which row is kept, and the loser returns it.
- **Refused before the AI service is called, nothing stored:** a submission that is not `GRADED` (409 `HINT_NEEDS_GRADED_SUBMISSION`, a new code: 5.4d's `SUBMISSION_NOT_GRADED` message is about scoring by hand) and a fourth request (409 `HINTS_USED_UP`). The rule "at least one test did not pass" is 7.2c's, and the clear 503 for an AI failure is 7.3a's: until then an `AiServiceException` is the generic 500, with nothing stored (tested).
- **A hint never reads or changes the grade** (tested: the total is unchanged after two hints).
- **Supporting changes:** `entity/AiFeedback` maps V10 (report columns read-only until 7.4b), `AiFeedbackRepository` (count, by level, all by level); `RealHttpTestBase.emptyTables` deletes `ai_feedback` before the submissions it references; a role-matrix row (students only); `AiServiceException`'s constructors are public so tests (and 7.3a) can make the client fail.
- **Tests (+20, backend 2316 -> 2336; ai-service 919 and frontend 3 unchanged and passing):** `RealHttpHintRequestTests` (15, the AI client a `@MockitoBean`): the first request stores level 1 (201, the body, the row); the request sent is the student's view with the hidden test as `{passed: false}` and no hidden marker; three requests give levels 1, 2, 3 and a fourth is 409 without a fourth call; levels are per submission; a fallback is shown (200, `fallback: true`, `createdAt` null), not stored, and the next request asks level 1 again and stores it; two simultaneous requests (held until both have asked) store one row and both get it, one 201 and one 200; three unfinished statuses are 409 without a call; another student's submission 403, a missing one 404, the course owner 403, none calling the AI service; no transaction open at the call; the grade unchanged; a failed call stores nothing. Role matrix +5 (the new row, once per caller).
- **Mutation-checked, each failing at least one test:** one transaction around the method (2 failures); a fallback stored (1); no level cap (1); the level off by one (6); the unique-constraint race not handled (1); an ungraded submission allowed (3); teachers allowed (1, the role matrix); a stored hint answered 200 (4).

## 7.2b — `GET /submissions/{id}/hints`

- **"Same role-based projection as 5.5a" = the same access path and a role-picked shape.** `HintService.list` asks `SubmissionViewService.view(user, role, id)` first, so the rule is exactly the submission's: the student who made it may read (another student's existing submission is the 403 `ACCESS_DENIED` of 5.5a, a missing one 404), the owner or an admin may read, another teacher gets the 404 of a missing id (5.5b). Then the token's role picks `HintsResponse.StudentHints` or `TeacherHints`, a sealed type as `SubmissionResponse` is. Reusing `view` loads the submission's details only to throw them away; a lighter access check was not written, so the rule cannot drift from the submission's.
- **The student's shape is `{level, content, createdAt}`:** the level is what identifies a hint to the student (7.4b's report path takes it), so no id. No report fields: the report is read by the teacher (7.4b's note); whether the student sees that they reported is 7.4b's to decide.
- **The teacher's shape adds `id` and `reported`, `reportReason`, `reportedAt`** (V10's columns, false and null until 7.4b writes them), so 7.4b only has to fill them.
- **Level 1 first** (`findBySubmissionIdOrderByHintLevelAsc`). A fallback hint is never listed: it is not stored (7.2a). A submission without hints, graded or not, is an empty list.
- **Reading never calls the AI service and stores nothing** (tested for all five kinds of caller). The hidden-test sweep (3.6b) already resolves `{submissionId}`, so the new GET is swept for hidden-test markers with no change; it stays green.
- **One test context for the hint tests:** `RealHttpHintListTests` declares the same `@MockitoBean AiServiceClient` as `RealHttpHintRequestTests`, so Spring reuses that context instead of starting another (see the 5.1e note on context count).
- **Tests (+14, backend 2336 -> 2350; ai-service 919 and frontend 3 unchanged and passing):** `RealHttpHintListTests` (9): the student's hints level 1 first with exactly `level, content, createdAt`; no report or id in the student's shape even after a report; an empty list; another student 403 with nothing of the hint in the body and a missing submission 404; owner and admin see `id` and the report; an unreported hint shows `reported: false`; another teacher's 404 byte-identical to a missing id's; no AI call and nothing stored for five callers; anonymous 401. Role matrix +5.

## 7.2c — Eligibility: a test that did not pass

- **"Did not pass" is read from the student's own view** (`StudentSubmissionResponse`, the same object the request to the AI service is built from): a public test whose outcome is not `PASSED`, or a hidden test with `passed: false`. So every non-`PASSED` outcome counts (`FAILED`, `TIMEOUT`, `MEMORY_LIMIT`, `RUNTIME_ERROR`, `COMPILE_ERROR`), and the rule cannot see more of a hidden test than the student does.
- **Judged on the test results, never on the total** (the row's note): a submission that passed every test but lost a `MANUAL` mark is refused, tested through a real manual save that leaves the total below the maximum.
- **A graded submission with no tests (an all-`MANUAL` rubric) is refused too.** The row's rule is "at least one test did not pass", and with no tests none did; the AI service's feedback is built around test results, so there is nothing for it to work from. Read literally, not asked; the human can ask to change it.
- **The error:** 409 `HINT_NOTHING_TO_IMPROVE`, fixed message "Every test passed, so there is nothing to improve" (the row's wording), a new code next to 7.2a's. Checked after access and `GRADED` (an unfinished submission's view has no tests, so it must stay `HINT_NEEDS_GRADED_SUBMISSION`) and before the level count; the AI service is not called and nothing is stored.
- **No DTO changed:** the pass test is a private helper in `HintService` (`instanceof` on the sealed result type; Java 17 has no pattern `switch`), not a new method on `PublicResult`, so the student's JSON keys stay exactly as `StudentTestResultResponseTests` pins them.
- **Tests (+9, backend 2350 -> 2359; ai-service 919 and frontend 3 unchanged and passing):** in `RealHttpHintRequestTests`: every test passed is 409 with no call and nothing stored; a lost manual mark on a fully passing submission is still 409; a graded submission without tests is 409; a public test that `FAILED`, `TIMEOUT`, `MEMORY_LIMIT` or `RUNTIME_ERROR` (hidden passed) gets a hint; a hidden failure alone gets one; a compile error gets one.
- **Mutation-checked, each failing at least one test:** no check (3 failures); hidden results ignored (9); only `FAILED` counted as not passed (3); a submission without tests allowed (1); the check before the `GRADED` one (3); judged on the total instead (2).

## 7.3a — AI service failure: 503, nothing changed

- **One status and one code for every failure:** down, timeout, unreachable, an error status (5xx, 4xx) and an unreadable answer are all 503 `HINTS_UNAVAILABLE`, "Hints are unavailable right now; your submission and its grade are not affected. Try again later". The student cannot act on the difference, and the cause (which can be a configuration fault of ours) is not theirs to see; the client's fixed reason is never echoed (no `HTTP <n>` in the body).
- **Caught in `HintService`, not in `GlobalExceptionHandler`:** the hint request is the only caller (7.1a), and the service knows the submission and level for the log line. An `AiServiceException` that escaped anywhere else would still be the generic 500, which is right for a caller that should not exist.
- **Nothing is changed, by construction and tested:** the failure is thrown before the insert, and the grade is never written by a hint (7.2a). The test compares the submission's row, grade, criterion scores, test results and hints before and after, for eight failure kinds.
- **Not retried** (the row: retry and backoff are Phase 16's). One call per request, tested; the level stays unused, so the student's next request asks for it again (tested: 1, fail, 2 again, stored 1 and 2).
- **A refused token is logged as a configuration error** (anticipating 7.5c's "reported as a clear configuration error, not retried"): a 401 or 403 from the AI service is an `ERROR` saying that `AI_SERVICE_TOKEN` must be the AI service's own, without a stack trace; every other failure is a `WARN` with the submission id, the level and the client's fixed message (the cause chained for the log). The student still gets the same 503. Neither line holds the token or the code (tested for the code). 7.5c will add its own end-to-end test against a real refusing service.
- **Log assertions** use Spring Boot's `OutputCaptureExtension` (already in `spring-boot-test`, no new dependency).
- **Tests (+10 net, backend 2359 -> 2369; ai-service 919 and frontend 3 unchanged and passing):** in `RealHttpHintRequestTests` the old "a failed call stores nothing" (>= 500) is replaced by: eight failure kinds (503, 500, 502, 401, 403, timeout, unreachable, unreadable) each a 503 with the fixed code and message, nothing of the reason in the body, everything stored unchanged and one call; after a failure the same level is asked for again and stored; a 401 logged as an `ERROR` naming `AI_SERVICE_TOKEN` and called once; a timeout logged as a `WARN` with its reason and without the student's code.
- **Mutation-checked, each failing at least one test:** the failure rethrown as a 500 (10 failures); 401 not treated as a configuration error (1); every failure logged as one (1); a retry after a failure (10).

## 7.4a — Hints used on the submission

- **A field `hintsUsed` (an `int`, 0 to 3) on both shapes of `GET /submissions/{id}`**, last in each record. Read with the rest of the view (`SubmissionDetails.hintsUsed`, `AiFeedbackRepository.countBySubmissionId`, in `view`'s read-only transaction): "derived from `ai_feedback` rows, no separate counter", as the row says. A fallback is not stored (7.2a), so it is not counted.
- **Shown at any status, not gated on `GRADED`** like the grade and results: it is a count of what the student received, not a result of grading; an unfinished submission cannot have hints (7.2a), so it shows 0. A test pins the 0 for `QUEUED`, `RUNNING` and `ERROR`.
- **The same number for student and teacher.** The row names both views; the hints themselves are listed by 7.2b.
- **One source for "hints used":** `HintService.requestNext` now takes the next level as `view.hintsUsed() + 1` instead of counting again, so the number the student sees and the level they get next cannot disagree. Same query, same transaction boundaries (the view's read), so the race behaviour of 7.2a is unchanged (its tests stay green).
- **Not added to the submission lists (5.5c)** or to `my-grade`: the row says "the submission DTO". A count per list row would be one more join; easy to add when a screen needs it.
- **Hints never affect the score:** the test reads the student's grade before and after each of three hints and finds it unchanged.
- **Key sets updated** where they are pinned: `StudentTestResultResponseTests` (component names), `RealHttpStudentSubmissionViewTests`, `RealHttpTeacherSubmissionViewTests`, `SubmissionAuthorizationMatrixTests` (raw JSON). The hidden-test sweep is unchanged and green.
- **Tests (+7, backend 2369 -> 2376; ai-service 919 and frontend 3 unchanged and passing):** `RealHttpHintsUsedTests` (shares the hint tests' context): 0, 1, 2, 3 after each hint for the student, the owner and an admin, the grade unchanged, a fourth refused and the count still 3; a fallback not counted; the count follows rows inserted and deleted directly; each submission counts only its own; an unfinished submission shows 0 in both views (3 statuses).
- **Mutation-checked, each failing at least one test:** the count always 0 (3 failures); the student's view always 0 (3); the teacher's view always 0 (2); the next level taken as the count instead of the count + 1 (24).
