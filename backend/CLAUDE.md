# backend/CLAUDE.md

Spring Boot 4.1.1, Java 17, Maven. Project-wide rules (gates, defaults, Git safety, PR flow) are in the root `CLAUDE.md`; this file only holds what is specific to `/backend`.

## Commands (run from `/backend`)
- Build + test: `./mvnw -B verify` (`mvnw.cmd -B verify` on Windows). This is also what CI runs (`.github/workflows/backend-ci.yml`).
- Tests only: `./mvnw -B test`
- Run: `./mvnw spring-boot:run` — real OS environment variables are read directly (no dotenv library), so load `backend/.env` into the shell or the IDE run configuration first. See the root README, "Environment variables".
- Format: `./mvnw spotless:apply` (palantir-java-format, 4-space). `spotless:check` is bound to the `verify` phase, so `./mvnw -B verify` (and CI) fails on unformatted code — run `spotless:apply` before committing.
- Use the Maven wrapper, never a system Maven — it pins the version.
- Spring profiles: `dev` for local development, `prod` for deployment (root README). Both live in `src/main/resources/application.yml` (the only config file) as profile-specific YAML documents; select one with `SPRING_PROFILES_ACTIVE`. No profile is active by default, and tests run without one. `dev` falls back to the compose database URL and username (the password has no fallback), `prod` has no datasource fallback and fails fast.

## Layout
- Base package: `com.gradingplatform.backend`. Tests mirror it under `src/test/java`.
- On the classpath: Web, Security, Validation, Data JPA, Flyway (`spring-boot-starter-flyway` plus `flyway-database-postgresql` — in Spring Boot 4 bare `flyway-core` does not autoconfigure), the PostgreSQL driver and jjwt 0.13.0 (`jjwt-api`/`-impl`/`-jackson`, version pinned in `pom.xml`, not managed by Spring Boot; chosen by the human at 2.4a). jjwt only signs and checks our own tokens: **no OAuth or social login (Google, GitHub, ...)**; adding any OAuth dependency needs an explicit task, and `NoSocialLoginTests` fails if one appears.
- Migrations live in `src/main/resources/db/migration` (plain SQL, Flyway, run on startup; files named `V<n>__<snake_case_description>.sql`, one per task row). Hibernate runs with `ddl-auto=validate`, so it never changes the schema. Dev-only seed data lives in `src/main/resources/db/dev-seed` (versions from `V1000`, so they sort after every schema migration), a separate Flyway location that `application.yml` puts on the path only under the `dev` profile (`prod` and the no-profile tests use `db/migration` alone; the `DevSeed*Tests` add the location explicitly via `spring.flyway.locations`). `dev` also sets `spring.flyway.out-of-order: true`, so a schema migration added after the seed (V1000+) still applies to an existing dev database. Dev logins and passwords are documented in the header of `V1000__seed_users.sql`; the seeded course and assignments are in `V1001`, the seeded submissions, results, grades and criterion scores in `V1002`.
- `GET /health` (2.2b) is public and returns `{"status":"UP"}` (200) when a database connection is obtained and valid within 3 s, otherwise `{"status":"DOWN"}` (503); it exposes nothing else. `POST /auth/signup` (2.3b, 2.3c) creates a `STUDENT` (a `role` in the body is ignored) with a BCrypt hash from the single `PasswordEncoder` bean. Emails are trimmed and lower-cased (`AuthService.normalizeEmail`, to be reused by signin in 2.4a); a duplicate is a 409 (`EmailAlreadyUsedException`, found through the unique constraint, not a pre-check); the password must be 8 characters to 72 bytes (`dto/PasswordPolicy`); DTOs that carry a password override `toString` so logs never show it. No Spring Boot Actuator: it would be a new dependency.
- Entities (first one: `entity/User`, 2.3a) map a table with explicit `@Column(name = ...)` for every field, so a renamed Java field cannot silently change a column; `ddl-auto: validate` makes startup fail on any mismatch with the Flyway schema. Enums are stored with `EnumType.STRING`. Columns filled by a database default (such as `created_at`) are `insertable = false, updatable = false` with `@Generated(event = EventType.INSERT)` so Hibernate reads the value back after the insert.
- `POST /auth/signin` (2.4a) returns `{token, tokenType: "Bearer", expiresIn, user}` **in the JSON body only, never a cookie** (the human's decision); the client sends `Authorization: Bearer <token>`. `security/JwtService` signs HS256 tokens (claims: `sub` = user id, `email`, `role`, `iat`, `exp`) valid for `jwt.expiration` (24h). `JWT_SECRET` (bound to `jwt.secret`) is required in every profile: it has no default, must be at least 32 characters, and the app refuses to start without it. For `./mvnw spring-boot:run` put it in `backend/.env`; tests get a throwaway one from the surefire `environmentVariables` in `pom.xml`, so an IDE run of the tests needs `JWT_SECRET` set too. A wrong password and an unknown email both give the same 401 (and cost one BCrypt comparison each).
- `GET /auth/me` (2.4c) returns the signed-in user as `UserResponse`, read from the database by the token's subject (not from the claims, so a changed role shows at once); a token whose user was deleted is a 401 (`AccountNoLongerExistsException`). Controllers get the caller with `@AuthenticationPrincipal AuthenticatedUser`.
- Security chain (2.4b, `security/SecurityConfig`): stateless (no session, no cookie), CSRF off (the token only ever travels in the `Authorization` header), form login, HTTP Basic, logout and request cache off. Public: `GET /health`, `POST /auth/signup`, `POST /auth/signin` and `/error` (must stay: errors are forwarded to it); everything else needs a valid token. `JwtAuthenticationFilter` (not a `@Component`, added by the chain) asks `JwtService.parse` and, if the token verifies, authenticates with an `AuthenticatedUser` principal (id, email, role from the claims alone, no database lookup) and the authority `ROLE_<role>`; a missing or bad token just leaves the request anonymous, so a protected path answers a plain **401** (no body, no redirect, no `WWW-Authenticate`) and public paths ignore a bad token. A wrong role is 403 (see the role convention below). Add new rules to the `authorizeHttpRequests` block. A `@WebMvcTest` that imports `SecurityConfig` needs a `@MockitoBean JwtService`.
- Role convention (2.5a): `@EnableMethodSecurity` is on `SecurityConfig`, and the role rule of an endpoint is a `@PreAuthorize` on its **controller method** (never on the class, never as a URL matcher by role), e.g. `@PreAuthorize("hasRole('ADMIN')")` or `@PreAuthorize("hasAnyRole('TEACHER', 'ADMIN')")`. Roles are listed explicitly: there is no role hierarchy, so `ADMIN` does not imply `TEACHER` (write `hasAnyRole('TEACHER', 'ADMIN')` where the row says "teacher or admin"). No annotation means any signed-in user. Anonymous is 401, signed in with the wrong role is 403 (no body, no challenge). The role comes from the token, so a promotion applies after the next signin (2.4b). Role checks alone do not protect course data; ownership checks come in 3.1c. `PreAuthorizeConventionTests` fails on a role name that is not a `Role` (a typo such as `hasRole('TEACHR')` would silently lock everyone out) or a class-level rule; `RealHttpRoleSecurityTests` has the pattern for testing a role rule over real HTTP (a probe controller nested in the test class).
- CORS (2.4d, `config/CorsConfig` + `config/CorsProperties`): the allowed origins come from the comma-separated `CORS_ALLOWED_ORIGINS` (bound to `cors.allowed-origins`, no default in `application.yml`; unset or empty = no cross-origin call allowed). Entries must be plain `http(s)://host[:port]` origins: a wildcard, a path or a trailing slash stops startup. Credentials are off (the token is a header, never a cookie, 2.4a); methods `GET POST PUT PATCH DELETE OPTIONS`, headers `Authorization Content-Type Accept`, preflight cached 1h. `SecurityConfig` enables it with `http.cors(...)` so a preflight (which carries no token) is answered before authentication; a request from any other origin is a 403. A new header the frontend must send has to be added to the allowed list in `CorsConfig`.
- `MockMvc` does not perform the container's error dispatch to `/error`, so it cannot see a security rule turning an error status into 403. `RealHttpAuthTests` and `RealHttpJwtFilterTests` (a real server on a random port) covers the statuses that matter to clients; add a real-HTTP check for any new endpoint whose error statuses are part of its contract.
- Schema conventions (set in 1.2a, reuse in every later migration): `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`, enum-like values (e.g. `role`) are plain `VARCHAR` validated in the application layer, no DB `CHECK`; foreign keys get an explicit `idx_<table>_<column>` index (Postgres does not create one) unless the column is already the leading column of the primary key or a unique constraint. Migration tests (`*MigrationTests`) run against Testcontainers inside a `@Transactional` test; Postgres aborts the transaction on the first constraint error, so use one test per violation.
- The `SPRING_DATASOURCE_*` environment variables bind directly to `spring.datasource.*` and always override the file. Outside the `dev` fallbacks they have no default, so the app fails at startup if they are missing (the `prod` case). Tests never use them.
- Configuration comes from environment variables listed in `backend/.env.example` (datasource, `JWT_SECRET`, `AI_SERVICE_URL`, `AI_SERVICE_TOKEN`, `CORS_ALLOWED_ORIGINS`). Never commit `backend/.env`, and never log secrets.

## Conventions
- Packages are organised **by layer** under the base package (2.1b, chosen by the human): `controller`, `service`, `repository`, `entity` (JPA entities and their enums), `dto` (request/response objects; entities are never returned from the API), `config`, `security`, plus `sandbox` (Phase 4) and `ai` (Phase 7). Each has a `package-info.java` saying what belongs there; put new classes in the matching package and add a new top-level package only through a task. No other naming convention exists yet — each is decided by the task that introduces the first class of its kind (a choice with no default in any `*.md` file is a gate).
- Backend-relevant rules fixed in the root `CLAUDE.md` Defaults: schema changes only through Flyway; Spring Security + JWT, no OAuth; student code runs only in a sandbox container started through a `SandboxRunner` interface (`docker` CLI via `ProcessBuilder`); calls to the AI service are never made inside an open database transaction and never decide the grade.
- Spotless owns formatting: don't hand-format or fight it — run `spotless:apply`.
- Tests are part of the commit that adds the code, and all tests of all three projects must pass before a task counts as finished (root `CLAUDE.md`, Workflow).
- Tests get their database only from Testcontainers (`postgres:16`, matching `infra/docker-compose.yml`) — never the compose database or a CI service container. A `@SpringBootTest` imports `TestcontainersConfiguration` (`@ServiceConnection`); see `FlywayMigrationTests` for the pattern. This is a small first version; 2.7a turns it into the shared test base.
- Docker must be running for the backend tests (Testcontainers) and for the sandbox tests (from Phase 4). On Windows start Docker Desktop first, or `./mvnw verify` fails before running any test.
