## 3.1a — `POST /courses`

- **Teachers only, admins excluded.** The row says "(teacher)" and there is no role hierarchy (2.5a), so the rule is `hasRole('TEACHER')`, not `hasAnyRole('TEACHER', 'ADMIN')`. Later rows say "owning teacher or admin" where they mean both. An admin who needs a course promotes or uses a teacher account; if the human wants admins to create courses it is a one-word change plus a flipped matrix row.
- **Code: 8 symbols from a 32-symbol alphabet, upper case, `SecureRandom`.** The alphabet is `A–Z` without `I` and `O`, plus `2–9`, so none of `0/O`, `1/l/I` can appear and lower case is not needed. 32^8 = 2^40 codes. `SecureRandom` rather than `Random` because the code is the only thing between a student and a course; unlike the placeholders elsewhere this length is mine, not the human's, and `EnrollCodeGenerator.LENGTH` / `ALPHABET` are named constants (the column allows 20). **For 3.2a:** upper-case what the student typed before the lookup, and a code is never stored in any other case.
- **The unique constraint decides, same as for the email (2.3c).** No `existsByEnrollCode` before the insert: it would not hold for two simultaneous creations. `CourseService.create` catches the violation of `courses_enroll_code_key` and draws another code, at most 5 times (`MAX_CODE_ATTEMPTS`), then throws `IllegalStateException` (a generic 500, cause in the log). Five is only a guard against a loop that can never end; at 2^-40 per existing course a second attempt is already vanishingly rare.
- **`create` is deliberately not `@Transactional`.** Postgres aborts a transaction at its first constraint error, so a retry inside the same transaction would fail every time. Each attempt is `saveAndFlush`'s own transaction. If a later row makes course creation write a second table, the retry must stay outside the transaction that writes it.
- **A teacher whose account was deleted is a 401, not a 500.** The token outlives its user (claims-only tokens, 2.4b), and `courses.teacher_id` is a foreign key, so the insert fails with `courses_teacher_id_fkey`. It is translated to `AccountNoLongerExistsException` (`ACCOUNT_NO_LONGER_EXISTS`), the same answer `/auth/me` gives. Any other integrity violation is rethrown untouched, so it cannot be mistaken for either case. The constraint names are Postgres's defaults for V2's inline `UNIQUE` / `REFERENCES`; `theConstraintNamesWeLookForAreTheOnesPostgresReports` fails if they ever differ.
- **`Constraints.isViolationOf`** replaces the private `violatesEmailUniqueness` in `AuthService` (same cause-chain walk, now shared). Behaviour of signup is unchanged; its tests passed untouched.
- **Request/response.** `CourseRequest {title, description}` (named for reuse by `PUT /courses/{id}` in 3.1d); no `teacherId`, `enrollCode`, `id` or `createdAt` field, so a client cannot choose the owner or the code (unknown JSON properties are ignored, as at signup; tested with six such keys). Title is trimmed and required (≤ 255, the column); a blank description is stored as `null`. **Description cap of 5000 characters is my placeholder** (`CourseRequest.DESCRIPTION_MAX`): the column is `TEXT`, and an uncapped body would let one request store megabytes. Flagged in the PR for the human to keep or change. Response is `201` with `CourseResponse {id, title, description, teacherId, enrollCode, createdAt}`; no `Location` header (signup has none either).
- **`CourseResponse` carries the enrollment code, which is right for the owner only.** Anyone holding the code can join, so 3.1b/3.1c must decide what a student sees of a course (probably the same record without `enrollCode`). Noted in the class's Javadoc so the next row does not reuse it unchanged.
- **Test infrastructure.** `RealHttpTestBase` now also autowires `CourseRepository` and clears `courses` before `users` in its before/after hook (a course references its teacher, so `users.deleteAll()` alone would fail); its method is renamed `emptyTables`. Each later phase adds its tables to that hook, referencing tables first. `TestcontainersConfiguration` became `public` so a test outside the root test package (`CourseServiceTests`, in `service`, which needs the package-private constraint constants) can import it.
- **Role matrix.** `POST /courses` is a row of `RoleMatrixIntegrationTests`. Unlike the earlier rows, a teacher who passes there really creates a course (a `POST` has no id that can point at nothing); the base class empties `courses` after each test, and the row carries a comment saying so.
- **Side effect on an existing test (found by the full run):** `RealHttpJwtFilterTests` (2.4b) used `/courses` as its "protected path with no handler" and expected 404 from an authenticated caller; five of its tests failed (405 and 400 now) as soon as the path got a handler. Its stand-in is now `/no-handler-is-ever-mapped-here`, which no phase will map, so later phases cannot break it the same way. Nothing else in the suite relied on `/courses` being unmapped.
- **Tests (+44, backend 480 → 524; ai-service and frontend unchanged and passing):** `RealHttpCourseCreateTests` (real server: 201 and the stored row, optional/blank description, trimmed title, limits, non-ASCII round trip, owner and code cannot be chosen, 40 distinct codes, six missing/blank-title bodies, over-long title/description, malformed bodies, student/admin/anonymous/bad token refused with nothing saved, deleted teacher 401, promoted student can create after signing in again, other methods 405), `CourseServiceTests` (real schema, scripted generator: collision retried, five-in-a-row, endless collision stops, deleted teacher, another violation not mistaken for a collision, constraint names), `EnrollCodeGeneratorTests` (alphabet, length, all symbols used, no repeats in 20,000), 5 more matrix checks.
- **Known and not changed:** a teacher demoted to student keeps the right to create courses until their token expires (24h, 2.4b/2.5b), like every role-gated endpoint.

## 3.1b — `GET /courses`

- **One endpoint, the role picks the query; nothing in the request can change it.** Teacher: `teacher_id = caller`. Student: courses with an `enrollments` row for the caller. Admin: all. The role is the token's (2.4b), so a promotion or demotion applies after the next signin, as everywhere. A teacher who is also enrolled somewhere (possible after a promotion) sees only what they own; a test pins it. Extra parameters such as `?studentId=` are ignored (tested), so there is no way to ask for someone else's list. No `@PreAuthorize`: all three roles are allowed, so the matrix row is "any signed-in user".
- **Paginated, which the row did not say.** The row only says "role-aware list". "Admin sees all" grows without bound, and 2.5c fixed one envelope for every list (`PageResponse`, `?page&size`, default 20, max 100), so the list uses it for all three roles, ordered by id (stable, pages never overlap). A client that wanted "all my courses" in one call must now page; with the default size of 20 a teacher with more than 20 courses sees that. Say if you would rather have an unpaginated list for teachers and students.
- **Who sees the enrollment code (my call; 3.1a had flagged it).** Teachers (their own) and admins get `enrollCode`; **students never do, not even for courses they are in**: the code is the join secret, and a student who holds it can hand it on, which is the teacher's decision. For a student the key is absent from the JSON, not `null`, so there is nothing to forget to hide. `@JsonInclude(NON_NULL)` is on that one record component only, because a class-level rule would also drop a `null` description, which the 3.1a tests (and a client) expect to be present. `CourseResponse.forRole` is the single decision point and 3.1c must use it. Admin getting the code is the less obvious half: an admin can see and change every course anyway, so withholding it would protect nothing.
- **`Enrollment` entity now.** The student case needs to read `enrollments`, and 3.2a (join) will write it, so the entity and `EnrollmentRepository` are added here, mapped with an `@Embeddable` record `EnrollmentId(courseId, studentId)` as `@EmbeddedId` (the table's composite primary key). Nothing writes enrollments yet except the tests. `enrolled_at` is read back like `created_at`.
- **Query:** `findEnrolledBy` is `c.id in (select e.id.courseId from Enrollment e where e.id.studentId = :studentId)` rather than a join, so a course can never appear twice and the page's `totalElements` is right; a test enrolls six students in one course and checks it appears once with total 1. The `idx_enrollments_student_id` index from V3 serves the subquery.
- **`listVisibleTo` is `@Transactional(readOnly = true)`**, the first transactional method of `CourseService`; `create` stays deliberately without one (3.1a).
- **Test infrastructure:** `RealHttpTestBase` also clears `enrollments` (first, they reference courses and users) and exposes `enrollments`.
- **Tests (+25, backend 524 → 549; ai-service and frontend unchanged and passing):** `RealHttpCourseListTests` (teacher own with codes, empty page, teacher-enrolled-elsewhere, student enrolled only, no enrollments, one course with many students appears once, student JSON has no `enrollCode` key and not the code anywhere in the body, foreign parameters ignored, admin all with codes, 25 courses over three pages in order without gaps, totals of a teacher's list, default size and page past the end, six bad paging parameters, anonymous/bad token 401, joining does not leak to a classmate) and one more row in the role matrix (5 checks). The 3.1a test that said GET arrived in 3.1b was renamed to what it checks (PUT/DELETE on the collection are 405).

## 3.1c — `GET /courses/{id}` and `CourseAccess`

- **Not visible = not found (404), not 403 — my call, flagged in the PR.** The row says "with an access check" and nothing fixes the status. A 403 for a course that exists but is not yours would let any signed-in user walk the ids and learn which courses exist; 3.2a already argues the same for enrollment codes ("404, not 403, so codes can't be probed by error type"). So a missing course and a hidden one give the identical answer: status, `COURSE_NOT_FOUND` code, message, body bytes and header names (tested by comparing the two responses). The cost: a teacher who types the wrong id for someone else's course is told it does not exist, not that it is not theirs. A new `ErrorCode.COURSE_NOT_FOUND` (not the generic `NOT_FOUND`) lets the frontend say "course not found" specifically.
- **The reusable place the row asks for is `service/CourseAccess`.** `canView(userId, role, course)` and `requireViewable(userId, role, courseId)`; teacher = owns it, student = has an `enrollments` row (`existsById` on the composite key), admin = any. The role is the token's, as in the list. Nothing else may restate the rule. Later phases (assignments 3.3b, submissions) add methods to it (or a sibling in the same style) and call `requireViewable` first. I did not add `canManage` (owner or admin, for 3.1d) now: what a non-owner gets on a write (404 or 403) is 3.1d's call and is better decided with the endpoint in front of me.
- **The rule exists twice, so a test ties the two together.** `listVisibleTo` (3.1b) is the same rule as a query; `CourseAccessTests.theListAndTheSingleCourseCheckAgreeForEveryUserAndCourse` runs both for every user and course of a mixed world and fails on any disagreement. Mutation-checked: making teachers able to view every course fails five tests (the two role tests in the service, the consistency test, and two over HTTP).
- **Response:** `CourseResponse.forRole`, so a student gets no `enrollCode` key (3.1b); the owning teacher and an admin do.
- **Path id:** a non-number or an id beyond `long` is a 400 `MALFORMED_REQUEST` (Spring's type mismatch); `0` and negatives are a plain 404.
- **`CourseService` gained a third constructor argument (`CourseAccess`)** and a thin `getVisibleTo`; `CourseServiceTests` builds the service by hand, so it passes a real `CourseAccess`.
- **Tests (+26, backend 549 → 575; ai-service and frontend unchanged and passing):** `RealHttpCourseGetTests` (owner/admin with code, enrolled student without the key, other teacher and non-enrolled student 404, enrollment elsewhere gives nothing, an enrolled teacher gets nothing, access follows an enrollment at once, hidden = missing byte for byte, missing for every role, `0`/`-1`, three non-numeric ids, anonymous and bad token 401, PUT/DELETE 405 until 3.1d), `CourseAccessTests` (4), and one more row in the role matrix (5 checks).

## 3.1d — `PUT` and `DELETE /courses/{id}`

- **Status convention for writes, consistent with 3.1c (my call, flagged in the PR):** a caller who cannot *see* the course gets the same 404 `COURSE_NOT_FOUND` as for a missing id; a caller who can see it but may not change it gets 403 `ACCESS_DENIED`. In practice: another teacher → 404; a student (enrolled or not) → 403, and that one is the `@PreAuthorize("hasAnyRole('TEACHER', 'ADMIN')")` role rule firing before any lookup, so a non-enrolled student learns nothing about the id either. `CourseAccess.requireManageable` still implements the full rule (404, then 403) so it stays right if a role ever gets more rights; `AccessRefusedException` is the generic 403 for "visible but not allowed". `canManage` ⊆ `canView` is tested over every user/course pair, otherwise a 403 could reveal a course someone should get a 404 for.
- **`PUT` is a full replace of two fields.** Same `CourseRequest` and limits as create, so an omitted description clears it (tested), the title is trimmed, and `teacherId`/`enrollCode`/`id` in the body are ignored. The owner is never reassigned, not even by an admin (an admin editing a course leaves its teacher as it was). The enrollment code cannot be regenerated; if the human wants "rotate code" it is a task of its own. No optimistic locking: two simultaneous edits, last one wins.
- **`DELETE` removes the course's enrollments with it, and refuses while assignments exist.** The row only forbids cascading over assignments/submissions. Enrollments are membership with no student work attached, and the foreign key would otherwise make every course with a student undeletable, so they go (`EnrollmentRepository.deleteByCourseId`, a bulk delete). Everything runs in one transaction.
- **Assignments are refused by the foreign key, not by a lookup.** There is no `Assignment` entity until 3.3a, and a check-then-delete would race with an assignment being created at that moment. `courses.delete` + `flush` raises the violation of `assignments_course_id_fkey` (the constraint name is checked, like the others in 3.1a), which becomes 409 `COURSE_HAS_ASSIGNMENTS` with the message "The course has assignments and cannot be deleted; delete its assignments first". The exception makes the transaction roll back, so **the enrollments deleted a moment earlier come back**; `theRefusalLeavesEverythingAsItWasEnrollmentsIncluded` pins it. Once 3.3c lets a teacher delete an assignment (blocked when it has submissions), the message's advice becomes workable.
- **A refused delete is also what an admin gets**; there is no force flag. Deleting submissions is out of scope for v1.
- **`204` with an empty body** on success; a second delete is a 404 (the course is gone), not an idempotent 204.
- **Test infrastructure:** `RealHttpTestBase.emptyTables` now also runs `DELETE FROM assignments` through `JdbcTemplate` first (no entity or repository until 3.3a; replace the line with the repository then), and exposes `jdbc`. Tests insert an assignment with plain SQL for the same reason. `CourseServiceTests` builds the service by hand, so it now passes the enrollment repository too.
- **Tests (+42, backend 575 → 617; ai-service and frontend unchanged and passing):** `RealHttpCourseChangeTests` (PUT: owner, replace semantics, trim, admin, owner/code in the body ignored, other teacher 404, students 403, anonymous/bad token, missing course, four invalid bodies, limits, student still has no code; DELETE: owner, enrollments removed and only that course's, admin, other teacher 404, students 403, anonymous, twice, missing, non-numeric; assignments: refused with the message, rollback leaves enrollments and assignment, admin refused too, only the course with assignments is blocked, deletable once they are gone, still editable), three `CourseAccessTests` (manage table, manage ⊆ view, 404-vs-403), and two more rows in the role matrix (10 checks). The 405 tests for PUT/DELETE on `/courses/{id}` written in 3.1c were removed now that the methods exist; the ones on the collection `/courses` stay.

## 3.2a — `POST /courses/enroll`

- **Students only (`hasRole('STUDENT')`).** The row says "student joins". A teacher or admin gets 403 whatever the code, so the endpoint cannot be used by them to test codes (tested with a right and a wrong code). A teacher's own course needs no enrollment, and the list/read rules treat the owner separately (3.1b/3.1c).
- **Unknown code is 404 `ENROLL_CODE_NOT_FOUND`, a code of its own rather than `COURSE_NOT_FOUND`.** The row fixes 404 (not 403). A separate code lets the frontend say "check the code" instead of "course not found", and leaks nothing, since "no course has this code" is the only reason the endpoint ever gives. Every unknown or near-miss code gets the identical body (tested). A code longer than the column (20) cannot match and is a 400 `VALIDATION_FAILED` (its value is not echoed).
- **What counts as the same code:** `EnrollCodeGenerator.normalize` = trim + `toUpperCase(Locale.ROOT)` (a Turkish default locale cannot change it; tested), nothing more. No aliasing of `0`/`O` or `1`/`l`: codes never contain those, so a code that does is simply wrong. 3.1a's note ("upper-case what the student typed") is now implemented.
- **Idempotent through the primary key, in one statement.** `INSERT ... ON CONFLICT DO NOTHING` (native `@Modifying` query) instead of the entity `save` or a check-then-insert: `save` on a composite key does a select-then-insert that two simultaneous requests can both lose, and a plain insert violating the key would also abort the surrounding Postgres transaction. Eight simultaneous joins by one student (three rounds) all get 200 and leave one row; six students joining at once all get in. Mutation-checked: without `ON CONFLICT`, three tests fail (twice-join, another spelling, the simultaneous joins). The insert returns the row count (1 new, 0 already there); the service ignores it, since both are the same answer.
- **Answer: 200 with the course as a student sees it, for a first and a repeated join alike** (not 201/200): the row says repeating is "not an error", and one status means a client cannot tell a first join from a retry, which it has no need to. No enrollment code in the body: the student already holds it, but the teacher decides who passes it on (3.1b).
- **A deleted student is 401 `ACCOUNT_NO_LONGER_EXISTS`** (FK `enrollments_student_id_fkey`), as in 3.1a; a course deleted between the lookup and the insert (FK `enrollments_course_id_fkey`) is reported as an unknown code. Both constraint names are checked against real Postgres in `CourseServiceTests`.
- **`GET /courses/enroll` is a 400, not a 404:** it matches `GET /courses/{id}` with a non-numeric id. Harmless; a test pins it so nobody is surprised by it.
- **Not done: no rate limit on guessing codes.** 2^40 possible codes make blind guessing impractical, but a signed-in student can try as fast as the server answers. Same family as the signin suggestion from 2.4a; added to `docs/suggestions.md`.
- **Tests (+48, backend 617 → 665; ai-service and frontend unchanged and passing):** `RealHttpEnrollTests` (join and the student view of the course, in list and readable afterwards, five spellings, several students, other courses untouched, twice, another spelling, 8 simultaneous joins × 3 rounds, 6 students at once, unknown code, seven near-misses, identical answers, deleted course's code, a failed attempt changes nothing, four missing/blank bodies, over-long code, four malformed bodies, code hidden in `toString`, teacher/admin 403 with right and wrong code, anonymous/bad token, deleted student, `GET /courses/enroll`), five `EnrollCodeGeneratorTests` (`normalize`), one `CourseServiceTests` (constraint names), and one more matrix row (5 checks).

## 3.2b — leave a course, list a course's students

- **Leaving: one `DELETE`, 0 rows = 404 `COURSE_NOT_FOUND`.** No lookup beforehand, so there is no check-then-act gap. A student who was never in the course, a course that does not exist and a second leave all get the same 404 (tested byte for byte), which is the existing "cannot see it" answer (3.1c). An idempotent 204 on a repeat would be the opposite of 3.1d's delete-twice behaviour.
- **Leaving is students only (`hasRole('STUDENT')`).** The row says "student leaves"; teachers and admins get 403. A teacher removing a student is not in the phase, so it is not built.
- **Past submissions stay by construction.** `submissions` references `assignments` and `users`, never `enrollments`, so deleting the enrollment cannot touch them; `leavingKeepsWhatTheStudentSubmitted` inserts a real submission and checks it. Re-joining with the code brings access back (tested). What a left student may still see of their own old submissions is for the submission endpoints (Phase 5) to decide.
- **The roster is open to the owning teacher and to admins** (the row says "teacher"). Same rule and statuses as 3.1d's writes via `CourseAccess.requireManageable`: another teacher gets the 404 of a course they cannot see, a student gets 403 by role even if enrolled. Admin access follows the project-wide pattern (admin sees everything); say if it should be teacher-only.
- **Row shape `{id, email, fullName}`.** Enough to tell students apart; no role (always `STUDENT`), no hash, no `enrolledAt` (not asked for; easy to add). Student id order, so pages are stable. A new DTO rather than `UserSummaryResponse`, which is the admin list's shape and carries the role.
- **Tests (+35, backend 665 -> 700; ai-service and frontend unchanged and passing):** `RealHttpCourseLeaveTests` (10), `RealHttpCourseStudentsTests` (15), and two more role-matrix rows (10 checks).

## 3.3a — `POST /courses/{id}/assignments`

- **Gate resolved by the human: temporary allow-list for the language.** The row says to validate against the languages config, which only arrives with 4.1b. Chosen: `assignments.languages` (`JAVA`, `PYTHON`) in `application.yml`, bound by `AssignmentProperties`, so no language is named in code. 4.1b's row now says to make the real config the source and delete the stand-in. An empty list stops startup.
- **Identifiers are upper-case and typed values are normalised** (trim + `toUpperCase(Locale.ROOT)`, tested under a Turkish locale), matching the `JAVA`/`PYTHON` the migrations and dev seed already use (decisions-phase-01). `python` is accepted and stored as `PYTHON`.
- **Teachers only, admin excluded**, like `POST /courses`: the row says "owning teacher". Access check first (`requireManageable`): another teacher gets the 404 of a course they cannot see even with an invalid body (tested).
- **Two new error codes instead of a field error:** `UNSUPPORTED_LANGUAGE` and `DEADLINE_NOT_IN_FUTURE` (both 400). They depend on configuration and the clock, so Bean Validation cannot express them (`@Future` would use the system clock, not the injected `Clock`); the frontend can tell them apart by `code`.
- **Time and memory limits are required, with no defaults.** The spec lists them as the teacher's choice and the columns are `NOT NULL`; a default would be a value nobody chose. Easy to relax if you want defaults.
- **Placeholder maxima, for the human to set:** description 20000 chars, starter code 50000, attempts 1-100, time 1-10000 ms, memory 1-1024 MB (named constants in `AssignmentRequest`). The minimum for time and memory is 1: a limit too low for the language just fails the teacher's own reference run.
- **`updated_at` is only DB-defaulted for now** (`insertable = false, updatable = false`); 3.3c, the first update, makes the application maintain it (V4's comment).
- **Deadline boundary:** exactly "now" is refused, one millisecond later is accepted (`AssignmentServiceTests`, fixed clock). The race where the course is deleted after the access check is mapped from the foreign key to a 404 (name checked against real Postgres).
- **Tests (+62, backend 700 -> 762; ai-service and frontend unchanged and passing):** `RealHttpAssignmentCreateTests` (create and stored values, optional fields, language spellings, ignored body fields, maxima, unsupported languages, past deadlines, missing/blank/over-long/out-of-range fields, malformed bodies, other teacher / student / admin / anonymous, course undeletable afterwards), `AssignmentServiceTests` (4), `AssignmentPropertiesTests` (5), one more matrix row (5 checks).
