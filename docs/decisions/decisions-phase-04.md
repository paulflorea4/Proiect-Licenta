## 4.1a — `SandboxRunner` interface and types

- **Shape: one call, `SandboxResult run(SandboxRequest)`.** The row names exactly these inputs and outputs. 4.6a needs "compile once, run each test in its own container" with the compiled output surviving between containers; that may require a second method (e.g. a prepared workspace) on this interface. Deliberately not guessed now: 4.3a/4.6a extend the interface when the Docker plumbing shows what it needs, and the single-call form stays valid for a runner that does both steps itself.
- **A sixth status, `SANDBOX_ERROR`, beyond the five the later rows name** (`OK`, `COMPILE_ERROR`, `RUNTIME_ERROR`, `TIMEOUT`, `MEMORY_LIMIT`). Docker being down or an image missing is not the student's fault and must not be reported as a runtime error or become a zero grade. Phase 5 can map it to the submission's `ERROR` status. Cheap to add now, awkward to add after callers `switch` over the enum.
- **Result carries `stdoutTruncated` / `stderrTruncated` already** (the row for the cap is 4.3c). 4.3c says truncated output must be marked so the comparison cannot pass on a prefix; putting the flags in the type now means 4.3c changes no signature. `completedCleanly()` is the one check Phase 5 should use before comparing stdout (it looks at stdout only: a cut stderr does not affect the comparison).
- **`OK` requires exit code 0** (enforced in the record). Other statuses may carry any exit code or none (a timeout and a compile error have no program exit code).
- **Limits are only the two per-assignment values** (`timeLimitMs`, `memoryLimitMb`), both required positive, with no "unlimited". CPU, PID and output limits are fixed in the runner (4.3), not negotiable by a caller. No upper bound is enforced in the type: the assignment's own maxima (`AssignmentRequest`) apply on the way in, and the runner may only tighten.
- **`SourceFile` names must be plain file names** (no `/`, `\`, `:`, control characters, `.`/`..`, trailing dot or space), and a request refuses two names that differ only by case. The names will come from the languages config (4.1b), not from students, so this is defence in depth for the bind-mounted working directory (4.3a), where a name like `../x` would write outside it, and a Windows host would otherwise fold `A.java` and `a.java` into one file.
- **`toString` of request, result and source file shows lengths, never content**, as `EnrollRequest` does for the code: student code, hidden-test input and program output must not reach a log line.
- **`language` is a free string here** (non-blank), not an enum and not checked against a list: the languages config (4.1b) is the single source of what exists, and adding a language must not touch Java code.
- **Tests (+36, backend 1435 -> 1471; ai-service and frontend unchanged and passing):** `SandboxTypesTests`. Docker Desktop was not running at the start of the session and was started from its user-level install (`%LOCALAPPDATA%\Programs\DockerDesktop`) for the Testcontainers tests.

## 4.1b — Languages config and loader

- **Where the file is: `sandbox.languages` in `application.yml`.** The row says "config file". `application.yml` is already documented as the only config file (backend `CLAUDE.md`), it is what 3.3a's stand-in used, and Spring's relaxed binding lets an environment variable override one value (e.g. an image tag) without a second file or a new parser. A separate YAML/JSON file would have needed its own loader and path configuration. If the human prefers a standalone file, only `SandboxProperties`' source changes.
- **Replaced, not wrapped, the 3.3a stand-in.** `AssignmentProperties`, `AssignmentConfig` and `assignments.languages` are deleted; `AssignmentService` asks `SandboxProperties.supports` (same method names, so the service diff is the type only). `AssignmentPropertiesTests` moved into `SandboxPropertiesTests` (its normalisation, locale and empty-list cases kept). The Turkish-locale case still holds.
- **Commands are lists, not strings** (`compile-command: [javac, -encoding, UTF-8, Main.java]`), so the runner (4.3a) passes each element as one argument and no shell ever parses them (4.3a's rule). A command element may not be blank.
- **Java: `Main.java`, `javac -encoding UTF-8 Main.java`, then `java -cp . Main`.** The file/class name `Main` is the convention 4.4b must document for teachers and students. `-encoding UTF-8` so non-ASCII source does not depend on the container's locale. No `-Xmx` in the run command: the container's memory limit is the limit, and the JVM sizes its heap from it. Python: `python main.py` (the image decides which interpreter `python` is). Both are provisional until 4.2b builds the images.
- **Image names `grading-sandbox-java:dev` / `grading-sandbox-python:dev` are placeholders** (as the row says) until the 4.2a gate. Validation refuses an image that starts with `-` or contains whitespace, because 4.3a puts it on a `docker run` command line and a leading `-` would be read as an option.
- **Source file name is validated with the same rule as `SourceFile`** (plain file name), so a typo in the config cannot point outside the working directory.
- **The map binder lower-cases the YAML keys** (`JAVA` arrives as `java`); `SandboxProperties` normalises every key to upper case anyway, and rejects two keys that normalise to one id. A missing or misspelled property in an entry (the first run of this commit failed with `source-file` instead of `source-file-name`) stops the application at startup with the reason, rather than leaving a language half-configured.
- **"No code branch" is guarded by a test, not just a promise:** `NoLanguageBranchTests` scans `src/main/java` for a language name in a string literal. It is a heuristic (it cannot see an enum), which is why `RealHttpNewLanguageTests` also proves the positive claim: a `RUST` entry given only as properties is accepted end to end.

## 4.2b — Runner images

- **Two Dockerfiles, one per language, in `infra/sandbox/<lower-case id>/`.** The test locates the Dockerfile from the language id, so a new language's image directory follows the id with no extra mapping. Built locally under the tags already in `application.yml`; nothing is published.
- **A fixed non-root user `10001:10001`, created in the image,** with no home directory and no login shell. A numeric id so the runner can pass `--user 10001:10001` and prepare the host working directory for exactly that id (4.3a, the bind-mount ownership question the row flags for Windows/Docker Desktop is still open until then). `/work` is created and owned by that user; it is the `WORKDIR`, so the runner's bind mount lands there.
- **"No extra tooling":** the base images were inspected before writing anything. `eclipse-temurin:17-jdk-jammy` ships `curl` and `wget` (purged, with `apt` lists), `python:3.12-slim` ships `pip` (uninstalled). `apt-get` itself stays in both (it is part of the base and unusable without root). A check on the raw base images reproduces the finding (Java: `curl wget`; Python: `pip pip3`), so `SandboxImagesTests.noDownloadToolsOrPackageInstallersAreShipped` fails if a future change brings them back. This is defence in depth: the network is off at run time (4.3a) and the root filesystem is read-only, so the tools could not do much anyway.
- **Python: `PYTHONDONTWRITEBYTECODE=1`, `PYTHONUNBUFFERED=1`.** No `.pyc` files written next to the submission; unbuffered so output printed before a timeout kill is not lost in a buffer (4.3b will report `TIMEOUT` with whatever was printed).
- **The images carry no restrictions on purpose.** Network, read-only root, capabilities, limits and `no-new-privileges` are `docker run` flags in 4.3a, where each must be asserted by a test. Putting any of them in the image would give a false sense that the image is the sandbox.

They go through a new test helper `DockerCli` (argument lists, output via temp files so a chatty command cannot block on a full pipe, timeout that kills the process); 4.7a's hostile-program tests reuse it.
- **Windows gotcha, documented in `backend/CLAUDE.md`:** a double quote inside a `sh -c` argument is mangled between `ProcessBuilder` and `docker.exe` (the first run failed with `Syntax error: end of file unexpected`). Scripts use single quotes only. This will matter again in 4.3a (any argument that could hold a quote) and is why that row insists on list arguments.
- **`command -v` exit status differs by shell** (127 for a missing command in the image's `sh`), so the tool check prints the names that exist and asserts the output is empty rather than testing an exit code.

## 4.3a — `DockerCliSandboxRunner`

- **Bind mounts work on this Windows/Docker Desktop host, so `docker cp` is not needed** (the row asked to check early and record it). Checked by hand before designing: a `--mount type=bind,source=C:\...,target=/work,readonly` directory is readable by uid 10001, a write to it fails with "Read-only file system", and a read-write mount lets uid 10001 create files that the host sees. The mounted file shows as `rwxrwxrwx root` inside the container, so host permissions play no part on Docker Desktop. On a Linux host (CI, deployment) they do: the run directory is made `rwxrwxrwx` so the container's user can write it in the compile step, the work root `rwx------` so no other host user can reach it. That path is only exercised by CI; a test asserts the permissions on POSIX hosts and is skipped here. `--mount` rather than `-v` because a Windows path contains a colon; a comma in the path would end the `--mount` value, so the work root may not contain one.
- **Git Bash rewrites `/work` into `C:/Program Files/Git/work` in manual `docker` probes** (an MSYS path conversion; `ProcessBuilder` does not do it). Only matters when trying commands by hand: set `MSYS_NO_PATHCONV=1`.
- **`DockerRunArguments` holds every restriction as one list-building function and named constants** so a change is one diff and one test. Placeholders, not the human's numbers: `CPUS = 1`, `PIDS_LIMIT = 128`, tmpfs `size=64m` (flagged for tuning; Java's thread count is checked in 4.4b and the fork bomb in 4.7a). Memory comes from the assignment; swap equals memory.
- **`--pull never`:** a missing image must be a `SANDBOX_ERROR`, not a silent download at grading time. `--interactive` only for stdin; no `--tty`, `--env`, `--publish`, `--privileged`, devices or shared namespaces (a unit test lists what must never appear).
- **The exit code comes from `docker inspect`, not from `docker run`'s own exit status.** `docker run` returns 125/126/127 for its own failures, and a program can return those too; the container's recorded `State.ExitCode` is unambiguous, and "no such container" means the sandbox failed (typically a missing image). 4.5a will add `OOMKilled` and the kill cases from the same inspect.
- **Container removed in a `finally` with `docker rm --force`, not `--rm`,** as row 4.3d explains; 4.3a already does the removal (a runner that leaks containers is not usable even in its first form) and a test counts labelled containers before and after, for success, failure and a missing image. What 4.3d still adds: the directory removal on every path including a killed run, and the leftover test against timeouts.
- **A safety net, not the time limit:** `SAFETY_CEILING` (10 minutes) bounds any run so a test or a bug cannot hang forever; the assignment's time limit, the `docker kill` and the `TIMEOUT` status are 4.3b. Until then **the runner must not be wired to anything that takes a student's code**; written in the class Javadoc and in `backend/CLAUDE.md`.
- **Stdin is written from a separate thread.** Writing on the calling thread blocks once the pipe is full if the program never reads its input, and then the timeout is never reached. Found while writing the "never reads its input" test (200 KB stdin).
- **Compiled languages return `SANDBOX_ERROR` for now** ("compile step not supported until 4.4b") rather than running `java -cp . Main` on source and reporting a misleading runtime error. The container-running method already takes a `writable` flag for the compile step.
- **`SANDBOX_ERROR` carries a fixed message; Docker's own text (which can include host paths and image names) goes to the log.** The result is never shown to a student anyway; Phase 5 maps it to the submission's `ERROR`.
- **Runtime is measured around `docker run`,** so it includes container start-up (a few hundred ms); it is not a CPU-time measurement and is not used for grading.
- **Tests (+38, backend 1507 -> 1545; ai-service and frontend unchanged and passing):** `DockerRunArgumentsTests` (11, no Docker), `SandboxFlagsTests` (9: each restriction read back from a created container with `docker inspect`), `DockerCliSandboxRunnerTests` (18 incl. one POSIX-only: stdin and output, unicode, several files, exit codes and tracebacks, user/cwd, read-only `/work` and `/etc` but writable `/tmp`, no network, read-write compile mount seen by the host, unconfigured language, compiled language, missing image, no leftovers). **Mutation-checked:** network `bridge`, swap = 2 x memory and `--cap-drop NET_RAW` produced 7 failures across the three classes (including the real "connected" behaviour test); code restored. Also: `SandboxImagesTests` now shares `SandboxTestImages` (build once per run) and `DockerCli` delegates to the runner's own `DockerCommand`.

## 4.3b — Wall-clock timeout

- **The deadline is the request's time limit plus `START_GRACE` (2 s).** A `docker run` includes pulling the container up (a few hundred ms here, more on a loaded CI runner), and charging that to the student would fail correct programs with a tight limit. The cost is leniency: a program that overruns by less than 2 s is not stopped, and `runtime` (which includes the start-up) shows the true time. The allowance is a named placeholder pending the human's tuning. The alternative, measuring only the program's own time, would need a signal from inside the container (a started marker) and is more machinery than the row asks for. `startingTheContainerIsNotChargedToTheProgram` pins the behaviour (a 100 ms limit with a trivial program is still `OK`).
- **The container is killed, not the client.** `DockerCommand.run` takes an optional timeout action; the runner passes `docker kill <name>`. Without it, destroying the `docker run` client only detaches us: `DockerCommandTests.killingOnlyTheClientLeavesTheContainerRunning` demonstrates that the program keeps running (state `running`) after the client is gone. With the kill, the container ends `exited 137` and the client returns on its own within seconds, which the tests assert (the client is destroyed only as a last resort after 15 s, `AFTER_TIMEOUT`, and a run that needed that would be well over the allowance the tests check).
- **Kill retried while the container does not exist yet.** If the deadline fires while Docker is still creating the container (only plausible with a heavily loaded host), `docker kill` says "No such container"; it is retried every 250 ms for up to 5 s. "is not running" (the program ended in the same instant) is not an error. The `docker rm --force` in the `finally` is the backstop for any remainder. 4.3d adds the leftover-container checks for the other paths.
- **`TIMEOUT` carries no exit code** (the kill makes it 137, which says nothing about the program, and 4.5a's table must not confuse it with an out-of-memory 137) and keeps the stdout/stderr printed before the kill, for the teacher's debugging view.
- **The 10-minute `SAFETY_CEILING` of 4.3a is removed:** the assignment's own maximum (10 s, `AssignmentRequest`) plus the allowance now bounds every run.
- **Still not safe to wire to student code: no output cap yet (4.3c).** The output goes to temp files, so a program that prints in a loop fills the disk for up to the time limit. `backend/CLAUDE.md` and the class Javadoc now say "until 4.3c".
- **Test timings are deliberately loose** (`limit + 2 s + 8 s`) so a slow CI runner does not flake them, yet a missing kill (client destroyed after 15 s) still fails them: **mutation-checked** by making `killContainer` a no-op, which failed the four stop-it tests (the suite took 122 s instead of ~23 s); code restored.
- **Tests (+12, backend 1545 -> 1557; ai-service and frontend unchanged and passing):** `DockerCommandTests` (3), `SandboxTimeoutTests` (9: infinite loop, sleep forever, blocked wait, large unread stdin, partial output kept, next run unaffected, early finish returns early, start-up not charged, a 2 s program within a 6 s limit is not cut). The first four also assert no running or stopped sandbox container and no working directory is left.

## 4.3c — Output size cap

- **The cap is applied while reading, not after.** Until now the client's output went to temp files and was read back whole: a printing loop would have filled the disk for the whole time limit and then loaded all of it into memory. `DockerCommand` now reads both pipes continuously on two threads into a `BoundedCapture` that keeps the first `limit` bytes and discards the rest as it reads. Two consequences worth knowing: the program is never blocked on a full pipe (we always drain), and the temp files are gone. The price is that a program that prints without end still burns CPU on both sides until its timeout; stopping it at the cap would need a status for it (below).
- **1 MiB per stream, not 64 KB.** The row says "e.g. 64 KB". Test cases may have an expected output of up to 100000 characters (`TestCaseRequest`), so a 64 KB cap would cut off a correct program and fail it. 1 MiB is above anything a test case can expect (100000 characters is at most about 400 KB of UTF-8), still bounds memory at 2 MiB per run, and is a named placeholder (`OUTPUT_LIMIT_BYTES`) for the human to tune. A runner that took the limit from the expected output (a field on `ExecutionLimits`) would be tighter; not done, because it is a decision about Phase 5's contract.
- **Marked, not rejected.** The flags `stdoutTruncated` / `stderrTruncated` were already in `SandboxResult` (4.1a); they are now set, for `OK`, `RUNTIME_ERROR` and `TIMEOUT` alike. `completedCleanly()` looks at stdout only, so a cut stdout can never be compared as if complete (`OK` + truncated is false), while a cut stderr (never compared) does not matter.
- **No "output limit exceeded" status.** The five statuses the rows name stay; a program that prints past the cap keeps running to its exit or the timeout. Judges often stop the program at that point; if the human wants that (faster, and a distinct verdict for students), it is a new status plus a kill, a small follow-up. Recorded here rather than guessed.
- **The cut never splits a UTF-8 character.** One extra byte beyond the limit is kept so the byte after the cut is known; a continuation byte there means the cut is inside a character, and that character is dropped whole. Without this, the text would end in a U+FFFD the program never printed. Tests cover 2-, 3- and 4-byte characters, every limit from 1 to 39, and a real 1 MiB cut.
- **Boundaries are exact:** output of exactly the cap is whole and unmarked, one byte more is marked (`SandboxOutputCapTests`, `BoundedCaptureTests`). Both were mutation-checked (`>` to `>=`, and the character backoff disabled): 7 failures across the two classes; code restored. A first mutation attempt did not compile (`while (false)`), so it proved nothing and was redone.
- **Other docker commands use a default 1 MiB cap too** (`inspect`, `rm`, `kill`, `build`), so a surprising amount of output from them cannot grow memory either.
- **The runner can now be wired once 4.4b and 4.5a land.** The two ways a student's program could hurt the host (running forever, printing forever) are bounded; what remains before grading uses it is Java (compile step) and the status mapping (out-of-memory is still reported as `RUNTIME_ERROR`).
- **Tests (+21, backend 1557 -> 1578; ai-service and frontend unchanged and passing):** `BoundedCaptureTests` (13, no Docker), `SandboxOutputCapTests` (8, Docker).

## 4.3d — Guaranteed cleanup

- **Most of the row was already true.** Since 4.3a the container is named, inspected and `docker rm --force`d in a `finally`, and the run directory is deleted in a `finally`; the timeout and failure tests of 4.3a/4.3b already assert no container and no directory is left. This commit does not rewrite that; it looks for the ways the `finally` could still not clean up.
- **Found and fixed: an interrupted thread leaked the container.** `DockerCommand.run` turns an `InterruptedException` into an exception and sets the thread's flag again; `removeContainer` then ran `docker rm` with the flag set, so its own wait threw at once and the removal was never confirmed (the container stayed, running, with its client). `removeContainer` now clears the flag, removes, and restores it; the interruption is not swallowed. `DockerCommand` also destroys its client process when the wait is interrupted. The new test reproduced the leak before the fix (a running sandbox container was left) and passes after.
- **Not covered, deliberately: a crash or kill of the JVM.** No `finally` runs then, so containers (labelled `com.gradingplatform.sandbox`) and run directories under the work root stay. A sweep on startup (remove labelled containers and old `run-*` directories) would close it, but it needs a decision with Phase 5's requeue (a sweep must not remove a container of a run still in flight in the same process) and is a new mechanism outside the row: filed in `docs/suggestions.md` and, at the human's request, added as task row 4.3e (a sweep that runs before the executor accepts work cannot touch a run in flight, which settles the worry above for a single instance).
- **Also not covered: files a container created in a writable run directory** (the compile step, 4.4b). The directory is `rwxrwxrwx`, so files in it can be deleted by the host, but a subdirectory created by user 10001 (a Java package directory) is `755` and its content cannot be deleted by the host user on Linux. Windows with Docker Desktop is unaffected. To be handled in 4.4b, where such files first exist (for example `umask 000` in the compile command, or deleting through a container).
- **Tests (+2, backend 1578 -> 1580; ai-service and frontend unchanged and passing):** `SandboxCleanupTests`.

## 4.3e — Startup sweep of orphaned containers and directories

- **Hook: `SmartInitializingSingleton`, not `ApplicationRunner`.** It runs once all singletons exist and before any `ApplicationRunner`, so Phase 5's startup recovery (5.2c, likely a runner) and executor cannot start a run before the sweep. That ordering is what makes the sweep safe: it removes *every* labelled container, so it must never run while this process has runs of its own. The constraint is written on `SandboxStartupSweep` and in `backend/CLAUDE.md` for Phase 5: no worker may start before it (a worker thread started in a bean's `@PostConstruct` would be too early).
- **Single-instance assumption (recorded as the row asks).** The label and the work root (`<tmpdir>/grading-sandbox`) are not per instance. A second backend on the same Docker daemon or temp directory would have its live runs removed. v1 is one instance; for more, the label would need an instance id.
- **Docker unavailable does not stop startup.** Listing failures (non-zero exit, docker missing, timeout) are logged and the containers are skipped; the directories are still handled; `SandboxStartupSweep` also catches anything else. Tests start a context without caring about it either way.
- **Directories: only `run-*` real directories, links not followed.** Anything else in the work root is left alone, and a symlink named `run-x` is not entered (`Files.isDirectory(NOFOLLOW_LINKS)`; `deleteTree` does not follow links either). The symlink test cannot run on this Windows host (skipped); the behaviour rests on those two JDK defaults.
- **Reuses `removeContainer`** (which takes the full id as well as a name), so a removal that fails is logged and the sweep goes on; it also keeps 4.3d's interrupt handling.
- **Still open (from 4.3d, not part of this row):** files a container creates in a writable run directory (compile step) may not be deletable by the host on Linux; for 4.4b. The sweep's `deleteTree` has the same limit there.
- **Tests (+8, backend 1580 -> 1588; ai-service and frontend unchanged and passing):** `SandboxStartupSweepTests`: running and stopped containers removed, a container without our label kept, directories with nested content removed while other entries (including a file called `run-...`) stay, symlink not followed (skipped on Windows), second sweep finds nothing, a normal run after the sweep, the hook calls the sweep once, and a failing sweep does not throw.

## 4.4b — Java compile step

- **Where it lives: inside `run()`, before the run container.** Same writable-mount mechanism 4.3a prepared (`runInContainer(..., writable=true)`), then a read-only run on the same directory. A language is "compiled" only because its config entry has a `compile-command` — no language name appears in code. 4.6a (compile once, run each test) will split `run` into a build and a run-with-existing-build; the pieces are already separate methods.
- **Compile limits are the platform's, not the assignment's (`COMPILE_LIMITS`, 30 s and 512 MB, placeholders, flagged).** `javac` does not fit in an assignment's 128 MB. This is a second set of limits, not a loosened one: network, read-only root, capabilities, PIDs, CPU and the tmpfs are the same as for a test container, and the compile container is killed on its own deadline like any run. Tuning is yours.
- **PID limit 128 (the 4.3a placeholder) was enough** for both `javac` and `java` here, so it is unchanged; nothing was loosened. The sandbox tests pass with it on this host (Docker Desktop); CI will show whether Linux differs.
- **Status mapping of a failed build.** Non-zero `javac` exit (it exits 1 for source errors, 2 for a missing file) = `COMPILE_ERROR` with the compiler's stdout/stderr and exit code. A build that times out = `COMPILE_ERROR` with the fixed text `Compilation took too long and was stopped.` and no exit code (my choice, flagged: it is the code's doing, and a student needs something to read; the alternative `TIMEOUT` would read as "the program is slow"). A build that is killed for memory shows as javac's own `OutOfMemoryError` text, also `COMPILE_ERROR`. A failure of the sandbox while compiling (Docker down, image missing) stays `SANDBOX_ERROR`, never a student's compile error.
- **Compiler output goes back to the student unfiltered**, as the row asks. It cannot hold a host path: `javac` is given `Main.java`, and the container sees only `/work`, so messages say `Main.java:3:`; a test pins that no host path appears. It is capped like any output (1 MiB).
- **`result.runtime()` is the run's, not the build's.** The time limit is the program's; the JVM's own start-up is inside it (README says so), covered by `START_GRACE`. Compile time is not charged to the student.
- **Convention for teachers and students is in the README ("Submission conventions")**, as the row asks: `Main.java`, public class `Main`, no `package` line (with one, `java -cp . Main` cannot find the class and the run fails as a runtime error). A file without a `Main.java` is a compile error from `javac` ("file not found").
- **Still open (from 4.3d/4.3e):** the compile container writes `Main.class` into the run directory as uid 10001. On Linux the host can still delete it (the run directory is world-writable, so the delete needs no ownership), so there is no leftover here; a source that makes `javac` create a *sub*directory would not be deletable by the host. Plain `javac Main.java` without `-d` and without packages does not create one, but a hostile source cannot choose the output directory either (the command is ours). Noted for 4.7a's hostile suite.

## 4.5a — Exit conditions to statuses

- **One `docker inspect` reads both `State.ExitCode` and `State.OOMKilled`** (`{{.State.ExitCode}} {{.State.OOMKilled}}`), before the container is removed (4.3d kept it for exactly this). The decision is a pure table in `ExitClassification` (unit-tested without Docker); anything that is not that shape is treated like "no container" (`SANDBOX_ERROR`).
- **Timeout is decided first, from our own deadline** (unchanged from 4.3b), so our `docker kill` (also 137) can never be read as a memory kill; there is no need to look at the flag on that path.
- **Rule: non-zero exit *and* the out-of-memory flag = `MEMORY_LIMIT`, whatever the code** (my choice, flagged; the row says "exit 137 with the OOM flag"). If the kernel killed something in the container for memory and the program then exited with 1 because its worker vanished, the limit was still hit. Cost: a program that catches its own child's death and exits non-zero is blamed on memory, which is true in cause.
- **Rule: exit 0 = `OK` even with the flag set** (my choice, flagged). A helper process OOM-killed while the main program ran to its end and exited normally: the program chose its output; calling that a memory failure would fail a program that handled it. Tested both ways.
- **137 without the flag is a plain `RUNTIME_ERROR`**: `exit(137)`, or a SIGKILL from somewhere else (a child killed by another signal shows as `-9` to its parent and the parent is `OK`).
- **Compile step:** a memory kill of the compiler is a `COMPILE_ERROR` with exit code 137 (existing `compileFailure` default branch), not `MEMORY_LIMIT`, which is about the student's program. Tested with `tail /dev/zero` as the compile command and a 64 MB compile limit.
- **Java memory bombs are a `RUNTIME_ERROR`, not `MEMORY_LIMIT` (decision for you).** The JVM's default heap is a quarter of the container's memory, so an allocation loop ends in `OutOfMemoryError` (exit 1, stack trace on stderr) long before the kernel acts and the flag is never set. Options: (a) leave it (what this commit does and pins in a test), a Java student sees `OutOfMemoryError` in the output, the status is `RUNTIME_ERROR`, a grade is the same either way; (b) map it by reading stderr for `OutOfMemoryError` (student-influenced text decides a status: a program can print that string, so I advise against it); (c) run Java with `-XX:MaxRAMPercentage=100`-style flags in `run-command` so the heap can grow into the container's limit and the kernel acts, at the cost of less headroom for the JVM's own off-heap memory (config change, no code; needs tuning). Not decided here.
- **Measured on this host first:** Docker Desktop (cgroup v2) sets `OOMKilled` for a Python allocation loop (exit 137, flag true) — the risk of an unreliable flag on cgroup v2 did not appear here; CI on Linux will show it there. A program cannot SIGKILL its own PID 1 from inside the container (the kernel ignores it), so the "other SIGKILL" case is tested with an explicit `exit(137)` and with a killed child.
- **PID limit 128, CPU and tmp size unchanged**; nothing loosened.
- **Tests (+35, backend 1607 -> 1642; ai-service and frontend unchanged and passing):** `ExitClassificationTests` (22: the table, the parser and its rejects), `SandboxExitStatusTests` (12: bomb = `MEMORY_LIMIT` with 137, reached long before the time limit, output before the kill kept, a program inside its limit untouched, `exit(137)` = `RUNTIME_ERROR`, killed child with a normal parent = `OK`, killed helper + normal parent = `OK`, killed helper + failing parent = `MEMORY_LIMIT`, timeout still `TIMEOUT`, ordinary failure, Java heap bomb pinned, nothing left behind), one compile-container test in `JavaCompileStepTests`. Mutation-checked: OOM branch removed -> 7 failures, code restored.

## 4.5b — Output comparison

- **Shape: an interface `OutputComparison` (`matches(expected, actual)`) with a default `passes(SandboxResult, expected)` and one implementation, `TrailingWhitespaceComparison`.** The row says "keep it swappable"; a functional interface is the smallest thing that is (a strict mode is `String::equals`, tested). `passes` is in the interface on purpose: "completed cleanly and matches" is one rule that no implementation can forget, so a truncated output (4.3c) or a crash after the right output can never pass, whatever comparison is plugged in. 4.6a/5.3a must grade with `passes`.
- **Not a Spring bean yet.** Nothing consumes it until 4.6a/Phase 5, and a per-assignment strict mode would need a lookup by mode rather than a single bean; that is a Phase 5 decision. `TrailingWhitespaceComparison.INSTANCE` is the default for now.
- **Package: `sandbox`** (Phase 4 rows, next to `SandboxResult`), although it never starts a container. If you prefer the grading code to own it, moving it to `service` is a rename.
- **The rule (flagged, mine):** split at `\n`; strip trailing whitespace of each line with `Character.isWhitespace` (space, tab, form feed, vertical tab... and the `\r` of CRLF, so CRLF = LF without a special case); drop trailing empty lines. Leading whitespace, interior blank lines, case and every other character count. Empty output equals whitespace-only output. A lone `\r` inside a line is an ordinary character. The no-break space (U+00A0) is *not* whitespace here: it is a visible difference, not a formatting one. Row 4.7c extends the real-world edge cases.
- **Unchanged from the spec:** comparison is of stdout only; stderr never counts. Hidden and public tests are compared by the same function with no knowledge of which they are (4.7d).
- **Cleanup in tests:** `PythonEndToEndTests` now uses the real comparison instead of its private throwaway.
- **Tests (+28, backend 1642 -> 1670; ai-service and frontend unchanged and passing):** `OutputComparisonTests`: equal after normalising (final newline either way, trailing spaces and tabs, CRLF vs LF and a mix, empty output, whitespace-only last line), still different (content, case, inner spacing, leading whitespace, blank lines, order, lone `\r`, no-break space, Unicode), `normalize`'s shape, null refused, a seeded random check of idempotence/symmetry/"a text matches its normal form"/trailing junk, `passes` (right output, wrong output, cut output, every non-`OK` status), and a strict rule swapped in. Mutation-checked: only spaces stripped and the clean-run guard removed -> 10 failures, code restored.

## 4.6a — Run all tests of an assignment for one submission

- **The interface grew one method, as 4.1a anticipated: `SandboxRunner.runAll(SandboxBatchRequest)`, a *default* method** (runs `run` per input, building every time). Making it abstract would have broken every simple implementation (a lambda fake in `SandboxTypesTests`); a default keeps them valid, and `DockerCliSandboxRunner` overrides it to build once. The trap (a runner that forgets to override builds per test) is slow, not wrong. `run(request)` in the Docker runner is now `runAll` of one input, so there is a single code path for the build and the runs.
- **`SandboxBatchRequest {language, sourceFiles, stdins, limits}`** is valid exactly when a `SandboxRequest` of it would be (it builds one to validate) and needs at least one input. It carries inputs only: no expected output, no test id, no visibility.
- **Compile once, run each test in its own container**, all on the same prepared directory: the build writes it (`COMPILE_LIMITS`, 4.4b), the runs mount it read-only, so a test cannot change what the next one executes (tested) and each container has its own tmpfs and processes (tested: a marker written to `/tmp` by one test is absent in the next). Sequential: Phase 5's worker pool parallelises across submissions, and one submission's tests share one directory.
- **A failed build is the result of every test** (the same `COMPILE_ERROR` with the compiler's output), as 5.3b expects, and no test container is started. After a `SANDBOX_ERROR` the remaining inputs are not tried and are marked `not run` (my choice, flagged): if Docker is down the other runs would fail one by one at a cost each, and the whole submission is retried anyway.
- **A sandbox failure is not a test verdict: `SubmissionTestRunner.runAll` throws `SandboxFailedException`** (new, fixed message, docker text stays in the log). The six `TestOutcome` values are exactly the `test_results.status` list, so nothing can be stored for a sandbox problem. Alternative considered: a seventh outcome `SANDBOX_ERROR` the caller must filter; rejected, a forgotten filter would grade a student for the platform's failure. Phase 5 (5.2b) catches it and sets `ERROR`.
- **Every test runs even after failures or timeouts.** The score is the weighted fraction passed, so a failing early test must not hide later ones. Worst case time = tests x (time limit + start-up allowance); Phase 5 may want to cap that (suggestion, not done).
- **`OK` becomes `PASSED`/`FAILED` by `OutputComparison.passes`**, so a cut output or a crash is never `PASSED` (4.5b). `TestRunResult.run` carries the full `SandboxResult`; it is the teacher's view and contains a hidden test's actual output, documented on the record and in `backend/CLAUDE.md`: 5.5a must mask, not filter.
- **`SubmissionTestRunner` is a `@Component`** with the default comparison (`TrailingWhitespaceComparison.INSTANCE`); a second constructor (package-private) takes another `OutputComparison`. A per-assignment strict mode is Phase 5's decision, as noted in 4.5b. `TestCaseInput` is a copy of the entity's fields so `sandbox` does not depend on the `entity` package.
- **Tests (+27, backend 1670 -> 1697; ai-service and frontend unchanged and passing):** `SubmissionTestRunnerTests` (15, fake sandbox: the verdict table, order and ids, the comparison rules and a swapped one, only inputs sent, one call per submission, sandbox failure throws, wrong result count, bad input, outcome names, `toString` hides texts, the default `runAll`, batch validation), `SubmissionRunAllTests` (12, real containers: five-test Python suite with pass/fail/timeout/crash, a timeout does not stop the rest, Java compiled and run, compile error for every test, one build proven by a shared `Main.class` modification time, fresh container per test, read-only directory for every run, own input per test, sandbox failure with `not run` and the exception, unconfigured language, nothing left behind, `run` still works). ## 4.7a — Hostile-program tests

- **One class, `SandboxHostileProgramTests`, no production change.** The older classes (timeout, exit status, output cap, flags) already ran an infinite loop, a sleep, a memory bomb and giant output; each row of the task is nevertheless run once here as a whole program, so the suite the thesis cites is self-contained. The class Javadoc is the threat map (category, hostile program, restriction that stops it). Small duplication on purpose; the detail stays in the older classes.
- **Probe style:** a Python prelude prints `label=ALLOWED` or `label=<errno name>` per attempt and the test asserts on the labels, so a failure names the attempt. Every test also runs through an `@AfterEach` that fails on a leftover container or run directory, and the fork-bomb tests end by running an honest program (the sandbox must still work after the attack).
- **Fork bomb in three shapes:** children that sleep and a parent that counts forks until `EAGAIN` (count must stay below `PIDS_LIMIT`), a bomb that ignores refusals (`TIMEOUT`, killed with the container), a bomb that dies at the first refusal (`RUNTIME_ERROR`). Plus a Java thread bomb (threads count against the same limit). The unbounded bomb is only safe because of `--pids-limit` and the 128 MB memory limit; a mutation without the limit was therefore run for the two bounded tests only.
- **Swap:** a slow 1 MB-per-10-ms growth must end `MEMORY_LIMIT` well before the time limit, and the container's own `memory.swap.max` is read and must be `0` (skipped on a cgroup v1 host or without swap accounting; it ran here).
- **Hidden-test exposure is not this row:** the "other submissions' data" probe plants a marker in a sibling run directory and in the work root and walks the whole container filesystem for the names. The property that hidden *test data* never exists in the container is 4.7d.
- **Mutation check (each restriction removed from `DockerRunArguments`, suite must fail):** no network (3 failures), no swap limit (1), no pids limit (2 of the 2 tests run), no `--read-only` (1), no `--cap-drop` (1), no `no-new-privileges` (1), writable `/work` (1), `noexec` removed (the first version of the test **survived**: Docker adds `noexec` to a tmpfs by default, so the mutation must say `exec`, and the probe script had no shebang; fixed on both counts and it now fails under the right mutation). **One survivor remains by nature:** dropping `--user` changes nothing, because both Dockerfiles already set `USER 10001`; only `SandboxFlagsTests` (reads the flag back) notices. Kept as a second layer, not removed.
- **Found while writing:** Docker masks `/proc/kcore` with an empty file (reading it works and returns nothing), so the probe asserts "no bytes came back" rather than "refused".
- **Tests (+22, backend 1697 -> 1719, 2 skipped as before; ai-service 1 and frontend 3 unchanged and passing; lint and format clean).** The class takes about 45 s.
- **CI failure after the PR opened (fix commit on the same branch):** `aForkBombThatDiesOnTheFirstRefusalIsARuntimeError` got `MEMORY_LIMIT` on the GitHub runner (native Linux Docker) where Docker Desktop gave `RUNTIME_ERROR`: about 127 busy Python processes forking in a loop need more than the 128 MB limit, so the kernel's out-of-memory kill came before the process limit refused a fork. The bomb was contained either way; the test had pinned one of two valid outcomes. Both fork-bomb tests that cannot tell which limit bites first now accept the two (`RUNTIME_ERROR` or `MEMORY_LIMIT`; `TIMEOUT` or `MEMORY_LIMIT`) and still require "not a clean run", the time bound and an honest program graded afterwards. The sleeping-children test (counts forks, children never touch memory) and the Java thread bomb (256 MB) are not affected and passed on CI. Lesson: a hostile-program outcome that depends on which of two limits fires first is host-dependent; run such tests on the CI runner before treating them as stable (only Docker Desktop was available locally).
