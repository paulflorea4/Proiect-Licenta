  - **[H1, tested] Every hint request holds a database connection for the whole AI call, up to 70 s.** `spring.jpa.open-in-view` is on (Spring's default; the tests warn "enabled by default"; `application.yml` never sets it), so the connection taken by `SubmissionViewService.view` stays checked out after its read-only transaction ends, through `AiServiceClient.feedback`. The 7.1a guard (`isActualTransactionActive()`) and its test pass because no transaction is active, but the purpose of the rule (not holding a connection) is missed. A probe counted 1 active Hikari connection during the mocked AI call, and 0 with `spring.jpa.open-in-view=false`. Failure: about 10 simultaneous hint requests (the pool's default size) with a slow Gemini exhaust the pool for up to 70 s, so the grading worker's `claim`/`finish`/`saveAll` wait 30 s and fail, and a failed `finish` leaves a row `RUNNING` until the next restart (5.2b): grading would depend on AI latency. Direction: `spring.jpa.open-in-view: false` (no entity has JPA associations, so nothing lazy-loads in a view), plus a test asserting no active connection inside the AI call.
  - **[H2, tested] The leak guard lets a whole corrected program through when the fix adds a line (level 3) or removes a line (every level).** `ai-service/src/ai_service/leak_guard.py` drops lines copied from the student's code before any check, and the complete-program and similarity checks look only at the new lines. Run against the real guard: the student's `a, b = input().split()` / `print(a + b)` plus a hint that reprints it with `a, b = int(a), int(b)` inserted passes at level 3; the student's program minus a faulty `a = a - 1` line, reprinted as a hint, passes at levels 1, 2 and 3. Root `CLAUDE.md`: "no level may output a complete working solution". Not among 6.4a's listed known limits. Direction: treat a block that reproduces most of the student's lines but differs from their program as a leak (the share as a named placeholder, the human's value), and add both shapes to `FULL_SOLUTIONS`.
  - **[H3, tested] A container that never starts is graded as the student's `RUNTIME_ERROR` (or `COMPILE_ERROR`), not `SANDBOX_ERROR`.** `DockerCliSandboxRunner.recordedState` inspects only `State.ExitCode` and `OOMKilled`; a container whose start failed stays `created` with exit code 127, 126 or 128 and an error text in `State.Error` (shown with the real sandbox image and a command that does not exist: `created exit=127 ... err=... OCI runtime create failed ...`). `ExitClassification` turns that into `RUNTIME_ERROR`, a stored zero, although `SANDBOX_ERROR` is "never a grade, never the student's fault". Failure: a typo in a config-only language's `run-command`, or a host that cannot start containers, zeroes every submission (re-grading is out of scope). Direction: read `State.Status`/`State.Error` in the same inspect; anything not `exited` with an empty error is `SANDBOX_ERROR`; a test with a run command that does not exist.
  - **[H4, read] A normal shutdown turns the submissions being graded into `ERROR` instead of leaving them `RUNNING` for recovery.** `SubmissionDispatcher.destroy()` calls `ThreadPoolTaskExecutor.shutdown()`, which, with `waitForTasksToCompleteOnShutdown` never set (default false), interrupts the running workers; the interrupt becomes a `SANDBOX_ERROR`, then `SandboxFailedException`, and `SubmissionWorker`'s catch-all writes `ERROR`. Recovery (5.2c) only re-queues `RUNNING` rows, so those submissions are never graded; the `destroy()` comment states the opposite intent. Only a hard kill gives the documented behaviour (root `CLAUDE.md`: re-queued on startup). Not reproduced end to end. Direction: an interrupted or shutting-down worker leaves the row `RUNNING` (no `finish`), or the pool waits a bounded time; a test that destroys the dispatcher mid-run.

  **Medium**
  - **[M1, read] A demoted admin can reinstate themselves and demote the admin who demoted them, within their token's 24 h.** `UserAdminService.changeRole` never re-reads the caller; `@PreAuthorize("hasRole('ADMIN')")` trusts the token's role claim. The documented "keeps admin rights until the token expires" (2.4b/2.5b) did not consider reversing the demotion. Direction: under the admin lock it already takes, re-read the caller's row and refuse unless it is `ADMIN`.
  - **[M2, tested] A memory limit below 6 MB is accepted but can never run.** `AssignmentRequest.memoryLimitMb` is `@Min(1)` and Python has no `min-memory-mb`; Docker refuses `--memory` under 6 MB ("Minimum memory limit allowed is 6MB", shown here), so every run is `SANDBOX_ERROR` and every submission `ERROR`, with nothing telling the teacher why. Direction: an absolute floor as a named constant, checked like `min-memory-mb` (value the human's).
  - **[M3, auditor] A submission that ends in `ERROR` after the deadline leaves the student no way to be graded (product decision).** `ERROR` gives the attempt back (5.1d), but a new submission is refused after the deadline, nothing re-queues `ERROR` rows and no teacher action re-runs one. Failure: Docker down, or the H4 shutdown, in the last minutes before a deadline. Options: judge a resubmission against the `ERROR` submission's arrival time, a teacher "re-run", or an automatic retry on `SANDBOX_ERROR` (GATE: the human's choice).
  - **[M4, auditor] Time and memory limits stay editable after submissions, so a submission still queued is graded with the new limits** (decided at 3.3c, with a flag). `SubmissionGrader` reads the limits at grading time; two students with the same code can get different outcomes. `backend/CLAUDE.md` (3.4a bullet) now says to lock "anything that changes what a submission is graded against", which contradicts it. Options: lock the limits like the language, or snapshot them on the submission when accepted; then align the wording (GATE).
  - **[M5, auditor, two audits] The AI service's worst case per hint is not inside the backend's 70 s read timeout.** Two Gemini attempts of connect 5 s + read 30 s each (httpx's read timeout is per socket read, so not a total) give at least 70 s before the service's own work; 504 is retried although Gemini's 504 can arrive late. Failure: the backend gives up, the student sees 503 and the hint the service produced is lost. Direction: an overall deadline in `generate_feedback`, or skip the second attempt when too little time is left, or a longer backend timeout (placeholders, GATE).
  - **[M6, auditor] The prompt's fence length multiplies by the number of blocks.** The fence is one backtick longer than the longest run in any block and is written around every block (description, code, and 2-4 per public test); the student controls the longest run (code up to 128 KiB, output up to 1 MiB per test). A program printing 1 MiB of backticks on 10 public tests yields a prompt of about 84 MB per hint request. Related to the 6.3a prompt-budget suggestion, which does not mention the multiplier. Direction: the budget caps what the builder includes, so the fence is bounded too.

- **(7.7b, 2026-10-28) The Java image's entrypoint script hides a missing run or compile command from 7.7b's check.** `eclipse-temurin:17-jdk-jammy` sets `ENTRYPOINT ["/__cacert_entrypoint.sh"]`, which our `infra/sandbox/java/Dockerfile` inherits. Every command runs through that shell, so a command missing from the image is the shell's `exec: ...: not found`, exit 127, and Docker records `exited 127` with no `State.Error`: exactly a program's own `exit(127)`, so it is still graded as the student's `COMPILE_ERROR` (build) or `RUNTIME_ERROR` (run). Checked: `docker image inspect` shows the entrypoint on the Java image and none on the Python image; a test with `javac-does-not-exist` as the compile command got `COMPILE_ERROR`. The script only matters when `USE_SYSTEM_CA_CERTS` is set (importing host CA certificates), which the sandbox never needs (no network). Options, each a choice not covered by any default: `ENTRYPOINT []` in the Java Dockerfile (the image changes; `SandboxImagesTests` would pin it), or `--entrypoint` in `DockerRunArguments` (a new `docker run` flag for every language), or leave it and rely on configuration review. Needs the human's decision.
