| 4.1a | `SandboxRunner` interface + request/result types (language, source files, stdin, limits → status, exit code, stdout, stderr, runtime) | Done | Pure Java, no Docker yet. Everything above this layer (Phase 5) codes against the interface, so a different runner can be swapped in later. |
| 4.1b | Languages config file (image, compile command, run command, source file name) + loader | Done | Java 17 and Python 3.12 entries; image names are placeholders until the 4.2a gate fixes them. Adding a language must be a config entry plus an image — no `if (language == ...)` anywhere. 3.3a validates assignment languages against a stand-in list, `assignments.languages` in `application.yml` read by `config/AssignmentProperties`: make the real config the source of that list and remove the stand-in. |
| 4.2a | **GATE** — confirm Docker is installed and approve the base images for the Java and Python runners | Done | Docker and base images are external software; stop and ask which images the human wants (e.g. a JDK image and a slim Python image). |
| 4.2b | Runner images: `infra/sandbox/java/Dockerfile` and `infra/sandbox/python/Dockerfile` | Done | Non-root user, no extra tooling beyond what compile/run needs. Blocked on 4.2a. |
| 4.3a | `DockerCliSandboxRunner`: start one container per run with `--network none`, memory limit with swap disabled (`--memory-swap` equal to `--memory`), CPU and PID limits, read-only root fs, a tmpfs `/tmp`, and the submission's working directory as the only bind mount, non-root user, all capabilities dropped, `no-new-privileges` | Done | Default per CLAUDE.md: `docker` CLI via `ProcessBuilder`, no new library. Every flag must be asserted by a test (4.7a), not just present in the code. Compiled output must survive between containers (4.6a compiles once, then runs each test in a fresh container), so a tmpfs can't hold it: use one per-submission host temp dir, mounted read-write in the compile container and read-only in test containers. Pass every `docker` argument as a list element, never through a shell string, and never interpolate student-controlled text into arguments. The dev host is Windows with Docker Desktop: check bind-mount path conversion and file permissions for the non-root user early, and if bind mounts prove unreliable there, use `docker cp` instead — record the choice in decisions. |
| 4.3b | Wall-clock timeout: kill the container itself (`docker kill`), report `TIMEOUT` | Done | Killing only the client process leaves the container running — that is the classic bug here. |
| 4.3c | Output size cap: truncate stdout/stderr at a named constant (e.g. 64 KB) | Done | Without it, `while(true) print(...)` fills memory on the host before the timeout fires. Mark truncated output so the comparison doesn't silently pass on a prefix. |
| 4.3d | Guaranteed cleanup: containers and temp workdirs removed on success, failure, and timeout | Done | Don't rely on `--rm`: 4.5a needs `docker inspect` (`OOMKilled`) after the container exits, which `--rm` makes impossible. Name each container, inspect it, then `docker rm -f` in a `finally`; verify with a test that counts leftover containers. |
| 4.3e | Startup sweep of orphaned sandbox containers and run directories (left behind when the JVM is killed or crashes mid-run) | Done | Added at the human's request after 4.3d (see `docs/suggestions.md`): the `finally` blocks of 4.3a-4.3d cannot run when the process dies. On startup, before the executor accepts any work, remove every container with the label `com.gradingplatform.sandbox` (`docker ps --all --filter label=...`, then `docker rm --force`) and delete the `run-*` directories under the work root. Safe because nothing of this process is in flight yet; it assumes a single backend instance (v1) — record that assumption. Must not fail startup if Docker is unavailable (log and go on). Pair with 5.2c, which re-queues the submissions those runs belonged to. Test: leave a labelled container and a `run-*` directory behind, build a new runner, expect both gone and unrelated containers/directories untouched. |
| 4.4a | Run a Python submission end to end with one stdin/stdout test | Done | First real proof that the container plumbing works — before adding compilation. |
| 4.4b | Java: compile step (`javac`), then run; compile errors returned as `COMPILE_ERROR` with the compiler output | Done | The public class/file-name convention must be documented for teachers and students (the languages config's source file name). |
| 4.5a | Map exit conditions to statuses: normal, non-zero exit → `RUNTIME_ERROR`, out-of-memory (exit 137 with OOM flag) → `MEMORY_LIMIT`, timeout → `TIMEOUT` | Done | Exit 137 alone is ambiguous (OOM vs. our own `docker kill`) — distinguish them. Read `State.OOMKilled` with `docker inspect` before the container is removed (4.3d). |
| 4.5b | Output comparison: pure function, normalizes trailing whitespace per line and trailing newlines | Done | Named, isolated, unit-tested — teachers will eventually want a strict mode; keep it swappable. |
| 4.6a | Run all tests of an assignment for one submission: compile once, run each test in its own container, collect per-test results | Done | Returns results only; persisting them is Phase 5. Compile once per submission, not once per test. |
| 4.6b | CI trigger: add `infra/sandbox/**` to the path filter of `.github/workflows/backend-ci.yml` | Not started | Added at the human's request after 4.2b (see `docs/suggestions.md`): the sandbox tests build the images from `infra/sandbox`, but a PR that changes only a Dockerfile triggers no backend check. One-line workflow change; keep every other path filter as it is. Do it before 4.7a, which needs Docker in CI. |
| 4.7a | Hostile-program tests: infinite loop, `sleep` forever, memory bomb (including growth that would spill into swap), fork bomb, outbound network call, write to the root filesystem, read of sensitive host paths, giant output — each contained and reported with the right status | Not started | This is the test suite the thesis's security chapter cites. Organize the cases by the categories used in published sandbox test suites (sensitive information exposure, filesystem manipulation, external communication, dangerous operations) so the chapter can map tests to threats; infinite-loop and sleep submissions are the standard judge sanity checks. Needs Docker in CI (0.4a). |
