## 2.1a — `application.yml` with `dev` / `prod` profiles

- **One file, profile documents:** `application.properties` is deleted; `application.yml` holds the common settings (application name, `ddl-auto: validate`) plus one `spring.config.activate.on-profile` document each for `dev` and `prod`. Comments from the old file moved with the settings they explain.
- **`dev` falls back on the URL and username only** (`jdbc:postgresql://localhost:5432/grading`, `grading`, the compose defaults). **The password has no fallback**, because `infra/docker-compose.yml` refuses to start without a `POSTGRES_PASSWORD` the developer chose, so there is no compose password to fall back to. The fallbacks are plain values, not `${SPRING_DATASOURCE_URL:...}` placeholders: the env vars already override the file through relaxed binding, so a placeholder would only repeat that.
- **`prod` has no datasource keys at all**, so a missing `SPRING_DATASOURCE_*` variable fails at startup with "Failed to configure a DataSource". Verified for real: `SPRING_PROFILES_ACTIVE=prod ./mvnw spring-boot:run` with no variables stops with exactly that message.
- **No profile is active by default (no `spring.profiles.default`).** Making `dev` the default would also activate it in the tests, where 2.2a will put the dev-only seed location on the Flyway path and break `DevSeedNotInDefaultPathTests`; it would also let a forgotten `SPRING_PROFILES_ACTIVE` on a server silently use localhost. The profile is chosen explicitly (`SPRING_PROFILES_ACTIVE=dev` locally, documented in the README, `backend/CLAUDE.md` and a commented line in `backend/.env.example`).
- **Verified `dev` for real:** `SPRING_PROFILES_ACTIVE=dev` with no variables reached the Postgres that is listening on this machine's `localhost:5432` and stopped on "server requested SCRAM-based authentication, but no password was provided" — so the fallback URL and username are applied and only the password is missing. (Port 5432 was already taken by a host Postgres, so no throwaway container could be bound there; no credentials were sent.)
- **Not done here, left to later rows:** the dev seed location and the `spring.flyway.out-of-order` question from 1.4a belong to 2.2a (this row only covers the datasource); the other `.env.example` variables (`JWT_SECRET`, `AI_SERVICE_URL`, `AI_SERVICE_TOKEN`, `CORS_ALLOWED_ORIGINS`) get bound by the tasks that first use them.
- **Tests (`ApplicationConfigTests`):** they parse `application.yml` with `YamlPropertySourceLoader` instead of booting a context, because a booted context would see any `SPRING_DATASOURCE_*` variable set on the developer's machine (env vars override the file) and the test would pass or fail depending on it. Covered: no `application.properties` on the classpath, the common settings, no datasource keys outside the profile documents, the `dev` URL and username, no `dev` password, no `prod` datasource keys, exactly the profiles `dev` and `prod`.
- **Local gotcha:** after deleting a resource, `target/classes` still holds the old copy until `./mvnw clean`; the "no `application.properties`" test failed locally for that reason only (passes on a clean build and in CI).

## 2.1b — Package structure

- **Gate resolved by the human: package by layer.** Neither the row nor any other document fixed it, and `backend/CLAUDE.md` treats that as a gate, so I asked; the options were by layer, by feature, or a hybrid. By layer won (the row's wording, simplest). Not revisited here.
- **Packages:** `controller`, `service`, `repository`, `entity`, `dto`, `config`, `security`, `sandbox`, `ai`. The row names the first four and asks for room for `sandbox` and `ai`; `dto`, `config` and `security` are my additions inside the chosen layout because 2.3–2.5 (signup DTOs, the JWT filter chain, CORS/properties) need an obvious home on day one. Enums live in `entity` (2.3a's `Role`).
- **Anchored by `package-info.java`**, since Java can't keep an empty package in git. Each Javadoc states what belongs there and the rule that bites in that layer (no business rules in controllers, entities never returned from the API so hidden test data can't leak, no AI call inside a transaction, only `sandbox` starts containers). No annotations (e.g. JSpecify `@NullMarked`) were added: a null-safety convention is its own decision.
- **No ArchUnit:** enforcing dependency direction between layers would need a new test dependency, which the root `CLAUDE.md` makes a gate. `PackageStructureTests` only checks that the nine `package-info.java` files exist with the right `package` line and that no other top-level package has appeared (new ones come through a task). Suggestion only if wanted: ArchUnit for layer rules.
- **Test location caveat:** `PackageStructureTests` reads the source tree relative to the working directory (`src/main/java/...`), which is `/backend` for `./mvnw` and for CI (`working-directory: backend`). Running it from an IDE with a different working directory would fail.

## 2.2a — Flyway under the `dev` and `prod` profiles

- **Wiring (in `application.yml`):** the common document now states `spring.flyway.locations: classpath:db/migration` explicitly (the production path, written down so the seed can't creep in); the `dev` document overrides it with `classpath:db/migration,classpath:db/dev-seed`. `prod` and the no-profile tests therefore never see seed data.
- **`spring.flyway.out-of-order: true` in `dev` only — my call, flagging it because 1.4a left it open.** Seeds are versioned from 1000 (1.4a), so a dev database that already applied them rejects a later schema migration (V11) with "Detected resolved migration not applied". Out-of-order lets that migration apply. Alternatives rejected: recreating the dev DB after every schema migration (easy to forget, loses dev data), or renumbering seeds (they always have to sort after the schema). Limited to `dev` because production never has seed versions, so there migrations stay strictly in order (`prod` test asserts `out-of-order` is false). Revert is one line if you prefer recreating dev databases.
- **Verified for real, not just in tests:** fresh throwaway `postgres:16` on port 55432 for each profile (the host's 5432 is taken by a local Postgres, so the datasource URL was overridden by env var), app started with `SPRING_MAIN_WEB_APPLICATION_TYPE=none` so it exits after startup. `prod`: 10 migrations applied, 0 users. `dev`: 13 migrations applied, 4 users. Hibernate's `ddl-auto: validate` also passed at startup (no entities yet, so trivially). Containers removed afterwards.
- **Tests:** `FlywayDevProfileTests` (3: locations on the path and 13 migrations applied at startup, seed rows present, out-of-order on), `FlywayProdProfileTests` (3: locations are `db/migration` only and 10 migrations applied, no users, out-of-order off), `FlywayOutOfOrderTests` (1: with a test-only `V999` probe migration, `outOfOrder=false` fails validation while `outOfOrder=true` applies it). They use `@ActiveProfiles` with Testcontainers; the profile's datasource URL is overridden by the Testcontainers connection, so the tests don't depend on a local database or env vars.
- **Probe migration lives only on the test classpath** (`src/test/resources/db/out-of-order-probe/V999__out_of_order_probe.sql`), and is numbered 999 so it can't collide with a real V11+ for a long time. The out-of-order test is its own class and `@DirtiesContext(AFTER_CLASS)`, because applying the probe changes the database. **Correction (found when CI failed on PR #44):** my first fix was only the separate class, on the wrong assumption that a class gets its own context. Spring caches a test context, and its Testcontainers database, across all classes with the same configuration, so `FlywayOutOfOrderTests` and `FlywayDevProfileTests` shared one database. Locally the dev class happened to run first and passed; in CI the order was reversed, the probe was already applied, and the startup count read 14 instead of 13. Reproduced locally with `-Dsurefire.runOrder=reversealphabetical`; with `@DirtiesContext` both orders pass. Lesson for later phases: any test that mutates shared state needs `@DirtiesContext` or its own cleanup, and "passes locally" says nothing about class order (relevant to 2.7a's shared test base).

## 2.2b — `GET /health`

- **Response shape:** `{"status":"UP"}` with 200, or `{"status":"DOWN"}` with 503 when the database check fails. The row only says "200 + DB connectivity check"; 503 for "down" is the usual contract for load balancers and the hosting probe in 16.8a. Nothing but the status is returned (no database name, URL, version or exception text), since the endpoint is public. The cause goes to the log at WARN (exception class and message only; no connection string or password is in a driver exception message, but this is worth a glance if the logging in 15.x grows).
- **No Spring Boot Actuator.** Its `/actuator/health` would fit, but the row names `GET /health`, and Actuator is a new dependency (a gate in the root `CLAUDE.md`). The hand-written endpoint is about 50 lines and keeps the path the AI service also uses (`GET /health`, 6.1a).
- **DB check:** `dataSource.getConnection()` then `connection.isValid(...)`, run on a separate thread with a 3 s limit (`HealthService.CHECK_TIMEOUT`, named constant). Reason: when the database is down Hikari waits up to 30 s for a connection, which would make a probe hang far past any orchestrator timeout. On timeout the request returns 503 and the worker thread is abandoned until the pool gives up. Raising/lowering the Hikari `connection-timeout` globally was rejected: it would also change how the grading workers behave under pool pressure, which is not this task's business.
- **Layering follows 2.1b:** `controller/HealthController` → `service/HealthService` → `DataSource`; `dto/HealthResponse`. The timeout is injectable through a package-private constructor so the hang test takes 0.3 s instead of 3 s.
- **Security (needed for the row to be true):** Spring Security is on the classpath, so before this commit every path, `/health` included, answered 401. Added a minimal `security/SecurityConfig`: `GET /health` is public, everything else requires authentication (403 for now, since no authentication mechanism exists yet). It is explicitly a stand-in: 2.4b writes the real JWT chain and its row already says `/health` must stay public. CSRF, sessions and the 401-vs-403 behaviour are deliberately left at the defaults for 2.4b to decide. `POST /health` is rejected (403 today) because only `GET` is permitted.
- **Verified for real:** app started (`prod` profile, throwaway Postgres on 55433, port 18080): DB up → 200 `{"status":"UP"}`; `/courses` → 403; `POST /health` → 403; DB container stopped → 503 `{"status":"DOWN"}` after 3.0 s; DB restarted → 200 again within the same app run. App and container removed afterwards.
- **Tests (12 new):** `HealthEndpointTests` (5, real app + Testcontainers: 200 UP, no credentials needed, body is exactly the status, other paths still need authentication, POST rejected), `HealthEndpointDownTests` (2, `@WebMvcTest` with a mocked service: 503 DOWN and 200 UP bodies), `HealthServiceTests` (5, mocked `DataSource`: valid → up, invalid → down, connection refused → down, a hanging connection → down in under 2 s, default timeout ≤ 5 s). The first run of the endpoint tests failed with 401 as expected before the security config existed.

## 2.3a — `User` entity, `Role` enum, `UserRepository`

- **Mapping:** `entity/User` ↔ `users` (the table is plural because `user` is reserved in Postgres, so `@Table(name = "users")`). Every field has an explicit `@Column(name = ...)` rather than relying on Spring's naming strategy, so renaming a Java field can't silently change a column. `id` is `GenerationType.IDENTITY`, which matches `GENERATED ALWAYS AS IDENTITY` (Hibernate omits the id on insert).
- **`Role`** in the `entity` package (as 2.1b said): `STUDENT`, `TEACHER`, `ADMIN`, stored with `EnumType.STRING`, so the VARCHAR holds the name (a reordered enum can never corrupt data). The spec says the role is validated in the application layer, so there is no DB CHECK, and an unknown value in the column would fail when the row is read.
- **`created_at`:** filled by the database default. Mapped `insertable = false, updatable = false` plus `@Generated(event = EventType.INSERT)`, so the entity never writes it and Hibernate reads the value back after the insert (the saved object has `createdAt` straight away). `Instant` maps `TIMESTAMPTZ` correctly.
- **Immutable apart from construction:** a public constructor `(email, passwordHash, fullName, role)`, a protected no-arg one for JPA, getters only. No setters: 2.3b creates users as `STUDENT` and nothing else changes them yet. The admin promotion in a later phase will add the one mutator it needs (`role`) then. No `equals`/`hashCode` either, for now (identity equality); adding a bad one is worse than none.
- **`UserRepository`:** `JpaRepository<User, Long>` plus `findByEmail` and `existsByEmail` (2.3b/2.3c and 2.4a need exactly these). **Email case:** lookups are exact and case-sensitive, like the database's `UNIQUE (email)`. Whether to normalise emails (lower-case on signup/signin) is 2.3c's call ("reject duplicate email"); a test pins the current behaviour so that change is deliberate. (`Ada@x.com` and `ada@x.com` are two accounts today.)
- **Validation of the mapping:** `ddl-auto: validate` was already on, and the entity makes it bite for the first time (before there were no entities). Checked with a deliberate break: renaming the column to `pass_hash` made every context fail with `Schema validation: missing column [pass_hash] in table [users]`; reverted.
- **Tests:** `UserRepositoryTests` (9, Testcontainers, rolled back): the three roles, generated id and `created_at`, every field in its own column, role stored as its name, a row inserted by SQL read back correctly, `findByEmail`, `existsByEmail`, case-sensitive lookup, the database still rejecting a duplicate email. `DevSeedUsersTests` gained one test: the repository reads the seeded admin/teacher/student roles back. The log shows one expected `duplicate key` WARN from the duplicate-email test.

## 2.3b — `POST /auth/signup`

- **Flow and shape:** `controller/AuthController` → `service/AuthService.signup` → `UserRepository.save`. Request `{email, password, fullName}`, response `201` with `{id, email, fullName, role}`; never the password or its hash. Records for both DTOs (`SignupRequest`, `SignupResponse`).
- **Role in the body: ignored, not rejected** (the row allowed either). `SignupRequest` has no `role` field, and Spring Boot's Jackson default ignores unknown properties, so a client sending `"role":"ADMIN"` still gets a `STUDENT` and no error. Rejecting would add a 400 path that protects nothing more (nothing can set the role either way). Pinned by a test.
- **Password hashing:** one `PasswordEncoder` bean, `BCryptPasswordEncoder` (strength 10, same as the dev seed hashes), in its own `security/PasswordEncoderConfig` so 2.4b rewriting `SecurityConfig` cannot drop it. `SignupRequest.toString()` is overridden to redact the password: a record's generated `toString` would print it into any log line or exception message that formats the request.
- **Presence only, here:** `@NotBlank` on the three fields (a missing one would otherwise reach the database as a NOT NULL violation, a 500). Everything the next row owns is not done here on purpose: duplicate email, minimum password length, email format. Default Spring error body for 400s; no error-format convention has been decided yet.
- **Hand-offs to 2.3c, both found by probing, not assumed:**
  1. **A duplicate email currently ends as a 500** (the unique constraint throws `DataIntegrityViolationException`). Intentionally untested here so it isn't pinned.
  2. **A password over 72 bytes also ends as a 500:** Spring's `BCryptPasswordEncoder` throws `password cannot be more than 72 bytes` (confirmed with a throwaway test: a 100-character password). BCrypt only uses the first 72 bytes, so the right rule is a maximum of 72 bytes (bytes, not characters, since non-ASCII characters take more) next to the minimum length 2.3c adds. Silent truncation was rejected as a surprise to the user.
- **Security chain (still the 2.2b stand-in, extended):** `POST /auth/signup` is public, and exempt from CSRF *only for that one request matcher*. Anonymous and with no cookie or session to forge a request against, so CSRF protects nothing there. Verified the exemption is what makes it work: with it removed, 8 of the 10 signup tests fail with 403. Whether CSRF is disabled for the whole stateless API is left to 2.4b/2.4a (it depends on the cookie-or-header token choice).
- **Transaction:** `@Transactional` on `signup`. BCrypt hashing (about 100 ms) happens inside it; fine now since there is no AI call or other slow I/O in the transaction (root rule: no AI call inside an open transaction), but if the method ever grows one, hash first and keep the transaction around the `save` only.
- **Tests (`SignupEndpointTests`, 10; real app + Testcontainers, rolled back):** 201 and body without secrets; stored as `STUDENT` with a `$2` BCrypt hash that matches the password and not a wrong one; same password gives different hashes; `role: ADMIN` ignored; no credentials or CSRF token needed; each missing field and each blank field gives 400 and saves nothing; malformed JSON gives 400; `toString` redacts the password; other POST paths still need authentication. The log shows one expected `duplicate key` WARN from the earlier `UserRepositoryTests`.

## 2.3c — Signup validation: duplicate email, password length

- **Duplicate email: catch the unique constraint, no pre-check (the row asked to pick one and be consistent).** `AuthService.signup` does `saveAndFlush` and turns the violation of `users_email_key` into `EmailAlreadyUsedException` (409 Conflict). A check-then-insert (`existsByEmail`) would still need the constraint for the race of two simultaneous signups, so it would be two mechanisms; the constraint alone is race-free and the single source of truth. Only that specific constraint is translated (found by walking the cause chain for Hibernate's `ConstraintViolationException` and comparing the constraint name); any other integrity violation is rethrown untouched so it can't be mistaken for "email taken". The name `users_email_key` is Postgres's default for V1's inline `UNIQUE`; the integration test would fail if it ever changed. `existsByEmail` (2.3a) stays in the repository, unused for now.
- **409 with `@ResponseStatus` on the exception** as a stand-in: 2.6a's global handler will give every error one JSON shape and take over. The body leaks nothing about the other account (a test checks it).
- **Account enumeration:** a 409 on signup tells anyone whether an email is registered. Accepted as the usual trade-off for self-service signup with immediate login (hiding it needs email verification, out of scope for v1).
- **Email normalisation (left to this row by 2.3a): trim + lower-case, applied at signup and, in 2.4a, at signin.** The database constraint is case-sensitive, so without it `Ada@x.com` and `ada@x.com` would be two accounts. `AuthService.normalizeEmail` (public static, `Locale.ROOT` so a Turkish default locale can't turn `I` into a dotless `ı`, covered by a test) is the one place; **2.4a must call it too, or a user who signed up as `Ada@x.com` cannot sign in.** The email is stored and returned normalised. Trimming also happens in `SignupRequest`'s compact constructor so stray spaces from copy-paste don't fail the `@Email` format check (found by two failing tests when only the service trimmed). Existing rows (the dev seed) are already lower-case.
- **Password policy: minimum 8 characters, maximum 72 bytes, nothing else** (`dto/PasswordPolicy` constants, a placeholder pending the human, flagged in the PR). Min length only, as the row says: no composition rules. **The 72 is bytes, not characters,** because BCrypt only uses the first 72 bytes and Spring's encoder throws above that (the 500 found in 2.3b); a custom `@MaxUtf8Bytes` constraint counts UTF-8 bytes (36 `é` = 72 bytes pass, 37 do not). Silent truncation was rejected.
- **Other size limits, to close further 500s:** email and full name are capped at 255 characters (their VARCHAR(255) columns), and the email must pass `@Email` (Jakarta's lenient check: `a@b` is allowed, `not-an-email` is not). The row didn't ask for these; 2.3b said format belonged here.
- **Errors for invalid input are still Spring's default 400 body**; the single consistent error shape is 2.6a.
- **Tests:** `SignupValidationTests` (13) is deliberately *not* `@Transactional`: a duplicate email makes Postgres abort the surrounding transaction (it also made the constraint violation unqueryable afterwards), so it cleans the `users` table before and after each test; checked order-independent with the other classes that share the cached context (alphabetical, reversed, random). `AuthServiceTests` (5, mocked repository): the email constraint maps to 409, another constraint and a plain integrity error pass through unchanged, `normalizeEmail` trims, lower-cases and ignores the default locale. The log shows several expected `duplicate key` WARNs.

## 2.4a — `POST /auth/signin`, JWT issuing

- **Gate resolved by the human (dependency):** a JWT library was needed and none was on the classpath (checked with `dependency:tree`: no Nimbus, jjwt or oauth2), so adding one was a gate. Asked; the human chose **jjwt** (over Spring's OAuth2 resource-server starter and over Nimbus directly) and asked specifically that nothing allow login or signup through other platforms. Added `jjwt-api` (compile), `jjwt-impl` and `jjwt-jackson` (runtime), version 0.13.0 in a `jjwt.version` property (Spring Boot does not manage it). `jjwt-jackson` brings Jackson 2.21.5 next to Boot's Jackson 3.1.5; they coexist (Spring keeps using Jackson 3, the whole suite passes). **No OAuth or social login:** jjwt cannot do it, and `NoSocialLoginTests` guards it (no `oauth2.client`, `resource.server` or `oauth2.jwt` classes on the classpath; `/oauth2/authorization/*` and `/login/oauth2/code/*` are neither served nor redirected, also checked over real HTTP). Signup and signin stay the only ways in.
- **Gate resolved by the human (token delivery): JSON body only.** No cookie, so there is no CSRF exposure and 2.4b can switch CSRF off for the stateless API. A test checks there is no `Set-Cookie` header. **For 8.3b:** the frontend must store the token itself, and its row says not to silently pick `localStorage`: choose and document the storage (memory, `sessionStorage`, ...) explicitly, with the XSS trade-off in mind.
- **Expiry: 24 hours** (`jwt.expiration`, default `24h` in `application.yml`, a `Duration`, must be positive). The row suggested "generous, e.g. 24h" because the spec has no refresh flow. **For Phase 8:** assume a token simply expires 24h after signin and the user signs in again; there is nothing to refresh. The response includes `expiresIn` in seconds so the frontend can handle expiry.
- **Token:** HS256 (explicit, not chosen by key length), claims `sub` (user id), `email`, `role` (the enum name), `iat`, `exp`; never the password hash. Claim names are constants on `JwtService` for 2.4b to share. Validating tokens is 2.4b; this row only issues them. A `Clock` bean (`config/ClockConfig`) makes time fixable in tests.
- **Secret handling:** `JWT_SECRET` binds to `jwt.secret` (relaxed binding), has no default in any profile (not even `dev`: a built-in signing secret would be a standing hole), and must be at least 32 characters, else startup fails. **It is validated in the `JwtProperties` constructor, not with `@NotBlank`/`@Size`**, because Spring Boot's binding error prints the rejected value (`Value: "..."`), which wrote a too-short secret into the startup log (seen on the first real run; a test now asserts the value appears nowhere in the failure chain). `toString` is redacted. Tests get a throwaway secret from the surefire `environmentVariables`, the same mechanism as production; a context-runner test must remove the environment property source to simulate "missing" (the first version of that test passed for the wrong reason).
- **Signin behaviour:** the email is normalised exactly as at signup (`AuthService.normalizeEmail`, as 2.3c required). Unknown email and wrong password give the same `InvalidCredentialsException`, a 401 with the same body. An unknown email still runs one BCrypt comparison against a throwaway hash computed at startup, so response time does not reveal which emails have accounts (unit-tested through the mocked encoder). `signin` is deliberately not `@Transactional` (the BCrypt check should not hold a connection for about 100 ms). Request validation: presence, email at most 255, password at most 72 bytes (a longer one can never be valid; 400); the password policy is not repeated on signin, so it is not revealed.
- **Bug found by the real run, fixed here, and affecting 2.3b/2.3c as well:** over real HTTP every error from an anonymous endpoint came back as **403**, not 400, 401 or 409. Cause: Spring MVC reports an error status by forwarding to `/error`, and the stand-in `SecurityConfig` guarded `/error` like everything else. MockMvc never does that forward, so all MockMvc tests (2.3b's and 2.3c's included) saw the right status and passed. Fixed by permitting `/error` in the chain; 2.4b's replacement chain must keep it. **New `RealHttpAuthTests` (10 tests, a real server on a random port)** pin the contract; verified they fail (5 of 10 get 403) with the `/error` rule removed. The 409 body is Boot's default error JSON (status, error, path; no message, no stack trace); 2.6a defines the final shape.
- **`SignupResponse` renamed `UserResponse`:** it now also appears in the signin response and will in `/auth/me` (2.4c).
- **Not done (suggestion filed):** no brute-force protection on signin (rate limit or lockout); out of scope for the row, noted in `docs/suggestions.md`.
- **Tests (+51):** `JwtServiceTests` (9, fixed clock: claims, roles, expiry, HS256, wrong-secret, tampered and expired tokens rejected, no hash in the payload), `JwtPropertiesTests` (9: missing, blank and short secret and missing, zero and negative expiry fail startup; the secret is never echoed or printed), `SigninEndpointTests` (16, MockMvc), `AuthServiceTests` (4 new signin tests, 9 in all), `RealHttpAuthTests` (10), `NoSocialLoginTests` (2). Backend 256 on a clean build.
- **Real run (throwaway Postgres on 55434, `prod` profile):** no `JWT_SECRET` fails with "must not be blank"; a short one fails without printing it; with a valid one: signup 201, duplicate 409, weak password 400, wrong password and unknown email both 401, signin 200 with a token whose payload decodes to `{"sub":"1","email":...,"role":"STUDENT","iat":...,"exp":iat+86400}` and header `{"alg":"HS256"}`, no `Set-Cookie`, social-login paths 403, protected path 403. (A first attempt of this run was invalid because exporting `MSYS_NO_PATHCONV` broke the Maven wrapper, so nothing started; redone without it.)

## 2.4b — Spring Security config (JWT filter, stateless, public-vs-protected)

- **Unauthenticated is 401, not 403.** The stand-in chain answered 403 to an anonymous call to a protected path (Spring's default with no login mechanism configured). Now an `HttpStatusEntryPoint(401)` answers: plain status, no body, no redirect, no `WWW-Authenticate` challenge. 403 is left for "authenticated but the wrong role" (no such endpoint yet, so untested). `RealHttpAuthTests` was updated from 403 to 401.
- **A bad token is anonymous, not an error.** `JwtAuthenticationFilter` never rejects: on a missing, malformed, forged, unsigned, expired or wrong-algorithm token it leaves the request unauthenticated, so public endpoints still work with a stale token in the browser (tested) and protected ones answer 401. `JwtService.parse` returns an empty `Optional` for every failure reason and does not say why, so a forger learns nothing. A token missing a claim, with a non-numeric `sub` or with a role name that is not in `Role` is also refused. Expiry is judged by the injected `Clock`, so it is unit-tested with a fixed clock (valid until the last second, refused one second after).
- **Claims only, no database lookup per request.** The principal is built from the token, so a deleted user or a changed role takes effect only when their token expires (24h, 2.4a). That is the usual price of a stateless JWT; the spec has no refresh or revocation flow. **For Phase 3+ and the admin promote task:** a promoted teacher keeps `STUDENT` rights until they sign in again. If that matters, the alternative is a lookup per request, which would be a task of its own.
- **CSRF off, with the reason in the code.** The token is never a cookie (2.4a), so no browser attaches credentials on its own. The former per-endpoint CSRF exemptions are gone. Form login, HTTP Basic, logout and the request cache are disabled explicitly rather than relying on defaults; `/login` and `/logout` do not exist (401 anonymous, 404 with a token).
- **Filter is not a bean.** A `OncePerRequestFilter` that is a `@Component` is also registered in the servlet container outside the security chain; `SecurityConfig` instantiates the one instance and adds it before `UsernamePasswordAuthenticationFilter`. Authority is `ROLE_<name>` so `hasRole` works in later phases.
- **Side effect on an existing test:** `HealthEndpointDownTests` (a `@WebMvcTest` importing `SecurityConfig`) failed to load because the chain now needs a `JwtService`; it gets a `@MockitoBean` (no token is sent there).

## 2.4c — `GET /auth/me`

- **Reads the user from the database by the token's subject, not from the claims.** The row says "current user from the JWT"; the JWT supplies only the id (the `AuthenticatedUser` principal). Reason: 2.4b's filter trusts claims, so a role changed after signin (admin promotion) would otherwise be invisible in `/auth/me` for up to 24h; reading the row shows the current name and role at once, and it is the one place the frontend can learn that a token outlived its account. Cost: one primary-key lookup per call. The token's own role still decides authorisation until it expires (see 2.4b). Tested: a role changed in the database after signin shows in `/auth/me`.
- **A valid token whose user was deleted is 401** (`AccountNoLongerExistsException`, `@ResponseStatus`, same interim approach as `InvalidCredentialsException` until 2.6a), the same status as a token that does not verify, so the client reacts the same way (sign in again). Not 404: the caller's identity, not a resource, is what is missing.
- **Response is `UserResponse`** (`id`, `email`, `fullName`, `role`), the same shape as signup and in signin's `user`; never the hash. No new DTO.
- **Tests (+10):** `RealHttpMeTests` (8, real server: signup → signin → `/auth/me` end to end, no hash or cookie in the response, no token 401, bad token 401, deleted user 401 with no internals in the body, current role not the token's, each user gets their own account, POST is 405), `AuthServiceTests` +2. Backend 290 on a clean build; ai-service and frontend (tests, lint, format, build) pass.

## 2.4d — CORS configuration

- **No credentials.** 2.4a put the token in the JSON body and the `Authorization` header only, so `Access-Control-Allow-Credentials` is never sent and the allowed origin is always an exact string, never `*`.
- **Unset means closed, a bad value stops startup.** `CORS_ALLOWED_ORIGINS` has no default in `application.yml` (the Vite origin lives in `.env.example`, as decided in Phase 0). If the variable is missing or empty no cross-origin call is allowed, the safe failure; a same-origin or non-browser client is unaffected. An entry that is a wildcard, has a path, a query, a trailing slash or a non-http(s) scheme fails startup with a message naming the variable, because a browser compares origins as exact strings and such an entry would never match. Spaces and empty entries from a stray comma are tolerated, duplicates dropped.
- **Wired through `http.cors(...)`, not a `CorsFilter` bean.** That runs the check inside the security chain ahead of authentication, so a preflight `OPTIONS` (no token) is 200 rather than 401, and a 401 to the frontend still carries `Access-Control-Allow-Origin` so the browser lets the app read it and send the user to sign in.
- **Fixed lists for methods and headers** (`GET POST PUT PATCH DELETE OPTIONS`; `Authorization`, `Content-Type`, `Accept`), not "echo whatever was asked". Preflight cached for 1h. Nothing is exposed to scripts beyond the CORS-safelisted response headers; add `exposedHeaders` if a later task needs one (e.g. a download filename).
- **A disallowed origin gets 403 even with a valid token**, Spring's default for a cross-origin request that is not on the list. Requests with no `Origin` header (curl, server to server, same-origin) are not CORS requests and are unaffected.
- **Tests (+36):** `CorsPropertiesTests` (20: comma list, environment-variable binding, trimming, empty/unset, 11 rejected forms, config has no wildcard or credentials), `RealHttpCorsTests` (16, real server: preflight without token, signin preflight, second origin, six look-alike origins refused, unlisted method/header refused, header on 200/401/public, no credentials header, other origin 403 with a valid token, no `Origin` untouched).
- **Unrelated fix found by the full run:** `JwtServiceTests.theTokenIsSignedWithHmacSha256` (2.4a) parsed with jjwt's real clock against a token issued at a fixed `2026-10-06T12:00Z` and valid 24h, so it began failing on 2026-10-07 12:00Z. It now uses the fixed clock like the other parsers in that file. No production code involved.

## 2.5a — Method-level security and the role convention

- **Convention: `@PreAuthorize` on the controller method, not URL matchers.** The row asked to pick one and use it everywhere. The rule then sits next to the code it guards, and Phase 3's ownership checks (3.1c) are expressions on the same annotation, which URL matchers cannot do. `SecurityConfig` keeps deciding only "signed in or not" (public list, everything else authenticated). Class-level `@PreAuthorize` is not used, so one look at a method shows who may call it.
- **No role hierarchy.** Roles are listed explicitly (`hasAnyRole('TEACHER', 'ADMIN')`). The spec does not say ADMIN inherits TEACHER, and the Phase 3 and 5 rows spell out "owning teacher or admin" / "admin sees all", which only makes sense without a hierarchy. If the human wants one it is a `RoleHierarchy` bean and a task of its own.
- **No custom meta-annotations (`@AdminOnly`, ...).** They would save a few characters but hide the rule behind a name, and Phase 3 needs the full expression anyway. The risk with raw strings (a typo like `hasRole('TEACHR')` compiles and locks everybody out) is covered by `PreAuthorizeConventionTests`, which reads the real controllers and checks every role name is a `Role`.
- **Statuses:** anonymous or bad token 401, signed in with the wrong role 403 with an empty-of-internals body and no `WWW-Authenticate`. The 403 survives the error dispatch to `/error` because that path is public (2.4a); tested over real HTTP.
- **Testing without a real restricted endpoint:** none exists yet, so `RealHttpRoleSecurityTests` nests a probe `@Controller` in the test class. Spring Boot's test type filter keeps classes nested in a test class out of component scanning, so no other test sees it. Spring 6+ does not treat a bare type-level `@RequestMapping` as a handler, hence `@Controller`. The first run of the test, before `@EnableMethodSecurity` was in place, returned 200 to students on the admin endpoint, so the test does catch a missing or disabled rule.
- **Tests (+10):** `RealHttpRoleSecurityTests` (7: each of the three roles against admin-only, teacher-or-admin and any-signed-in; anonymous 401 on all; bad token 401; refused caller learns nothing; allowed role gets the response), `PreAuthorizeConventionTests` (3).

## 2.5b — `PATCH /admin/users/{id}/role`

- **Body is `{"role": "TEACHER"}`, exact enum spelling.** `@NotNull Role`: a missing, null, numeric, lower-case or unknown value is a 400 (Jackson refuses it), and nothing is written. No leniency on case, so the frontend's role selector (8.5b) sends the enum names.
- **Last-admin rule counts under a lock.** A plain "count the admins" check is not enough: two admins demoting each other at the same moment would each see the other as an admin and leave none. `changeRole` first runs `SELECT ... FOR UPDATE` over the admin rows (ordered by id, so callers lock in the same order), then decides. The second request waits for the first to commit and counts again, so exactly one succeeds (200) and the other gets 409. The lock is taken on every role change, not only demotions: role changes are rare and this also serializes a promotion against a demotion. Verified by mutation: with the lock replaced by a plain read the race test fails 5 of 5 runs.
- **Self-demotion is allowed while another admin exists**; the last admin cannot demote themselves (409). Setting the role a user already has is a 200 no-op, including for the last admin, so a retried request is harmless.
- **409 for the last admin, 404 for an unknown id**, both declared with `@ResponseStatus` for now like the other interim errors (2.6a unifies the shape).
- **Known consequence of claims-only tokens (2.4b), for the human to weigh:** the role is a token claim and there is no revocation, so a promoted user keeps their old rights until they sign in again, and **a demoted admin or teacher keeps their old rights until their token expires, up to 24h** (2.4a). `/auth/me` reflects the change at once because it reads the database. Closing this needs a per-request lookup or a token-version/revocation scheme, which is a task of its own; nothing was built for it here. Tested as the current behaviour (old token still 403 on an admin call after promotion, new signin works).
- **No audit trail.** The spec has no audit table; who changed whose role is not recorded.
- **Tests (+25):** `RealHttpAdminRoleTests` (real server: promote, demote, make admin, no-op, student/teacher/anonymous/bad token refused with nothing changed, unknown id, 8 bad bodies, non-numeric id, PUT/POST/DELETE 405, last admin 409, self-demotion with a second admin, two admins demoting each other (repeated 5×), promotion visible in `/auth/me` and the next signin). `PreAuthorizeConventionTests` now also covers the new controller.

## 2.5c — `GET /admin/users`

- **Pagination shape chosen by the human at the gate** (nothing in the docs defined one): our own envelope `PageResponse<T>` `{items, page, size, totalElements, totalPages}` with `?page=0&size=20`, rather than Spring Data's `PagedModel`. Page is 0-based, default size 20, maximum 100. Phase 5's lists (5.5c) and the admin page (8.5b) reuse it; the convention is in `backend/CLAUDE.md`.
- **Over-large `size` is clamped, not refused**, and the response reports the size actually used so a client is not misled; a size below 1 or a negative page is a 400. An empty `page=` is treated as absent (Spring turns the empty string into null) and gets the default; I kept that rather than add code to refuse it.
- **Bug found by the tests: a huge page number was a 500.** `page=2147483647&size=100` made the row offset overflow the `int` JPA takes (`setFirstResult`). `PageResponse.pageable` now throws `PageOutOfRangeException` (400) when `page × size` exceeds `Integer.MAX_VALUE`, so every list gets the guard. The last addressable offset still returns an empty page with 200.
- **Order is by id** (stable, never changes, so pages do not overlap or skip while accounts are added at the end). No search or filter and no other sort: the row asks for the list only. If 8.5b needs searching by email, that is its own task.
- **Rows are `id`, `email`, `role` only** (`UserSummaryResponse`): "email and role only" from the row, plus the id because `PATCH /admin/users/{id}/role` needs it. No name, no hash, no creation date.
- **Tests (+19):** `RealHttpAdminUserListTests` (16, real server: fields, envelope, 25 users across three pages in order without overlap or gaps, page past the end, offset limit, clamping, 7 bad parameters, empty `page=`, student/teacher 403 and anonymous/bad token 401, a promotion showing in the list), `PageResponseTests` (3).

## 2.6a — Global exception handler and the error shape

- **Shape chosen by the human at the gate** (nothing in the docs defined one; 8.2a builds the frontend wrapper on it): our own `{status, code, message}` with `fieldErrors: [{field, message}]` on validation errors only, over RFC 7807 `problem+json`. The `code` is a stable name from the `ErrorCode` enum so the frontend never parses text.
- **Every error our code raises extends `ApiException`**, which takes an `ErrorCode` (status + code + fixed message in one place). The six interim `@ResponseStatus` exceptions (2.3c–2.5c) were converted; their statuses and messages are unchanged, they now also carry a code (`EMAIL_ALREADY_USED`, `INVALID_CREDENTIALS`, `ACCOUNT_NO_LONGER_EXISTS`, `USER_NOT_FOUND`, `LAST_ADMIN`, `PAGE_OUT_OF_RANGE`). `ErrorCode` and `ApiException` live in `dto` (they are the API contract) to avoid a new top-level package.
- **Spring's own exceptions go through `ResponseEntityExceptionHandler`'s single `handleExceptionInternal`**, which ignores Spring's message and answers a fixed one per status. That covers malformed JSON, wrong parameter types, missing parameters, 404, 405 (the `Allow` header is kept), 406 and 415 without listing them, and cannot leak parser text, class names or the rejected value. Statuses with no code of their own become `REQUEST_REJECTED` (other 4xx) or `INTERNAL_ERROR`.
- **Validation errors list field and reason, never the value** (a rejected value can be a password); sorted by field so the order is stable. Request parameters failing `@Min` (2.5c) are reported under the parameter's name.
- **Unexpected exceptions are a generic 500** with the cause logged at ERROR and nothing else in the body. A catch-all handler would also have swallowed method-security refusals (they are thrown from inside the controller call and used to reach the security filters), turning every 403 into a 500; so `AccessDeniedException`/`AuthenticationException` are handled explicitly, anonymous 401 and signed-in 403, as the filters answered before.
- **The security chain and the servlet container answer in the same shape.** Their errors never reach the MVC handler, so `JsonAuthenticationEntryPoint` / `JsonAccessDeniedHandler` write the body with the injected `JsonMapper` (Jackson 3), and `ApiErrorController` replaces Boot's `/error` for errors raised by the container. 401 still has no redirect and no `WWW-Authenticate` (2.4b).
- **Not done:** `DataIntegrityViolationException` and similar are a generic 500 here (the one known unique constraint, the email, is already translated to 409 in `AuthService`). No `Retry-After`/rate limiting codes, no i18n of messages.
- **Tests (+26):** `RealHttpErrorShapeTests` (14, real server: 401/403 from the chain and from method security, each of our codes, validation without echoed values and in stable order, parameter validation, malformed JSON/types without parser text, 404, 405 with `Allow`, 415, a probe endpoint that throws giving a 500 with no internals, exact body keys), `ErrorPiecesTests` (10: codes, `forStatus` mapping, handler cases, container error page), `JsonSecurityErrorTests` (2). All 380 earlier tests passed unchanged: none asserted an empty error body.

## 2.7a — Shared Testcontainers setup and base class

- **Measured first:** one full backend run started **eight** `postgres:16` containers, because every distinct Spring context (a profile, a property, a `@MockitoBean`, `@DirtiesContext`) built its own `@ServiceConnection` container bean. Now it starts one (checked by counting "Creating container" in the Maven log: 8 → 1). Backend run time 42.9 s → 27.7 s on this machine.
- **One container, one database per context, not one database for all.** A single shared database would have broken tests that depend on a clean one: the dev-seed tests run Flyway with extra locations (V1000+), which the default-location contexts would then reject as applied-but-unresolved, and `FlywayOutOfOrderTests` applies a probe migration and uses `@DirtiesContext` precisely so nobody sees it. So `SharedPostgres.newDatabase()` runs `CREATE DATABASE test_<uuid>` in the shared container for each context. Isolation is exactly what it was; only the container start is saved. Databases are never dropped (the container goes at the end of the JVM).
- **`JdbcConnectionDetails` bean instead of `@ServiceConnection`.** The container is no longer a bean of any context, so closing one cached context cannot stop the database under another. The bean takes precedence over `spring.datasource.*` and over `SPRING_DATASOURCE_*` (so a developer's env cannot reach a test), and Boot's `DataSource` and Flyway both read it. Same mechanism name (`TestcontainersConfiguration`) and same `@Import` in all 34 test classes: nothing about how a test asks for a database changed, so no second mechanism exists.
- **The container is started in a static initializer** the first time a test needs a database, so the pure unit tests still run without Docker. It relies on one test JVM per run (Surefire's default); parallel forks would each get their own container, which still works.
- **`RealHttpTestBase`** for tests over real HTTP: the same eight lines of fields, cleanup and request helpers were copied into every `RealHttp*Tests` class. Four classes written in this phase (`AdminRole`, `AdminUserList`, `ErrorShape`, `Cors`) moved onto it (−181 lines, same 406 tests); 2.7b–2.7d and later phases extend it. `RealHttpAuthTests`, `RealHttpMeTests`, `RealHttpJwtFilterTests` and `RealHttpRoleSecurityTests` were left alone: their helpers take the full `Authorization` header or differ in other small ways, and rewriting every call in them was churn for no new behaviour.
- **Left in place:** the `spring-boot-testcontainers` and `testcontainers-junit-jupiter` test dependencies are now unused by our code (only `testcontainers-postgresql` and `JdbcConnectionDetails` are). Removing a dependency is a `pom.xml` change outside this row, so it is noted in `docs/suggestions.md` instead.
- **Tests:** no new test classes; the change is the infrastructure under all 406 and they pass unchanged.

## 2.7b — Signup → signin → protected endpoint

- **A new class, `AuthFlowIntegrationTests extends RealHttpTestBase`** (the first user of the 2.7a base class), not more cases in `RealHttpMeTests`: that class tests `/auth/me`; this one tests that the earlier pieces agree with each other, feeding only what one response gives the next request (ids, the token string), never the repository or `JwtService.issue`.
- **What it pins down that the unit-level tests do not:** the id in the signup response is the `sub` of the token signin issues (`JwtService.parse` returns exactly `AuthenticatedUser(id, email, STUDENT)`); the user in the signin response is the signed-up one; `expiresIn` equals the configured `jwt.expiration`; `/auth/me` with that token returns the same account; the same token is accepted on `/admin/users` and judged by the role rule (403, not 401); no token or a token with its signature altered is 401; two users each get their own identity; signing in twice gives two tokens that both work (stateless); an email typed with spaces and capitals at signup is found by a differently capitalised signin; signin before signup gives no token; no response in the flow contains the password or a hash.
- **One test sleeps 1.1 s** (`signingInAgainGivesAnotherTokenAndTheFirstKeepsWorking`): tokens are stamped to the second, so two signins in the same second would give an identical string. Cheaper than injecting a clock into a running server.
- **Passwords in tests** are the plain phrase `correct horse`; GitGuardian flagged a made-up random-looking one on PR #56.
- **Tests (+10):** `AuthFlowIntegrationTests`. Backend 416.

## 2.7c — Duplicate signup and wrong password

- **Mostly covered already, so only the gaps were written.** The rules themselves have fast tests: `SignupValidationTests` (409, normalization, no leak) and `SigninEndpointTests` (401, same answer for unknown email and wrong password), both MockMvc, plus a few status checks in `RealHttpAuthTests`. `AuthRejectionIntegrationTests extends RealHttpTestBase` adds what they do not: the behaviour over a real server and database, with the 2.6a error codes.
- **Duplicate signup:** 409 with `code` `EMAIL_ALREADY_USED`; case and surrounding spaces make the same account; **a rejected duplicate cannot take over the account** (the stored hash and name are unchanged, the original password still signs in, the attacker's does not); and **six signups for one email released together give exactly one 201 and five 409, never a 500, and one row** (repeated 3×). That last one is the proof of the comment in `AuthService.signup` that the unique constraint, not a pre-check, decides; nothing tested it under concurrency before.
- **Wrong password:** 401 with `INVALID_CREDENTIALS`, no token, no cookie; every near-miss is refused (other capitals, one character more or less, leading/trailing space, doubled space, a NUL character, another user's password); the answer for a wrong password and for an unknown email is identical in status, body and header names (the hint to an attacker would be a difference); a failed signin does not touch the stored hash; a 73-byte password is a 400, not a 500.
- **Deliberately not asserted:** that many wrong attempts never lock the account. There is no lockout (see the 2.4a suggestion about brute-force protection); a test of "never locked" would have to be deleted by whoever adds one.
- **Tests (+20):** `AuthRejectionIntegrationTests` (counting the 3 repetitions and 8 password variants). Backend 436.

## 2.7d — Role matrix

- **A table, not a list of tests.** `RoleMatrixIntegrationTests` holds one `ENDPOINTS` row per endpoint and runs every row against five callers (nobody, bad token, student, teacher, admin): 6 endpoints × 5 callers = 30 checks from six lines. The expected answer is derived from the row (public / any signed-in / these roles): 401 with `UNAUTHENTICATED` for an anonymous or bad-token caller, 403 with `ACCESS_DENIED` for a signed-in caller with the wrong role, "anything but 401/403 and below 500" for a caller who may pass (the endpoint answers itself: 400, 404, 200).
- **Later phases cannot forget it.** `everyMappedEndpointHasARowInTheMatrix` reads the handler mappings Spring built and compares them with the table; a new controller method without a row fails the build with the missing `METHOD /path` named (checked by removing a row: it fails naming `GET /health`). Only `/error` is exempt (the container's error page, public by design). This is the "every later phase adds its endpoints" of the task row, made mechanical.
- **Signup cannot create a teacher or an admin:** nine ways of asking in the body (`role` TEACHER/ADMIN/ROLE_ADMIN, `Role`, `roles`, `authorities`, `admin`, `isAdmin`, a nested `user.role`) all give 201, role `STUDENT` in the response and in the database, and the token of that account is a student's on `/auth/me` and 403 on both admin endpoints. A second test follows a real promotion: the student cannot promote themselves (403, unchanged), the admin promotes her, after the next signin she is a teacher, and a teacher is still refused on every admin endpoint.
- **Finding: wrong role plus malformed body is 400, not 403.** The first version of the matrix sent `{}` to every endpoint and failed for student and teacher on `PATCH /admin/users/{id}/role`: they got the 400 of body validation. Cause: Spring resolves and validates `@RequestBody` before invoking the controller method, and `@PreAuthorize` (2.5a) is an advice around that method. Consequences are small: no user data is revealed (with a valid body a non-admin gets 403 whether or not the user exists, tested), an anonymous caller is stopped by the filter chain (401) before any parsing, and the caller learns only the body rules of an endpoint that exists. Not changed here, because closing it means either validating by hand inside every admin method or an authorization check ahead of argument resolution (an interceptor), both of which reverse the convention chosen in 2.5a. The matrix rows therefore carry a body that is valid for their endpoint, and `aWrongRoleCallerMayStillSeeValidationOfAMalformedBody` pins the current behaviour with a comment saying it should flip to 403 if this is ever closed. Raised with the human in the PR and in `docs/suggestions.md`.
- **Anonymous callers cannot map the protected API:** unknown paths under `/admin` and unsupported methods on `/admin/users` are 401, not 404/405.
- **Tests (+44):** `RoleMatrixIntegrationTests` (30 matrix checks, the guard, 2 ordering tests, 9 signup variants, the promotion lifecycle, the unknown-path test). Backend 480.
- **Phase 2 is complete** with this row.
